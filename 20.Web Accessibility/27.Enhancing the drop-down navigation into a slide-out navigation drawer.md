In this chapter we’re going to discuss the accessible implementation as well as important usability considerations of two common mobile navigation patterns.

In both patterns, the mobile navigation is initially hidden; and it is shown when a navigation button is activated.

In the first pattern, when the navigation is shown, it takes up its natural place in the page’s layout.

In the second pattern, it slides out of the left side of the viewport like a drawer; and when it does, it overlays (and obscures) the page’s content.

## Hiding and showing the navigation using the navigation toggle

In the first pattern, when the JavaScript runs, the navigation is hidden, and a navigation button is presented to the user in its place.

The navigation button is typically implemented as an icon button. But to make our button more inclusive, we’re going to give it a visible text label, and we will hide the icon from assistive technologies using the `aria-hidden` attribute:

```html
<button>
  <svg
    height="21"
    viewBox="0 0 24 24"
    width="24"
    aria-hidden="true"
    style="color: inherit;">
    <path
      d="M3 13h18c0.552 0 1-0.448 1-1s-0.448-1-1-1h-18c-0.552 0-1 0.448-1 1s0.448 1 1 1zM3 7h18c0.552 0 1-0.448 1-1s-0.448-1-1-1h-18c-0.552 0-1 0.448-1 1s0.448 1 1 1zM3 19h18c0.552 0 1-0.448 1-1s-0.448-1-1-1h-18c-0.552 0-1 0.448-1 1s0.448 1 1 1z"
      fill="currentColor"></path>
  </svg>
  Navigation
</button>
```

When the button is activated, it toggles the visibility of the navigation. To communicate the state of the navigation (whether it’s expanded or collapsed), we will give the button an `aria-expanded` state attribute:

```html
<button
  class="nav-toggle"
  aria-expanded="[ true | false ]"
  hidden>
  <svg
    height="21"
    viewBox="0 0 24 24"
    width="24"
    aria-hidden="true"
    style="color: inherit;">
    <path
      d="M3 13h18c0.552 0 1-0.448 1-1s-0.448-1-1-1h-18c-0.552 0-1 0.448-1 1s0.448 1 1 1zM3 7h18c0.552 0 1-0.448 1-1s-0.448-1-1-1h-18c-0.552 0-1 0.448-1 1s0.448 1 1 1zM3 19h18c0.552 0 1-0.448 1-1s-0.448-1-1-1h-18c-0.552 0-1 0.448-1 1s0.448 1 1 1z"
      fill="currentColor"></path>
  </svg>
  Navigation
</button>
```

This all sounds familiar, doesn’t it?

**The navigation button is a disclosure widget.** A disclosure widget is a control (typically a button) whose sole purpose is to toggle the visibility of some content.

But this disclosure widget doesn’t toggle the visibility of just _any_ content. It toggles the visibility of the `<nav>` element, which exposes one of the most important landmark regions of the page.

```css
/* Hide the navigation when the aria-expanded state attribute is false */
.nav-toggle[aria-expanded="false"] + .site-nav {
  display: none;
}
```

## Hide the navigation list, not the landmark

As we’ve learned in [the landmark regions chapter,](https://practical-accessibility.today/chapters/landmark-regions/) using page landmarks is a fundamental way for screen reader users to access page content. And the navigation landmark is one of the first landmarks users look for on a page.

If the `<nav>` element is hidden, so is the landmark it exposes. As such, the landmark will no longer be reachable via screen reader shortcuts, and the user will not have **easy access** to its contents when they need it. For example, the navigation landmark will no longer be listed in the Landmarks list in VoiceOver’s Web rotor; nor in NVDA’s landmarks list. The user can, technically, still find the navigation through the navigation button, but that’s not how screen reader users typically navigate web pages.

"You see, users of [assistive technologies] don’t just start feverishly tabbing through an interface just hoping to find what it is they’re looking for, says accessibility engineer Scott O’Hara in his article “(Navigation) Landmark Discoverability” Well. Maybe they would if they were trying to prove a point about how horrible a site was coded. But yeah. Not really."

To avoid degrading the usability of the page, **you want the `<nav>` element and the landmark it exposes to remain persistent and reachable by landmark navigation.**

To do that, instead of hiding the `<nav>` element itself, you should hide **the content of the navigation**—whether that be the primary list element (`<ul>`) or a `<div>`— a container—surrounding multiple components of the navigation. In other words, the navigation button should control the contents of the navigation, not the navigation element itself.

So, when the navigation button is activated, the navigation landmark persists, and you show and hide the contents of the navigation instead.

Then, if you pull up the list of landmarks on the page, the navigation landmark will be exposed in the list, and the user can use landmarks shortcuts to find it and navigate to it more efficiently.

You should also **place the navigation button inside the navigation landmark.**

### Place the navigation button _inside_ the navigation landmark

When the user navigates to the navigation landmark after its content has been hidden, they will land in an empty landmark region, and might therefore be confused.

The high level intent of hiding the navigation is to visually hide it from view until a user specifically wants to interact with it, _"but the overall intent is likely not to obscure the fact that a navigation exists,"_ says Scott O’Hara. _"Sighted users can see the navigation toggle button, and understand that this will show/hide a navigation per its common visual design. This same affordance needs to be provided to users of assistive technology."_

Placing the button inside the `<nav>` element allows for the navigation landmark to always have discoverable content within it (the button).

So now when the user accesses the navigation landmark, they will find a disclosure widget. This disclosure widget communicates that the content of the navigation is there, and that they can reveal it when they want.

```html
<nav class="nav">
  <button
    aria-expanded="[ true | false ]"
    class="nav-toggle"
    hidden>
    Navigation
  </button>

  <div class="nav-content">
    <ul role="list">
      <!-- navigation items -->
    </ul>
  </div>
</nav>
```

By placing the button inside the navigation before the navigation content, you can now also use the adjacent sibling selector to hide the navigation content when the `aria-expanded` state attribute on the button is `false`, instead of toggling the `hidden` attribute on the navigation content using JavaScript.

```css
/* Select and hide the nav content container, not the <nav> element itself */
.site-nav
  .nav-toggle[aria-expanded="false"]
  + .nav-content {
  display: none;
}
```

### Main takeaways

So the two main takeaways from this section are:

1. When the navigation is meant to be hidden, don’t hide the `<nav>` element. Hide the navigation content instead. This ensures that the navigation landmark region remains available and reachable by landmark navigation.
2. Place the navigation button inside the navigation landmark region. This ensures that the navigation content is discoverable by screen reader users.

## Enhancing the navigation into a slide-out navigation drawer

Quite often when the navigation is hidden on mobile, it is positioned off-screen — outside the viewport bounds; and when the navigation button is activated, it slides out into view like a drawer. This pattern is known as the “navigation drawer”.

A navigation drawer slides in from the left (or right), spans the height of the screen, with everything behind it visible but darkened by a scrim. [(Material Design System)](https://m1.material.io/patterns/navigation-drawer.html#)

The scrim is the translucent background behind the navigation.

In other words, this navigation overlays the page’s contents when it is shown, **similar to how a modal dialog does.**

The core markup for this pattern is the same as the previous pattern we just created. We have the navigation and the navigation button. But this pattern requires a few additions in markup, styles, and interactivity to make it accessible.

The hiding technique you choose to hide the navigation when it is off-screen, as well as the keyboard interactions you implement (or don’t implement!) will determine how accessible and usable this navigation pattern is.

### Choosing a hiding technique for the navigation drawer

When the navigation content is hidden from view, it must be hidden from all users. So it’s not enough to move the navigation content off-screen using CSS positioning properties and transforms. Doing so will hide it from sighted users, but not from keyboard and screen reader users.

You must choose a hiding technique that ensures that the navigation content cannot be reached by keyboard or other assistive technologies when it is out of view.

We learned in the hiding techniques chapter that there are three [hiding techniques](https://practical-accessibility.today/code/hiding-techniques/) that achieve that:

- the HTML hidden attribute (hides it from all users),
- the HTML inert attribute (makes content inert so it becomes unreachable by keyboard and prevents it from being discoverable by AT), and
- the CSS `display: none` and `visibility: hidden` declarations (also make content inaccessible to keyboard and AT users).

I like to use the `inert` attribute in combination with CSS positioning properties.

```css
/* move the navigation content outside the viewport bounds */
.nav-toggle[aria-expanded="false"]
  + .nav-content {
  position: fixed;
  z-index: 10;
  width: 75vw;
  top: 0;
  left: 0;
  bottom: 0;
  overflow-y: auto;
  transform: translateX(-100vw);
  ...;
}
```

```html
<nav
  class="site-nav"
  id="site-nav"
  aria-labelledby="nav-label">
  <span hidden id="nav-label">Site</span>
  <button
    aria-expanded="false"
    class="nav-toggle">
    .. Navigation
  </button>

  <!-- When the navigation is off-screen, make it inert -->
  <div class="nav-content" inert>
    <ul role="list">
      ..
    </ul>
  </div>
</nav>
```

Moving the navigation content off-screen using CSS hides it from sight. And adding the inert attribute ensures it cannot be reached by keyboard or screen readers. You can then use CSS transitions or animations to animate the navigation back into view when the navigation button is activated.

```css
.nav-toggle[aria-expanded="true"] + .nav-content {
  /* move the nav content back into view */
  transform: translateX(
    0vw
  ); /* add the translucent
background behind the navigation */
  box-shadow: 0 0 0 150vmax rgba(0, 0, 0, 0.75);
}
```

And when you do, the inert attribute is removed and the navigation content becomes interactive again.

When you hide the navigation off-screen, perform a quick manual test to ensure that it is properly hidden by tabbing through the page with a keyboard. If the navigation receives keyboard focus, then it’s an indication that you need to choose a different hiding technique, or make the navigation inert.

I love using [the Accessibility Insights Chrome extension](https://accessibilityinsights.io/) when I test the tabbing order on a page. This extension will create a visual path that “follows” you as you make your way through the interactive elements on the page.

To use the extension:

1. (After installation) Run a **Fast Pass** on the page that you’re testing.
2. Then go to **Tab Stops** and check the **Visual helper** option.
3. Then, start pressing tab to navigate the page.

If your keyboard focus moves to the invisible navigation items, it means that the navigation is still reachable by keyboard and screen readers, and that you have some work to do to fix it.

[using-accessibility insights chrome extension](/markdown-assets/27.1.using-accessibility%20insights%20chrome%20extention.mp4)

In this video, I am using the extension to demonstrate how keyboard focus moves to the hidden navigation when the navigation is only visually hidden using CSS, but not made inert. You can see the visual path "follow" my keyboard focus to items that are not visible. This indicates that those items need to be made inert, or that you need to choose a different hiding technique.

### Adding the necessary semantics and behavior to the navigation drawer when it is shown

#### When the navigation drawer is shown, make the page content inert

When the navigation drawer is shown, it obscures the remaining content of the page, **like a modal dialog does**. The content behind it is dimmed, indicating that it cannot be interacted with until the navigation is closed. What this means is that, while the navigation is shown, **the page’s content must be inert.**

Screen reader users can navigate a page in various ways, which include but are not limited to using keyboard shortcuts and using a virtual cursor. Making the page inert is critical to **preventing them from navigating to a link or a heading (or other elements)** in the wrong context (the right context being the navigation overlay).

Furthermore, keyboard users must be able to see where their focus is at any time. If their focus moves to an element outside the navigation and that is obscured by it, they will lose track of their position on the page. This is a usability problem, and a violation of WCAG 2.2 Success Criteria: **2.4.11 Focus Not Obscured (Minimum) (AA)**, and **2.4.12 Focus Not Obscured (Enhanced) (AAA).** You may prevent that from happening by closing the navigation when keyboard focus moves outside of it. But we’ll get to this later.

Using JavaScript, you can find and select all the top-level page landmarks (the banner **excluding the navigation itself,** the main landmark, the contentinfo landmark, and any other top-level complementary landmarks) and make them inert using the `inert` attribute. Making the landmark regions inert will make all the content inside of them inert.

#### Provide a way to dismiss the navigation drawer when it is shown

When the navigation drawer is shown, it obscures the page’s content, **including the navigation button.**

So, when the navigation is shown, you want to provide the user with a way to dismiss it. To do that, provide a separate button — a _Close_ button — inside the navigation drawer.

#### Provide a button to dismiss the navigation drawer

The Close button should precede all the navigation content (which, in our case, is the navigation list).

```html
<nav
  class="site-nav"
  id="site-nav"
  aria-labelledby="nav-label">
  <span hidden id="nav-label">Site</span>
  <button
    aria-expanded="false"
    class="nav-toggle">
    .. Navigation
  </button>

  <!-- When the navigation is off-screen, make it inert -->
  <div class="nav-content" inert>
    <button id="nav-closeBtn">Close</button>

    <ul role="list">
      ..
    </ul>
  </div>
</nav>
```

#### Make the navigation drawer dismissible using the Escape key

It is also a common practice to make modal dialogs dismissible using the `Esc` key. So, in addition to the Close button, the navigation drawer should be dismissible using the `Esc` key.

#### Move focus back to the navigation button when the navigation drawer is closed

Then, when either the Close button is activated or the Esc key is pressed, the navigation is hidden, and **keyboard focus should back to the navigation button.**

### Move keyboard focus to the Close button when the navigation is shown

As we just mentioned, when the navigation drawer is shown, it obscures the page’s content, including the navigation button and, by extension, the user’s keyboard focus. So, when the navigation is open, you want to **move focus to a visible focusable element inside of the navigation.**

Adrian Roselli wrote [an article](https://adrianroselli.com/2020/10/dialog-focus-in-screen-readers.html) to help you decide what to move focus to when you’re creating a modal dialog, which is a similar use case to our navigation drawer. In his article, he shares the results of how various dialog implementations _generally_ announce with default screen reader settings. You can use his test results as a starting point to inform your larger decision on which approach works best for all your users.

In most modal dialogs, it is a common practice to move focus to the first focusable element in the dialog. Since the Close button is the first focusable element in the navigation drawer, it is also a common practice is to move focus to this button when the drawer is shown:

```javascript
const navCloseBtn =
document.getElementById("nav-closeBtn");
..
function showNavigationContent(e){
  // show the navigation
   ...
  // and then move focus to the close button inside of it
 navCloseBtn.focus();
}
```

#### Give the navigation content container a role and a name

When focus moves to the navigation’s Close button, the screen reader announces the button. But it doesn’t announce the context of the button. So someone who can’t see the navigation may not understand why, after activating the navigation button, their focus was moved to a Close button, when all they wanted to do was to expand the navigation.

Typically, in modal dialogs, when focus is moved to the dialog’s Close button, a screen reader will announce the button (its name and role), followed by its context: “dialog”.

To provide the user with more context for the Close button, we can give the navigation content container a meaningful role and a name, so that when the button is announced, its context is announced with it.

The navigation content container is a generic `<div>` element. `<div>`s are name-prohibited. We learned in [the accessible names and descriptions chapter](https://practical-accessibility.today/chapters/mobile-navigation/chapters/accName/#not-all-elements-can-have-a-name) that if you use a `<div>` as a container for a region that needs a name, you will need to give it a meaningful role so that it qualifies for an accessible name.

You can give it either the group role, or a dialog role. The role you choose **will depend on how you manage keyboard focus inside the navigation when it is open.** We will discuss when either of these is appropriate shortly.

Once you’ve given the navigation content container a meaningful role, then, using `aria-labelledby`, you can use the navigation button to provide an accessible name to the group.

```html
<nav
  class="site-nav"
  id="site-nav"
  aria-labelledby="nav-label">
  <span hidden id="nav-label">Site</span>
  <button aria-expanded="false" id="nav-toggle">
    Navigation
  </button>

  <div
    role="[ group | dialog ]"
    aria-labelledby="nav-toggle"
    class="nav-content">
    <button id="nav-closeBtn">Close</button>

    <ul role="list">
      <!-- navigation items -->
    </ul>
  </div>
</nav>
```

The name of the group will be “Navigation”.

We have learned about using an element to provide an accessible name to another element in [the accessible name concatenation chapter.](https://practical-accessibility.today/chapters/accName-concatenation/)

### Managing keyboard focus inside the navigation drawer when it is shown

When the navigation is shown and focus is moved to the `Close` button, the user can navigate their way through focusable items inside the navigation using the `tab` key.

When they arrive at the last focusable element and then press the `tab` key, and since the rest of the page’s content is inert, their focus is going to move outside the page, to the browser. That’s not what they would expect or want to happen at that point.

There are two different things you may do to prevent this from happening.

#### Trap focus inside the navigation drawer until it is closed

Modal dialogs are typically expected to create a “focus trap” when they are open. This means that, using javaScript, keyboard focus is “trapped” inside the modal so that it does not move to any focusable elements outside of it. When the user tabs through focusable elements and reaches the last focusable element, pressing the tab key would move their focus back to the first focusable element.

For the navigation drawer, you may or may not trap focus inside of it. As with other usability decisions, your choice of focus management inside the navigation should be based on user testing.

If user testing shows that users expect focus to be trapped inside the navigation drawer when it is shown, then you will need to convey the appropriate semantics to the user so that they know what they are interacting with and what to expect. More on this shortly.

To trap keyboard focus inside the navigation, using JavaScript, you’re going to:

1. Get a list of all focusable elements within the navigation.
2. Get the first and last focusable elements (and save them in two variables).
3. Listen for when the tab key is pressed, then:
4. If focus is on the last focusable element, prevent default behavior and move it to the first focusable element.
5. If focus is on the first focusable element and the user presses the shift (i.e. they’re tabbing backwards), prevent default and move focus to the last focusable element.

Hidde De Vries has written [an article about trapping focus within elements](https://hidde.blog/using-javascript-to-trap-focus-in-an-element/) that goes through these steps and provides a snippet of code that you can use as a starting point for your own scripts. I recommend checking his article out for more details.

```javascript
/* Code snippet borrowed from Hidde's article */

function trapFocus(element) {
  // get all focusable elements
  var focusableEls = element.querySelectorAll(
    'a[href]:not([disabled]), button:not([disabled]), textarea:not([disabled]), input[type="text"]:not([disabled]), input[type="radio"]:not([disabled]), input[type="checkbox"]:not([disabled]), select:not([disabled])'
  );
  // Save first and last focusable elements
  var firstFocusableEl = focusableEls[0];
  var lastFocusableEl =
    focusableEls[focusableEls.length - 1];
  var KEYCODE_TAB = 9;

  // listen for a key press
  element.addEventListener(
    "keydown",
    function (e) {
      var isTabPressed =
        e.key === "Tab" ||
        e.keyCode === KEYCODE_TAB;

      // if the key pressed is not TAB, stop function execution
      if (!isTabPressed) {
        return;
      }

      // if shift + tab
      if (e.shiftKey) {
        if (
          document.activeElement ===
          firstFocusableEl
        ) {
          lastFocusableEl.focus();
          e.preventDefault();
        }
      }
      // else if tab
      else {
        if (
          document.activeElement ===
          lastFocusableEl
        ) {
          firstFocusableEl.focus();
          e.preventDefault();
        }
      }
    }
  );
}
```

#### Communicate that the navigation is modal to screen readers using ARIA

If you trap focus inside the navigation, you must communicate to screen reader users that the navigation is modal so that they understand _why_ their focus is being trapped in it.

You can expose the navigation content container as a dialog using [the dialog ARIA role.](https://w3c.github.io/aria/#dialog)

```html
<nav aria-label="Site">
  <button
    aria-expanded="false"
    class="nav-toggle">
    Navigation
  </button>

  <div
    class="nav-content"
    aria-labelledby="nav-toggle"
    role="dialog">
    <button class="nav__closeBtn">Close</button>

    <ul role="list">
      <!-- navigation items -->
    </ul>
  </div>
</nav>
```

#### Close the navigation drawer when focus moves outside of it

If user testing shows that trapping focus inside the navigation confuses users, or if you simply don’t want to trap it, you can alternatively close the drawer when focus moves outside of it.

Technically, this means that when focus is on the last focusable element and the tab key is pressed, you prevent the default behavior and close the navigation instead.

As we mentioned earlier, when the navigation is hidden, the page’s content should become active again, and keyboard focus should move back to the navigation button.

Since focus is not trapped inside the navigation, you don’t want to expose the navigation content container as a dialog anymore. As we mentioned earlier, modal dialogs are expected to trap focus inside of them. Since you’re not trapping it, you want to use another role that still provides a meaningful context for the Close button. The group role is an appropriate role in this case.

Now when the navigation is open and focus moves to the Close button, a screen reader will announce something along the lines of “Close, Navigation, Group.” And when you tab through the navigation elements and reach the last element in the list, tabbing one more time dismisses the navigation, and your keyboard focus moves back to the page’s content.

## Outro

You see, when it comes to hiding content from the user, there’s much more to consider than choosing a hiding technique.

Always be mindful of which elements you hide, and how hiding them affects the overall structure and usability of the page.

And always perform your own (manual) tests using assistive technologies to ensure the components you create, as well as the entire page, works as expected.
