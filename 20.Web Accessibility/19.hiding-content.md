# Hiding content using HTML, CSS, and ARIA — which one should you use when?

There are various ways you can hide an element using HTML, CSS, and using ARIA. As a developer, you should be knowledgeable of the various methods that can be used to hide elements, and you should be aware of how **each method affects the discoverability and accessibility of those elements.**

The technique that you use to hide an element will determine _who_, if anyone, will have access to that element. _Why_ you are hiding an element will determine which technique is more appropriate for the purpose. And the _type_ of the element you’re hiding also determines which techniques are suitable for hiding it, and which aren’t.

We learned about the accessibility tree in [a previous chapter](https://practical-accessibility.today/chapters/the-accessibility-tree/). And we learned that the markup and styles that we write will determine whether or not an element is exposed to screen readers via the accessibility tree. In this chapter, we will cover the different ways you can hide content on a page, and how each of them impacts the accessibility of that content.

## Hiding content with CSS

There are more than a handful of ways you can hide an element using CSS. The _type of invisibility_ of that element will be determined by the technique that you use to hide it. And the technique you use to hide an element will determine how accessible it will be.

### Make an element transparent with the `opacity` property & `opacity()` filter function

You can make an element fully transparent by setting its opacity to 0:

```css
.element {
  // make the element transparent
  opacity: 0;
}
```

Similarly, you can make an element transparent by using the opacity() filter function and setting its value to 0:

```css
.element {
  // make the element transparent
  filter: opacity(0);
}
```

Making an element transparent will visually hide the element, but **the element will still take up the space it would normally take in the page layout.** I like to think of using opacity as applying sort of a camouflage to an element.

The semantics and accessibility information of the element with transparency are not affected. **The element (and any of its children) can still be exposed in the accessibility tree. And it will remain screen reader, as well as keyboard, accessible.**

### Clip an element out of view with the `clip-path` property

You can also visually hide an element using the `clip-path` property.

Setting the value of the `clip-path` property to `inset(100%)` creates a rectangular clipping region _inside_ the element, equal to the entire element’s area. Effectively, this will create a zero-width and zero-height clipping region, which means that no part of the element will be shown.

```css
.element {
  // clip the element out of view
  clip-path: inset(100%);
}
```

Clipping is, in some way, kind of like placing an object in front of an element — it affects how much of that element is visible, but it doesn’t remove the element from its position in the page. Just like a transparent element, **a clipped element will still take up its normal space in the page layout.**

Clipping an element has no effect on the element’s semantics or accessibility information. This means that **it will remain screen reader, as well as keyboard, accessible.**

## Move an element off-screen with the `position` property

Using the `position` property, you can move and position an element anywhere on a page.

With `absolute` positioning, and combined with offset properties (`top`, `bottom`, `left`, `right`), you can hide an element from view by moving it out of the viewport (or “off canvas”). As you can imagine, moving an element somewhere else means that **it will no longer take up any space in the normal page flow.**

```css
#skip-link {
  // remove from page flow
  position: absolute;
  // position outside the viewport
  top: -200vh;
}
```

Positioning an element out of view does not remove the element from the DOM or accessibility trees. This means that **it will remain keyboard as well as screen reader accessible, even if it is moved out of sight.**

This, in turn, means that a screen reader will announce the presence of this element. And if the element is interactive, the user’s keyboard focus can move to the element even if it is positioned somewhere it cannot be seen. This is not only confusing to the user (because they are interacting with an element they can’t see), but it is also a WCAG violation.

Users must be able to see what they are interacting with. If an element is not visually accessible, it should also not be focusable, **unless you un-hide it when it receives focus.** When an element receives keyboard focus, it should clearly visible to the user so that they can see exactly what they are focusing on, and where they are on the page.

### Make an element invisible with the `visibility` property

You can also hide an element using the `visibility` property. The `visibility` property is used to determine the visibility of an element.

You make an element invisible by setting its `visibility` to `hidden`.

```css
ul {
  // make the list invisible
  visibility: hidden;
}
```

An invisible element **will be hidden from view as well as removed from the accessibility tree**, making it completely **inaccessible to _all_ users..** But the element **will still take up its normal space in the page layout.**

Using the `visibility` property is sort of like using an invisibility cloak — the element is still _there_, but it’s invisible to everyone.

While the `visibility` property determines the visibility of an element on the page, the `display` property can be used to completely remove any trace of the element from the page.

### Turn an element’s display off with the display property

When you set the `display` property of an element to none, you “turn off” the display of the element.

```css
button {
  // turn the element’s display off
  display: none;
}
```

When an element’s display is turned off, the result is like the element doesn’t exist at all — **it is removed from the page and from the accessibility tree, making it completely inaccessible to all users.**

### Other CSS properties may also affect accessibility

The purpose of the `display` property is to control the type of boxes an element will generate.

When the value of the property is none, you’re telling the browser to **generate no boxes for the element and any of its descendants.** In other words, the element and all of its descendants are not “generated” and will, therefore, be excluded from the accessibility tree.

The display property has not long ago gotten a new value: contents. The contents value is similar to none, with two major differences:

1. `contents` will determine whether **the element itself** generates any boxes, but **it has no effect on the element’s children** — the children will still generate boxes and will not be affected by the `display` set on their parent.
2. `contents` does not affect the semantics or accessibility of the element. It does not remove the element or any of its descendants from the accessibility tree.

When `display: contents` was implemented by browsers, they didn’t implement the behavior that was [defined in the specification](https://www.w3.org/TR/css-display-3/#box-generation). Browsers that implemented `display: contents` removed the element from the accessibility tree, making it inaccessible.

At the time of writing, most browsers have fixed this behavior, but not all of them have. So `display: contents` should be used with caution. Until you can guarantee that it works as expected in all browsers, you probably should limit its usage to elements that don’t have any meaningful semantics that need to be preserved (e.g. `div`s).

Other new CSS properties _could_ potentially, depending on browser implementations, also affect the accessibility of content. Properties that are used to change how or when an element is rendered on the page _may_ impact how and whether that element is exposed at all.

Before the implementation was fixed in browsers, there was an accessibility issue with another CSS property called [content-visibility](https://developer.mozilla.org/en-US/docs/Web/CSS/content-visibility).

`content-visibility` is a property aimed at improving page performance by controlling whether or not an element renders its contents before it is needed. It enables the browser to skip an element’s rendering work (including layout and painting) until it is needed — which makes the initial page load much faster.

Prior to `Chromium 90`, semantic elements like headers and landmark roles contained within an element using `content-visibility: auto` were not exposed to accessibility APIs. As of `Chromium 90`, this issue has been fixed, and content was exposed again in the browser’s accessability tree.

However, there is one caveat to keep in mind. When an element’s rendering is postponed, the styles used on the content inside of it are not applied. If you have content inside the element that is hidden from screen readers using `display: none` or `visibility: hidden`, that content will be discoverable by screen reader users even if you didn’t intend for it to be. So if you have any elements that you want to be hidden from screen readers, you will need to hide them using HTML or ARIA attributes instead of CSS.

So, if the browsers have already fixed the behavior of these properties, why am I mentioning all of this? The reason I am mentioning this is because I want you to keep in mind that just because something is designed to work a certain way, does not mean it _will_ work according to the specification. Any new CSS property may have gaps in implementation or may be implemented by browsers in a way that affects the accessibility of the content that it is applied to.

So you should **always, always test the behavior of new features across browsers and screen readers** to ensure that they work as expected, and that they do not create new barriers to access. You can also do a quick check of the accessibility tree created by the browser to get insights into the information that would be exposed to screen readers.

## Hiding content using HTML

There are two main HTML attributes that can be used to hide content on a page; and two attributes that don’t exactly _hide_ an element, but that have an impact the element’s _reachability_ with a keyboard.

### Turn an element’s display off with the `hidden` attribute

The `hidden` attribute is **the HTML equivalent of CSS’s `display: none`.** When used on an element — regardless of what value you give it, it turns off the element’s display so that it is no longer rendered on the page. **It will also remove the element from the accessibility tree,** making it **completely inaccessible** to _all_ users.

```html
<h2 hidden>
  This text is completely hidden from all users.
</h2>

<p hidden>I am hidden.</p>

<p hidden="invalid value">
  Yep, I'm hidden, too. An invalid value will
  default to a hidden state.
</p>

<p hidden="false">
  This text is also hidden, even if the attribute
  value is false, because false is not a valid
  value for hidden, and an invalid value will
  default to a hidden state.
</p>
```

### Disable interactive controls with the disabled attribute

The `disabled` attribute can be used to disable an interactive element — typically a form control such as a `<button>`, `<input>`, or `<select>`.

```html
<button type="submit" disabled="yep">
  Send message
</button>
```

`disabled` is a boolean attribute that indicates that the user cannot interact with the control or its descendant controls. When it is set on an element — regardless of what value you give it! — the element is disabled.

```html
<!-- the fieldset and all of its descendants are disabled -->
<fieldset disabled="yep!">
  <legend>Disabled fieldset</legend>
  ..
</fieldset>
```

When a control is disabled, it does not receive keyboard focus or mouse events anymore. **The element will no longer be reachable via the `tab` key.**

A disabled control is, however, **included in the accessibility tree and exposed to screen readers,** but the screen readers will announce the disabled state of the control, indicating that the user cannot activate or interact with it.

`Using the disabled attribute may also make a control visually inaccessible to users with low vision. When a control is disabled, the browser will often use a low-contrast grey color on the control, which makes it difficult to discern for some users. You should be mindful when disabling controls, and conduct usability tests to make sure that the disabled controls do not negatively impact the usability of your content. If you do disable a control, make sure you style it in a way that does not compromise its visual accessibility.`

### Make regions inert with the `inert` attribute

The `inert` attribute allows you to mark elements or regions of a page as inert.

When an element is `inert`, the element and all of its children are visually rendered on the page, but they are:

- not exposed to accessibility APIs (so they are no longer screen reader-accessible),
- completely non-interactive (so they are not keyboard accessible)
- not targeted for any user interaction events (including mouse or touch events).

This all means that the element and all of its children will only be visible to someone who can see the screen, but they will be completely inaccessible otherwise.

For example, setting the `inert` attribute on a region (such as a `<fieldset>` within a form) that contains links and input fields will make the region and all of its interactive descendants completely inaccessible to all users (screen reader, keyboard, mouse, touch, etc.):

```html
<!-- the fieldset and all of its descendants are inert -->
<fieldset inert>..</fieldset>
```

Making content inert is kind of like replacing the content with a static, non-interactive picture of the content, only that picture has no alternative text that describes it to AT users.

When content is inert, blind screen reader users are completely barred from accessing that content. Partially-sighted users or users with low vision who use screen readers may notice the rendered content, but they can’t access it. While inert content is expected to behave this way, you should make it clear that this content is not meant to be accessed. A good practice is to dim or obscure the content that is inert to provide a visual cue that the content is not presently accessible to anyone.

For example, an appropriate use case for `inert` is overlay patterns like modal dialogs that cover the entire page when they are open. A [good modal dialog](http://scottaohara.github.io/accessible_modal_window/) experience will “trap” the focus of the user inside the dialog when it is open. This ensures that no interactions happen with the parts of the page that are hidden by the “backdrop”, behind the dialog.

Since the content outside of the modal dialog shouldn’t be interacted with, it should be inert. And the inert content should also be visually dimmed and obscured by the dialog, making it visibly clear that it is not meant to be interactive.

If you are creating a custom dialog widget (instead of using the native `<dialog>` element), you can use the `inert` attribute to make the content outside the dialog inert. Without the inert attribute, you would have to traverse the DOM and prevent every focusable element from being focused, and hide the content from screen readers, which is not only a lot more work, but may also be difficult if you’re not comfortable writing JavaScript. (If you use the `<dialog>` element, the browser will provide this functionality for you.)

There’s often a little bit of confusion between the `inert` attribute’s behavior and the `hidden` and `disabled` attributes behavior.

#### The difference between `inert` and `hidden`

Unlike the hidden attribute, inert does not turn an element’s display off.

If you were to set the hidden attribute on a region, that region will disappear from sight. An inert element will still be visible, but it can’t be directly interacted with by any user anymore.

#### The difference between `inert` and `disabled`

Similar to the `disabled` attribute, the `inert` attribute will prevent a control from being reachable via the keyboard `tab` key.

The difference between `inert` and `disabled` is that an `inert` element will be hidden from screen readers; it will not be exposed at all, so they won’t know it exists. Whereas a `disabled` element will be exposed as normal. It will be included in the accessibility tree, and its disabled state will also be exposed, indicating that the user cannot activate or interact with it.

### Remove an element from keyboard tabbing order with the tabindex attribute

The `tabindex` attribute can be used to remove an element from the tabbing order.

When you set the `tabindex` to a -1 (or any other negative integer value) on an interactive element (such as a link or a button), **the element is removed from the tabbing order of the page.** A user tabbing their way through the page will no longer be able to move their focus to the element to operate it.

```html
<!-- this link is no longer reachable with the tab key -->
<a href="#" tabindex="-1"
  >Learn more about our company</a
>
```

tabindex does not affect the semantics or other accessibility information of an element. This means that **the element will remain screen reader as well as visually-accessible,** and can be operated just fine using mouse.

The `tabindex` attribute cannot be used to make an element non-focusable. The only way you can do that is by disabling the element (with the disabled attribute), or by making it inert.

The `tabindex` attribute can do much more than remove an element from the tabbing order. We will learn all about how it can be used to manage keyboard focus in custom UI components later in the course.

## Hiding content using ARIA attributes

The primary way to hide content using ARIA is using the `aria-hidden` attribute.

### Hide content from screen readers using the `aria-hidden` attribute

The `aria-hidden` attribute determines whether or not an element should be included in the accessibility tree.

When `aria-hidden` is set to `true` on a static element, it hides the presence of that element from assistive technologies:

```html
<!-- This paragraph will not be included in the browser’s accessibility tree, and will not be perceived by screen readers. -->
<p aria-hidden="true">
  This text is not screen reader-accessible.
</p>
```

Using `aria-hidden="true"` on focusable elements will only partially/inconsistently “hide” these elements from assistive technologies, even if they’ve been removed from the tabbing order using `tabindex="-1"`.

```html
<!-- this interactive link may not be consistently hidden from screen readers -->

<a href="#" tabindex="-1" aria-hidden="true"
  >..</a
>
```

You should **avoid hiding interactive/focusable elements using `aria-hidden`.** If a screen reader user tabs through the page using a keyboard, their focus will land on an element that may not be announced. This means that they will not know what they are interacting with.

Moreover, modern browsers (like Chrome) will expose a focusable element to assistive technologies even if you explicitly hide it using `aria-hidden="true"` and remove it from the tabbing order with `tabindex="-1"`, so it is best to avoid using `aria-hidden` on anything that can receive focus, including programmatic focus.

You should always aim to ensure parity between keyboard and screen reader experiences. **If an element is keyboard-accessible, it should be screen reader-accessible.**

Unlike the `hidden` attribute, setting `aria-hidden` on an element without giving it a value is equivalent to not setting `aria-hidden` on that element at all. When `aria-hidden` has no value, the browser will ignore the attribute and determine the visibility of the element based on other factors (such as other attributes or CSS styles).

```html
<!-- hidden can be set without a value -->
<p hidden>I am hidden.</p>

<!-- The aria-hidden is ignored because it has no value -->
<p aria-hidden>
  I am accessible to screen readers.
</p>
```

Setting `aria-hidden` to `false` should expose the element to the accessibility APIs, but, [as currently mentioned in the ARIA specification](https://www.w3.org/TR/wai-aria-1.1/#aria-hidden), `aria-hidden="false"` currently does not work consistently across browsers. So if you want to expose an element to the accessibility API, it’s better to remove the `aria-hidden` attribute altogether when the element is no longer hidden.

```html
<!-- this SHOULD expose the element to AAPIs, but is inconsistent across browsers -->
<p aria-hidden="false">
  I should be exposed to screen readers but may
  not be.
</p>

<!-- to expose an element to AAPIs, remove the aria-hidden attr altogether -->
<p>
  I am consistently exposed to screen readers.
</p>
```

Unlike the hidden attribute which hides an element from all users, `aria-hidden` _only_ removes the element from the accessibility tree. That is all it does. It has no other effect on the visual rendering or keyboard accessibility of the element. When an element is hidden with `aria-hidden`, **it will remain visible to sighted users, and keyboard users can still interact with it.**

You may use `aria-hidden` to hide visible content from screen reader users but only if hiding that content improves their experience by removing extraneous or redundant content. For example, you may hide an icon within a label when the label text provides an equivalent meaning to the icon.

For example, a navigation toggle button that has a visible text label:

```html
<button>
  <svg
    viewBox="0 0 24 24"
    height="24"
    width="24"
    aria-hidden="true">
    ..
  </svg>

  Menu
</button>
```

![menu with icon](./markdown-assets/19.1.MenuImage.png)

Since the label text is the equivalent of the icon, announcing both the icon _and_ the text label would be unnecessary. Hiding the icon so that only the text label is announced improves the user experience for screen reader users, and does not compromise the accessibility of the button.

`aria-hidden` is the primary way to hide content from accessibility API’s using ARIA attributes.

The `role` attribute can also be used to hide an element from AAPI’s — though, it does not work the same way `aria-hidden` works.

### Suppress an element’s semantics with the `role` attribute: `presentation` and `none`

`role: presentation` and `role: none` can be used to **suppress the implicit semantics of an element**. This means that the element will no longer map to any role, unless:

- The element is focusable (e.g. it is natively focusable like an HTML link or input, or it has a `tabindex` attribute); this means that interactive elements will be exposed even if they have role presentation or none set, and
- the element has one of the [global ARIA states and properties](https://www.w3.org/TR/wai-aria-1.1/#global_states) (e.g. `aria-label`)
  For example, if you set `role: none` on a heading, the heading will not be exposed as a heading in the accessibility tree anymore. It will just be reported in the accessibility tree as a text string with no semantic meaning.

```html
<h1 role="none">I’m a heading with no role</h1>
<h2>I have heading semantics</h2>
```

![none role usage on a heading](/markdown-assets/19.2.none-role-usage.webp)

Setting `role:none` on an element is similar to removing the opening and closing tags of that element in your markup. You can also think of it as _kind of_ like replacing the element with a `<div>`.

Setting `role: none` on an element does not hide the element’s contents. The heading text will still be exposed as static text and can be read out by screen readers.

For elements with no required children, any elements nested inside the element with `role=presentation/none` preserve their semantics.

In other words, `role: none` suppresses an element’s semantics, but it will not affect the semantics of the element’s children. The exception to this rule is when:

- the children are required (such as the children of a `<table>`: `<td>`, `<tr>`, etc.), or
- the children are “semantically tied” to the element. For example, `listitems` aren’t required children of a `list`, but a `listitem` is required to have a `list` parent. This strict relationship means that the semantics of the list items are tied to the semantics of their parent; because of that, the list item semantics will also be suppressed if `role: none` is applied to their parent list.

If a child element is not semantically tied or required by the element with role: none, its semantics will be preserved and exposed in the accessibility tree.

```html
<h3 role="none">
  <!-- the link semantics are preserved and exposed as normal because it is not a required child of the heading, nor is there a semantic relationship between them -->
  <a href="..">I'm a link</a>
</h3>
```

`presentation` and `none` are synonymous — they literally do the same thing. [From the ARIA specification](https://www.w3.org/TR/wai-aria-1.1/#role-none-note-none):

**In ARIA 1.1, the working group introduced none as a synonym to the presentation role, due to author confusion surrounding the intended meaning of the word “presentation” or “presentational.” Many individuals erroneously consider role="presentation" to be synonymous with aria-hidden="true", and we believe role="none" conveys the actual meaning more unambiguously.**

So it is currently recommended that you use `role: none` when you need to suppress an element’s semantics, instead of `role: presentation`.

```html
<!-- prefer this -->
<li role="none"></li>

<!-- over this -->
<li role="presentation"></li>
```

#### Useful applications for `role="none"`

There are very few instances where suppressing an element’s semantics is helpful. So you’ll want to avoid using this attribute unless you’re using it to improve the accessibility of a component. And you’ll also want to remember that, similar to the `aria-hidden` attribute, `role: none`’s ability to suppress an element’s semantics may be negated by other attributes of or on the element.

A useful application for `role: none` is removing table semantics from old code bases where tables are used as a layout method. Since the tables are strictly used for “presentation” purposes, you can safely suppress their semantics, which improves the navigation experience for screen reader users.

```html
<!-- this table is used for layout purposes only -->
<table role="none">
  <!-- suppressing the table's semantics will also suppress the semantics of all of its rows and cells (because they are required children) -->
</table>
```

`role: none` can also be used for hiding decorative images. When `role: none` is applied to an `<img>`, the image is completely hidden. In this case, `role: none` has the same effect as using `aria-hidden="true"` on the image. This is also equivalent to giving the image an empty `alt` text.

```html
<!-- these two are equivalent and will hide the img from screen readers -->
<img src=".." alt=".." role="none" />
<img src=".." alt=".." aria-hidden="true" />
<img src=".." alt="" />
```

### The difference between role="none" and aria-hidden

The difference between `role:none` and `aria-hidden` is that the latter will remove the element and all of its children from the accessibility tree, whereas `role: none` will not.

### Providing screen reader-only accessible text

Using HTML and CSS you can hide content from all users, from keyboard users only, or from screen reader users only.

But there are instances where it will be beneficial — and sometimes necessary — to provide supplementary information to screen reader users only. A sighted user can perceive and understand information using visual cues, but someone with low or no vision might miss that information because they lack the same affordances. For example, pricing discounts are usually visually styled by displaying a strike through the old price of a product:

![using cues for screen reader users like visual cues](/markdown-assets/19.3.usage-of-sr-only.webp)

A sighted user can perceive the meaning of these prices just by looking at them, but someone with a vision disability likely won’t perceive them the same way. In instances like these, you may supplement the accessibility information by spelling out the meaning of these prices in the markup:

```html
<span>New price: </span> <span>$350</span>
<span>Old price:</span> <span>$450</span>
```

Screen reader users benefit from this approach to understand the content, but since you don’t want the text to be visible, you can **visually-hide it while also keeping it accessible to screen reader users.**

There is currently no native way to visually-hide content while keeping it screen-reader accessible, so we need to use **a combination of CSS properties** to do so.

### Using visually-hidden text

Using a combination of CSS properties, you can create a utility class that, when applied to an element, will hide the element visually while keeping it accessible to screen reader users.

The utility class is commonly named either `sr-only` (which is short for “screen reader-only”) or `visually-hidden`. Since the `visually-hidden` text will be exposed by accessibility APIs to more than just screen readers, `visually-hidden` is a more appropriate name.

The code for the utility class looks like this:

```css
/* Visually hide text while keeping it accessible */
/* Source: https://www.scottohara.me/blog/2017/04/14/inclusively-hidden.html */

.visually-hidden:not(:focus):not(:active) {
  /* shrink to a 1px square */
  width: 1px;
  height: 1px;

  /* hide any resulting overflow */
  overflow: hidden;

  /* clip the element to remove any visual trace */
  clip: rect(0 0 0 0); /* for IE only */
  clip-path: inset(50%);

  /* remove from page flow so it doesn’t affect surrounding layout */
  position: absolute;

  /* ensure proper text announcement by screen readers */
  white-space: nowrap;
}
```

What the above class does is it:

1. shrinks the element to a 1px-square;
2. hides any resulting overflow;
3. clips it to remove any visual trace (such as any background colors);
4. removes it from the page flow (so it doesn’t affect the layout flow of surrounding elements);
5. and prevents text wrapping to ensure the text is properly announced by screen readers.

The result is that the element will be only be perceivable by assistive technology users.

If you want to dig deeper into each of the properties used and why they are important, I highly recommend [this article](https://www.tpgi.com/the-anatomy-of-visually-hidden/) on The Paciello Group blog.

The `:not(:focus):not(:active)` part of the selector indicates that the element is visually hidden only when it is not focused or activated. It ensures that, **if this utility class is used on an interactive element, the element becomes visible when it receives keyboard focus,** because interactive elements should always be visible when the user interacts with them.

My recommendation is to only use this utility class to hide textual content. Sometimes hiding links may be beneficial, but in very specific cases. In the [chapter in which we discuss skip links](https://practical-accessibility.today/chapters/skip-links/), we will see how this utility class is useful for hiding in-page, section-level skip links that improve navigation for keyboard users.

There are many instances where providing text for screen reader users is beneficial, especially if the content is otherwise not understandable enough without it. You may provide screen reader-only text to improve navigation, provide hints, or provide an accessible name for elements that don’t visually have one.

The `visually-hidden` utility class is a very useful and commonly used way to hide text while making sure it remains accessible for screen reader users who benefit from it. We’ll see quite a few examples of using it throughout the course.

### Exposing hidden text to screen reader users only using ARIA attributes

There’s another way to expose a piece of content to screen readers without displaying it visually.

When an element is hidden using the hidden attribute, it can be exposed in the accessibility tree **if it is referenced by another element on the page.** A practical example of that is a hidden piece of text that is used to provide an accessible name to another element on the page.

**By default, assistive technologies do not relay hidden information, but an author can explicitly override that and include hidden text as part of the accessible name or accessible description by using aria-labelledby or aria-describedby.**

**— [The Accessible Name and Description Computation Spec](https://www.w3.org/TR/accname-1.1/#mapping_additional_nd_te)**

In other words, you may use hidden to **declare a piece of content** (typically text) in your markup for the purpose of providing an accessible name for elements that otherwise don’t visually have one.

```html
<span hidden
  >[ accessible name for another element]</span
>
```

You may use this technique to provide an accessible name to an icon button, for example.

An icon button is a button that contains an icon and no (visible) accompanying text. It only has an icon as a label. Screen reader users will require a text alternative to identify this button. One way you could provide one is by using a hidden piece of text inside the button, and referencing that text inside `aria-labelledby` on the button:

```html
<button aria-labelledby="button-accName">
  <span id="button-accName" hidden>Menu</span>

  <!-- an svg icon, or an img may go here -->
</button>
```

By doing so, you are telling the browser to use the `hidden` span as an accessible name for the button.

If you inspect the accessibility information of the button in the accessibility tree using Edge or Chrome DevTools, you can see the hidden text exposed as an accessible name for the button.

[The accessibility panel in Chrome DevTools indicating that the accessible name of the button is derived from a span element with an ID referenced in the aria-labelledby attribute on the button.](/markdown-assets/19.4.aaccessibility-panel-using-aria-label.webp)

We will see more examples of providing accessible names and descriptions using the `hidden` attribute throughout the course.

## Recap

To make scanning and comparing the different hiding techniniques easier, I created [a comparison table](https://practical-accessibility.today/code/hiding-techniques/) that lists the various techniques and how they affect different types of accessibility.

When you’re developing for accessibility, you may sometimes need to combine more than one hiding technique to achieve the desired result without breaking the accessibility of your content.

You also want to keep in mind that there are exceptions to how these techniques work. For example, `aria-hidden` may not work on all types of content. The effect of the hidden attribute may be overridden in CSS. `role: none`’s effect may be negated by the use of other attributes on the element. And so on and so forth.

Remember: **The accessibility tree is a great way to get insights into how and whether your content is exposed to screen readers.**

Make sure that you **always, always test how your content is exposed to screen readers using a screen reader.** Different browser and AAPI combinations may result in different announcements and, as we mentioned earlier, some browsers and ATs try to correct the misuse of certain attributes by exposing content that “should” otherwise be hidden.

Testing across browsers and screen readers ensures that your content is exposed (or hidden!) the way it is meant to be. Furthermore, testing will help you find out if the techniques you are using are improving or worsening the usability of your content.

### How do you choose a hiding technique?

When you want to hide content, ask yourself: why are you hiding it? is it for the user’s benefit, or for purely aesthetic reasons? does it improve the user experience, or does it make it more confusing? Is there something else you can do to `avoid` hiding content? how does hiding the content affect users of various assistive technologies?

If you do need to hide an element, consider things like:

- Who are you hiding the element from?
- Who do you want to expose the element to?
- Who can benefit from the hidden element?
- What type of element are you hiding? is it interactive or focusable? or is it static text?

The answers to these questions will help you decide which hiding technique to choose.

## Outro

Being aware of the accessibility implications of hiding content is important. Knowing how browsers may exceptionally un-hide content is also important. But there is usually more to consider when hiding content than just the HTML or CSS properties you should use to hide it.

In the next two chapters, we’re going to discuss two different design patterns, and the accessibility as well as usability considerations that will guide our choice of hiding techniques for each of them.
