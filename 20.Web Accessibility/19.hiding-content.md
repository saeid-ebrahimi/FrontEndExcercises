# Hiding content using HTML, CSS, and ARIA — which one should you use when?

There are various ways you can hide an element using HTML, CSS, and using ARIA. As a developer, you should be knowledgeable of the various methods that can be used to hide elements, and you should be aware of how **each method affects the discoverability and accessibility of those elements.**

The technique that you use to hide an element will determine _who_, if anyone, will have access to that element. _Why_ you are hiding an element will determine which technique is more appropriate for the purpose. And the _type_ of the element you’re hiding also determines which techniques are suitable for hiding it, and which aren’t.

We learned about the accessibility tree in [a previous chapter](https://practical-accessibility.today/chapters/the-accessibility-tree/). And we learned that the markup and styles that we write will determine whether or not an element is exposed to screen readers via the accessibility tree. In this chapter, we will cover the different ways you can hide content on a page, and how each of them impacts the accessibility of that content.

## Hiding content with CSS

There are more than a handful of ways you can hide an element using CSS. The _type of invisibility_ of that element will be determined by the technique that you use to hide it. And the technique you use to hide an element will determine how accessible it will be.

### Make an element transparent with the `opacity` property & `opacity()` filter function

You can make an element fully transparent by setting its opacity to 0:

```css
.element {
  // make the element transparent
  opacity: 0;
}
```

Similarly, you can make an element transparent by using the opacity() filter function and setting its value to 0:

```css
.element {
  // make the element transparent
  filter: opacity(0);
}
```

Making an element transparent will visually hide the element, but **the element will still take up the space it would normally take in the page layout.** I like to think of using opacity as applying sort of a camouflage to an element.

The semantics and accessibility information of the element with transparency are not affected. **The element (and any of its children) can still be exposed in the accessibility tree. And it will remain screen reader, as well as keyboard, accessible.**

### Clip an element out of view with the `clip-path` property

You can also visually hide an element using the `clip-path` property.

Setting the value of the `clip-path` property to `inset(100%)` creates a rectangular clipping region _inside_ the element, equal to the entire element’s area. Effectively, this will create a zero-width and zero-height clipping region, which means that no part of the element will be shown.

```css
.element {
  // clip the element out of view
  clip-path: inset(100%);
}
```

Clipping is, in some way, kind of like placing an object in front of an element — it affects how much of that element is visible, but it doesn’t remove the element from its position in the page. Just like a transparent element, **a clipped element will still take up its normal space in the page layout.**

Clipping an element has no effect on the element’s semantics or accessibility information. This means that **it will remain screen reader, as well as keyboard, accessible.**

## Move an element off-screen with the `position` property

Using the `position` property, you can move and position an element anywhere on a page.

With `absolute` positioning, and combined with offset properties (`top`, `bottom`, `left`, `right`), you can hide an element from view by moving it out of the viewport (or “off canvas”). As you can imagine, moving an element somewhere else means that **it will no longer take up any space in the normal page flow.**

```css
#skip-link {
  // remove from page flow
  position: absolute;
  // position outside the viewport
  top: -200vh;
}
```

Positioning an element out of view does not remove the element from the DOM or accessibility trees. This means that **it will remain keyboard as well as screen reader accessible, even if it is moved out of sight.**

This, in turn, means that a screen reader will announce the presence of this element. And if the element is interactive, the user’s keyboard focus can move to the element even if it is positioned somewhere it cannot be seen. This is not only confusing to the user (because they are interacting with an element they can’t see), but it is also a WCAG violation.

Users must be able to see what they are interacting with. If an element is not visually accessible, it should also not be focusable, **unless you un-hide it when it receives focus.** When an element receives keyboard focus, it should clearly visible to the user so that they can see exactly what they are focusing on, and where they are on the page.

### Make an element invisible with the `visibility` property

You can also hide an element using the `visibility` property. The `visibility` property is used to determine the visibility of an element.

You make an element invisible by setting its `visibility` to `hidden`.

```css
ul {
  // make the list invisible
  visibility: hidden;
}
```

An invisible element **will be hidden from view as well as removed from the accessibility tree**, making it completely **inaccessible to _all_ users..** But the element **will still take up its normal space in the page layout.**

Using the `visibility` property is sort of like using an invisibility cloak — the element is still _there_, but it’s invisible to everyone.

While the `visibility` property determines the visibility of an element on the page, the `display` property can be used to completely remove any trace of the element from the page.

### Turn an element’s display off with the display property

When you set the `display` property of an element to none, you “turn off” the display of the element.

```css
button {
  // turn the element’s display off
  display: none;
}
```

When an element’s display is turned off, the result is like the element doesn’t exist at all — **it is removed from the page and from the accessibility tree, making it completely inaccessible to all users.**

### Other CSS properties may also affect accessibility

The purpose of the `display` property is to control the type of boxes an element will generate.

When the value of the property is none, you’re telling the browser to **generate no boxes for the element and any of its descendants.** In other words, the element and all of its descendants are not “generated” and will, therefore, be excluded from the accessibility tree.

The display property has not long ago gotten a new value: contents. The contents value is similar to none, with two major differences:

1. `contents` will determine whether **the element itself** generates any boxes, but **it has no effect on the element’s children** — the children will still generate boxes and will not be affected by the `display` set on their parent.
2. `contents` does not affect the semantics or accessibility of the element. It does not remove the element or any of its descendants from the accessibility tree.

When `display: contents` was implemented by browsers, they didn’t implement the behavior that was [defined in the specification](https://www.w3.org/TR/css-display-3/#box-generation). Browsers that implemented `display: contents` removed the element from the accessibility tree, making it inaccessible.

At the time of writing, most browsers have fixed this behavior, but not all of them have. So `display: contents` should be used with caution. Until you can guarantee that it works as expected in all browsers, you probably should limit its usage to elements that don’t have any meaningful semantics that need to be preserved (e.g. `div`s).

Other new CSS properties _could_ potentially, depending on browser implementations, also affect the accessibility of content. Properties that are used to change how or when an element is rendered on the page _may_ impact how and whether that element is exposed at all.

Before the implementation was fixed in browsers, there was an accessibility issue with another CSS property called [content-visibility](https://developer.mozilla.org/en-US/docs/Web/CSS/content-visibility).

`content-visibility` is a property aimed at improving page performance by controlling whether or not an element renders its contents before it is needed. It enables the browser to skip an element’s rendering work (including layout and painting) until it is needed — which makes the initial page load much faster.

Prior to `Chromium 90`, semantic elements like headers and landmark roles contained within an element using `content-visibility: auto` were not exposed to accessibility APIs. As of `Chromium 90`, this issue has been fixed, and content was exposed again in the browser’s accessability tree.

However, there is one caveat to keep in mind. When an element’s rendering is postponed, the styles used on the content inside of it are not applied. If you have content inside the element that is hidden from screen readers using `display: none` or `visibility: hidden`, that content will be discoverable by screen reader users even if you didn’t intend for it to be. So if you have any elements that you want to be hidden from screen readers, you will need to hide them using HTML or ARIA attributes instead of CSS.

So, if the browsers have already fixed the behavior of these properties, why am I mentioning all of this? The reason I am mentioning this is because I want you to keep in mind that just because something is designed to work a certain way, does not mean it _will_ work according to the specification. Any new CSS property may have gaps in implementation or may be implemented by browsers in a way that affects the accessibility of the content that it is applied to.

So you should **always, always test the behavior of new features across browsers and screen readers** to ensure that they work as expected, and that they do not create new barriers to access. You can also do a quick check of the accessibility tree created by the browser to get insights into the information that would be exposed to screen readers.
