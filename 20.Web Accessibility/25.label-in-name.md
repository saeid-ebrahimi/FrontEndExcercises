We took a deep dive into accessible names and descriptions in the previous chapters, and we’ve learned about the importance of accessible names to assistive technology users like screen reader users.

We’ve also talked about labels and how labels are not the same as accessible names. Though, **ideally, they should be identical.** In this chapter, we’re going to understand why.

And we’re going to learn why **missing** or **repeated text labels** can cause barriers to access to some assistive technology users.

More specifically, we’re going to learn about speech recognition software, how it works, how people use it to navigate and operate web content, and how the design decisions we make can improve or degrade their user experience, and what to do instead.

So, let’s dive right in.

## Consistent identification

The purpose of a name is to identify what an element does. As such, if there are two buttons on a page that perform **the exact same action,** then they should have the same accessible name. Similarly, if there are two links that go to the same place, they too would have the same accessible name.

WCAG [Success Criterion 3.2.4 Consistent Identification (Level AA)](https://www.w3.org/WAI/WCAG21/quickref/?showtechniques=136%2C244%2C324%2C131#consistent-identification) states that:

**Components that have the same functionality within a set of Web pages are identified consistently.**

One way to _fail_ this criterion is to create two (or more) buttons that have the exact same functionality but different accessible names.

If two buttons perform the exact same action, they should have the same accessible name.

## Unique accessible names

Conversely, if two buttons perform different actions, they should have unique, distinct names (that identify those actions).

And when two buttons don’t perform the exact same action, they should also, ideally, **not have the same label.**

Yet repeated labels are a common design pattern on many websites today. For example, “Add to Cart” buttons on e-commerce websites all share the same label (“Add to cart”), even though each button performs a unique action associated with the product it adds to the user’s cart. No two buttons add the same product to the user’s cart. And “Read more” links in card components also share the same label, even though each link takes the user to a different page.

`In this chapter, we're going to focus on the “Add to cart” buttons, but the concepts we'll discuss apply to the “Read More” links and other similar design patterns with repeated labels.`

Most sighted users can associate each “Add to cart” button with its product by means of visual cues such as layout, position, and proximity. So even if the buttons share the same label, their visual context helps identify their purpose.

But a blind screen reader user who can’t see what’s on screen does not have the same affordance.

When screen reader focus moves to each button, the screen reader will announce “Add to cart, button”. The accessible name of each of these buttons doesn’t identify _which product_ it is associated with.

Many screen reader users explore content on pages using screen reader shortcuts. A user may pull up a list of all buttons on the page to get an overview of what actions are available to them, and to quickly navigate to the button that they want.

For example, a VoiceOver user may pull up the Web Rotor to view the Buttons menu which lists all the buttons that are present on the page. In this list, the buttons are taken out of their context. Quickly scanning the buttons, you can tell that they provide very little value, as there is no way to tell which product each button corresponds to.

The accessible name of each button should identify the action it initiates. But when all the buttons have the same name, how does a user know which button they want to activate if they don’t know _which product_ it will add to their cart?

## Using visually-hidden text

To make the accessible names of the buttons unique, you may consider adding a visually-hidden piece of text inside each button that identifies the product that the button is associated with:

```html
<!-- Adding the product's name to the button that adds the product to cart would make the buttons' accessible names unique -->
<button>
  Add
  <span class="visually-hidden"
    >[ PRODUCT_NAME ]</span
  >
  to Cart
</button>
<!-- P.S. Don’t do this -->
```

So now if the user pulls up the list of buttons in their screen reader, each button will have a unique accessible name that clearly identifies its purpose.

But while providing visually-hidden text improves the experience of screen reader users, obscuring the full accessible name of the buttons degrades the usability of these buttons for other assistive technology users, especially speech recognition software users.

## What is speech recognition? Who uses it? And how?

Speech recognition software is a form of assistive technology that allows people to use **spoken commands to browse the Web and to interact with web content.**

Speech recognition software is used by people with **permanent, temporary, or situational disabilities;** for example, people with dexterity limitations, or cognition and learning disabilities; people with wrist injuries or who have Repetitive Strain Injury (RSI) or Carpal Tunnel from working on a computer for too long. It is also used by users who just happen to be in a situation that makes using their hands (or a mouse or a keyboard) difficult, such as someone driving a car or maybe even cooking in the kitchen.

Speech recognition software is used **as an alternative to using a keyboard or a mouse** when using a mouse or a keyboard is difficult or impossible. And its core navigation **verbally mirrors how you navigate with a keyboard.** For example, instead of pressing the tab key on your keyboard, you say “tab” to move focus to the next focusable item on the page; and “shift tab” to move focus to the previous focusable item. And to activate a link or button, you say “click” followed by the link or the button’s name, such as “Click Home”.

If you say “Click checkbox”, the software highlights all the checkboxes on the page and number them. You can then choose the number of the checkbox you want to click to activate it.

**Speech recognition software relies on the proper use of** [semantic HTML](https://practical-accessibility.today/chapters/html-semantics/). If you don’t use semantic HTML the way it is intended to be used, like we discussed in [the HTML semantics chapter,](https://practical-accessibility.today/chapters/html-semantics/) the software will not recognize these controls by their type or their name.

All popular platforms and devices come with Speech recognition software built into them. There is also third-party software that is typically more robust and is therefore preferred by many users.

One of the more popular Speech recognition software is [Dragon](https://www.nuance.com/dragon/business-solutions/dragon-professional.html), which offers long-form voice dictation and web browsing.

Here is an excerpt from [a video that Level Access created](https://www.youtube.com/watch?v=kJKQmTumFP0&ab_channel=LevelAccess) and that [demonstrates how Dragon is used to fill out form information on a page](https://www.youtube.com/watch?v=kJKQmTumFP0&ab_channel=LevelAccess). The video is 9 years old, but still very relevant today. And it is my favorite video demonstrating the use of Dragon to interact with content in a web page.

Here is another more recent demonstration of Dragon in this video by Tetralogical from their [Browsing with Speech Recognition](https://tetralogical.com/blog/2021/11/15/browsing-with-speech-recognition/) post, which is part of their “Browsing with Assistive Technology” series that we gave a shoutout to in [the “What is web accessibility?” chapter](https://practical-accessibility.today/chapters/web-accessibility/) earlier in the course.

Interacting with web pages using spoken commands requires vision. So voice control users are necessarily sighted. And they rely on visible text labels to activate controls on a page.

If text labels are hidden or obscured, the controls will be more difficult to interact with. The user will need to resort to using the **Mouse Grid** to focus the control they need to activate. And they may need to do this multiple times per session, which results in an exhausting and time-consuming experience.

This is one of many reasons why **visible text labels are important in user interfaces,** and why accessibility professionals always advocate for providing visible text labels for all controls on a page.

When the user says a control’s text label, **the Speech recognition software processes the voice input and searches for an accessible name that matches the name spoken by the user.**

If it finds an element with that name, it will execute the command said by the user (such as clicking the element). If there are multiple elements that have the same name, it will typically highlight and number all of them.

But when the accessible name of an element does not match the name said by the user, the Speech recognition software won’t be able to identify it.

Inserting visually-hidden text in the middle of a label will prevent Speech recognition software from matching the label to the accessible name.

This is why providing visually-hidden names is problematic. **Screen readers are not the only assistive technology that relies on accessible names.** And voice control users rely on both the label they can see and the programmatic name of an element to interact with it.

## Label in Name

[WCAG Success Criterion 2.5.3: Label in Name (Level A)](https://www.w3.org/WAI/WCAG21/quickref/#label-in-name) states that:

> **For user interface components with labels that include text or images of text, the name contains the text that is presented visually.**

From the success criterion’s [understanding page](https://www.w3.org/WAI/WCAG21/Understanding/label-in-name.html) (emphasis mine):

> **The intent of this Success Criterion is to ensure that the words which visually label a component are also the words associated with the component programmatically. This helps ensure that people with disabilities can rely on visible labels as a means to interact with the components.**
>
> **Most controls are accompanied by a visible text label. Those same controls have a programmatic name, also known as the Accessible Name. Users typically have a much better experience if the words and characters in the visible label of a control match or are contained within the accessible name. When these match, voice-input users (i.e., users of voice recognition applications) can navigate by speaking the visible text labels of components, such as menus, links, and buttons, that appear on the screen. Sighted users who use text-to-voice (e.g., screen readers) will also have a better experience if the text they hear matches the text they see on the screen.**

The Understanding page includes a note that says:

> **A best practice is to have the text of the label at the start of the name.**

The reason this is a best practice is that when the accessible name starts with the label, some Speech control software (currently Dragon, in particular) use heuristics to identify the element(s) that start with the term that the user speaks (the label), even if the element’s name doesn’t fully match the term.

So, whenever you need to add visually-hidden text to an element’s name, append it to the visible text label.

For the “Add to Cart” buttons, this means that the product name which uniquely identifies each button should be appended to the “Add to cart” text:

```html
<!-- Instead of this... -->
<button>
  Add
  <span class="visually-hidden"
    >[ PRODUCT_NAME ]</span
  >
  to Cart
</button>

<!-- ...do this. -->
<button>
  Add to Cart
  <span class="visually-hidden"
    >, [ PRODUCT_NAME ]</span
  >
</button>
```

Now when the user says “Click Add to Cart”, Dragon can find all the buttons whose name starts with “Add to cart”, and number them. And the user can then say “choose [number]” to activate the one that they want.

For the “Read More” links that we mentioned earlier in the chapter, the markup may look like this:

```html
<!-- Instead of this... -->
<a href="/path/to/article-title/">Read More</a>

<!-- ...do this. -->
<a href="/path/to/article-title/"
  >Read More
  <span class="visually-hidden"
    >about [ ARTICLE TITLE ]</span
  ></a
>
```

Instead of just “Read more”, the accessible name of each link would be “Read more about [whatever the article’s title is]”. And when the user says “Click Read More”, Dragon can also find all the links whose name starts with “Read More”, and number them. And the user can then say “choose [number]” to activate the one that they want.

This is great for Dragon users. But not all Speech recognition software use the same heuristics that Dragon uses. So, many users will still have to resort to using the more tedious methods to interact with elements on the page.

On some platforms, the user may be able to work around the presence of visually-hidden text by speaking specialized commands that enable them to display the full accessible names of elements so that they can choose the one that they want. But this requires a level of literacy with the software that not all users may have.

_"The larger question is why do we force people to do all this extra work?"_, says inclusive design advocate Eric Bailey in his article [“Voice Control Usability Considerations For Partially Visually Hidden Link Names”.](https://www.smashingmagazine.com/2022/06/voice-control-usability-considerations-partially-visually-hidden-link-names/) _"Partially visually hidden link text isn’t necessarily a hard WCAG failure, but it is also not a good user experience."_

Remember that WCAG conformance will help you improve the accessibility of your websites and applications, but, as we’ve mentioned several times throughout the course already, **you should always aim for usability beyond conformance.**

## Final Words

Accessible names are critical to assistive technology users like screen reader users, but keep in mind that screen readers are not the only assistive technology that relies on accessible names to identify interface elements.

Repeated or missing text labels can make content harder to interact with for many users.

When you’re designing user interface components:

1. Give each interactive element a unique accessible name that clearly identifies its purpose.
2. And show the full text of the name (i.e. match the element’s label to its name).

_"If you need to update your existing work to accommodate these kinds of real-world considerations, you’ll probably have to collaborate with content writers, developers, and project managers, says Eric. Design thrives in this kind of collaborative environment, where you can identify and work with the limits of the systems you work inside of. These efforts all speak to the value of a Shift Left methodology, where these kinds of considerations are named and dealt with early in the conception phase."_
