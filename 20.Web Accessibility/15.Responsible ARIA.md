# Responsible ARIA: The Rules of ARIA Use in

The [results of the 2022 WebAIM Million survey](https://webaim.org/projects/million/#aria) showed that home pages with ARIA present averaged 70% more detected errors than those without ARIA. This means that a user was likely to encounter an additional 23 potential barriers on home pages where ARIA was used.

When ARIA is used without full understanding of the attributes, how they work, what they do, and what they don’t do, the result is usually an experience that can be more confusing to the user, and that may introduce more barriers to access for them.

To mitigate against common issues caused by ARIA misuse, the W3C WAI has produced documents to guide developers on how to use ARIA to add accessibility information to HTML elements. These documents provide advice for proper use of ARIA in HTML.

The [Using ARIA guide](https://www.w3.org/TR/using-aria/) defines **five rules of ARIA use** that you should follow when you use ARIA attributes in your markup. These rules are _strong_ suggestions for using ARIA that will help you avoid common issues caused by ARIA misuse.

In this chapter, we’re going to learn about the Five Rules of ARIA use, as well as some general guidance to help you use ARIA more responsibly in your projects.

## The First Rule of ARIA

**If you can use a native HTML element or attribute with the semantics and behavior you require already built in, instead of re-purposing an element and adding an ARIA role, state or property to make it accessible, then do so.**

In other words, don’t use ARIA if the features you want already exist in HTML.

```html
<!-- Do this: -->
<button>Click me</button>

<!-- not this: -->
<div role="button">Click me</div>
```

When you’re creating a new component, always ask yourself if there is an HTML element that represents the type of content or control that you want to create. If the answer is yes, use that element.

Like any rule, there are exceptions to this rule.

- **If the feature you need is available in HTML but it is not implemented or it is implemented, but accessibility support is not.**

- **If the visual design constraints rule out the use of a particular native element, because the element cannot be styled as required.** If a native element or control cannot be styled to meet your design requirements, you may reach for ARIA to create a custom version of the component if you absolutely need to. The rule of thumb is that the less you use ARIA, the better. So if you can modify your design or simplify your patterns, that will almost always be a much better approach than rolling up your own custom ARIA widgets. [Under-engineering your design patterns](https://someantics.dev/underengineered/) will almost always result in a more accessible and more usable experience.

- **If the feature is not currently available in HTML.**

**So this rule doesn’t say: “Don’t use ARIA.”** It essentially says: “Prefer to use semantic HTML whenever you can, and reach for ARIA only if and when you need to.”

ARIA should be your **backup strategy.** Always think of it as a polyfill that you reach for when native semantics are lacking, or when there are gaps in accessibility information that you need to fill.

## The Second Rule of ARIA

**Do not change native semantics, unless you really have to.**

For example, suppose you want to build a heading that also acts as a tab that toggles the visibility of a tab panel.

Instead of doing this (overriding meaningful semantics):

```html
<h2 role="tab">Tab panel title</h2>
```

Do this:

```html
<div role="tab"><h2>Tab panel title</h2></div>
```

Remember that _if or when_ you use a non-interactive element (such as a heading element) as a basis for an interactive element (such as a Tab), you not only have to add the Tab semantics using ARIA, but you also need to add the appropriate interaction behavior using JavaScript. Remember: **ARIA does not add behavior. It only changes how the element is exposed to users.**

Another option to avoid overriding meaningful implicit semantics is to reach for the native HTML element for the control you are creating if it exists, and if the pattern allows it. For example, suppose you are creating a custom accordion, then instead of doing this (making the heading into a button):

```html
<h2 role="button" aria-expanded="false">
  heading that toggles a panel
</h2>
```

Do this (place a button inside the heading):

```html
<h2>
  <button aria-expanded="false">
    heading that toggles a panel
  </button>
</h2>
```

As a rule of thumb, you want to avoid overriding _meaningful_ implicit semantics. But there is an exception to this rule.

**It is OK to use native HTML elements, that have similar semantics to ARIA roles used, for fallback. For example, using HTML list elements for the skeleton of an ARIA-enabled, scripted tree widget.**

In other words, you can use JavaScript to add ARIA roles and behavior that enhance meaningful elements to more interactive versions of those elements. Being the big progressive enhancement advocate that I am, I personally endorse this “fallback strategy”. We will see examples of using ARIA to progressively-enhance elements into interactive components in other chapters.

## The Third Rule of ARIA

**All interactive ARIA controls must be usable with the keyboard.**

**If you create a widget that a user can click or tap or drag or drop or slide or scroll, a user must also be able to navigate to the widget and perform an equivalent action using the keyboard.**

**All interactive widgets must be scripted to respond to standard keystrokes or keystroke combinations where applicable.**

An interactive component is not fully accessible if it cannot be operated using a keyboard. This is a baseline WCAG requirement. [SC 2.1.1 Keyboard (Level A)](https://www.w3.org/WAI/WCAG21/quickref/#keyboard) states that:

**All functionality of the content is operable through a keyboard interface without requiring specific timings for individual keystrokes, except where the underlying function requires input that depends on the path of the user’s movement and not just the endpoints.**

We will elaborate more on what this exception means in another chapter.)

The Level AAA version of this SC 2.1.3 [Keyboard (No Exception)](https://www.w3.org/WAI/WCAG21/quickref/#keyboard-no-exception) states that:

**All functionality of the content is operable through a keyboard interface without requiring specific timings for individual keystrokes.**

If you need to create a button using the ARIA button role, for example:

```html
<div role="button">Do something</div>
```

you need to implement keyboard behavior into the button and ensure that the element (in this case: the `<div>`) is able to receive focus; and a user must be able to activate the action associated with the button using both the `Enter / Return` key, and the `Space` key, while keeping in mind the difference in events fired between both keys (as we mentioned [in the previous chapter](https://practical-accessibility.today/chapters/aria-button/)).

If you need to create a custom checkbox, or a custom `<select>`, or whatnot, you also need to make sure it is fully operable using expected keyboard interactions.

Similarly, if you create a desktop-application-style actions menu using ARIA menu roles, the menu items should be _fully_ operable with a keyboard. The user should be able to navigate the menu items using Arrow keys, activate them using `Space` and `Enter` keys, and close a menu using the `Esc` key, for example.

**Do not use role="presentation" or aria-hidden="true" on a focusable element .**

**Using either of these on a focusable element will result in some users focusing on ‘nothing’.**

Remember how we’ve said quite a few times already that ARIA does not affect the DOM — it only affects the accessibility information and how an element is exposed in the accessibility tree?

Just like ARIA does not add interactivity and behavior, **it also does not remove behavior or disable an already-interactive element.**

When you set `aria-hidden="true"` on an element, you remove that element from the accessibility tree. The element will no longer be “seen” by screen readers. But the element will remain present the DOM, and, if it is an interactive element (like a `<button>`), it will remain fully interactive. This means that if the user uses the tab key to navigate through the page, their focus will move to the element, but since its presence has been hidden from the accessibility tree, their screen reader will not announce the element. This will result in them focusing on “nothing”, which is a bad user experience. They know that there is an interactive element that should do something, only they don’t know what that element is, not what it does.

```html
<!-- this button will not be announced by some screen readers because it is removed from the accessibility tree using aria-hidden="true" -->
<button aria-hidden="true">Do something</a>
```

For example, here is a recording of happens when I navigate a page that contains a button that has been hidden using `aria-hidden="true"`. NVDA will not announce the button at all, even when I move my keyboard focus to it:

_The button in this video demonstration has been hidden using aria-hidden="true". Notice how NVDA does not announce its presence when I move my keyboard focus to it._

Similarly, if you set `role="presentation"` on an element, you suppress the element’s semantics so they are no longer included in the accessibility tree. The effects of `role="presentation"` and `aria-hidden="true"` are similar in that sense, but they are very different in how they work. We’ll learn more about them in [another chapter](https://practical-accessibility.today/chapters/hiding-techniques/).

For example, if you set `role="presentation"` on a link, a screen reader will not announce that it is a link when you move your focus to it. The difference here between the effect of `role="presentation"` and `aria-hidden="true"` is that the screen reader can “see” the contents of the link, but not the link itself.

_The link in the video demonstration has role="presentation" suppressing its semantics. Notice how NVDA does not announce the link when it receives focus, but it announces the text content of the link when I navigate to it._

If you apply `aria-hidden="true"` to an ancestor of an element, the element will also be hidden from assistive technologies while remaining focusable and interactive. So you don’t want to do that either.

```html
<!-- don't do this -->
<div aria-hidden="true">
  <button>do something</button>
</div>
```

## The Fifth Rule of ARIA

**All interactive elements must have an accessible name.**

For example, the input field in the following piece of code has a visible label (“user name”), but no accessible name:

```html
<!-- The label is not programmatically associated with the input field -->
<span>user name</span>
<input type="text" />
```

The label is visually associated with the input using layout and spacing cues. So a sighted user can make the association between the input and the text.

But there is no _programmatic_ association between the label and the input. So the text isn’t exposed as an accessible name for the input in the accessibility tree, and therefore the user doesn’t know what the purpose of the input field is — they don’t know that it expects a user name because they are missing this piece of accessibility information.

To associate the text with the input field, you may use aria-labelledby on the input and point to the ID of the text:

```html
<span id="uname">user name</span>
<input type="text" aria-labelledby="uname" />
```

Now the text is used as an accessible name to identify the input.

At this point it is worth re-iterating that you should follow the First Rule of ARIA and use native HTML elements instead of reaching for ARIA attributes. To provide an accessible name for an `<input>`, use the `<label>` element and associate it with the input using the for and id attributes:

```html
<label for="user_name">User name</label>
<input type="text" id="user_name" />
```

We will learn all about providing accessible names for different types of HTML elements and controls in [another chapter](https://practical-accessibility.today/chapters/accNames-and-descriptions/).

These are the five rules of ARIA use in HTML. We will see many practical applications of all of them throughout the course.

In addition to these five rules, there are a couple of additional notes that I want to mention about using ARIA.

Redundant ARIA
There is such a thing as redundant ARIA.

ARIA adds nothing to default semantics of most HTML elements, because most HTML elements, as we know by now, have implicit ARIA roles. This means that the browser treats them as if they already have an ARIA role set on them. As such, explicitly adding an ARIA role to an element that already maps to this role is redundant. For example:

- Adding explicit roles that match the implicit roles of interactive elements such as buttons:

```html
<button role="button">press me</button>
```

- Adding ARIA state or property attributes in addition to their native HTML counterparts:

```html
<input
  type="text"
  required
  aria-required="true" />

<div hidden aria-hidden="true"></div>
```

Not only are the ARIA state attributes redundant here, but they can fall out of sync with the native attributes if you don’t update them together, which creates an unnecessary liability in your code.

- Adding ARIA roles and states or properties to long-implemented structural elements which have very good support:

```html
<h1 role="heading" aria-level="1">
  heading text
</h1>
```

When HTML comes with implicit ARIA roles built in, explicitly adding these semantics is a waste of time. So, you probably want to avoid it.

And last but not least:

## No ARIA is better than bad ARIA

Almost every accessibility specialist you’ll come across will probably mention that: **No ARIA is better than Bad ARIA**.

(You know by now that) ARIA roles, states, and properties are analogous to CSS for assistive technologies — only they create a non-visual presentation of the interface. This means that, for blind screen reader users, ARIA affects what their non-visual experience looks like. Incorrect ARIA misrepresents visual experiences, with potentially devastating effects on assistive technology users.

This is one of the many reasons why using native HTML elements is often preferred over rolling (or [“rolling-up”](https://adrianroselli.com/2020/02/role-up.html)) your own. If you use native HTML elements and controls, you’ll get a lot of accessibility information and functionality built into those elements by browsers. By doing so, you’ll need to reach for ARIA attributes less.

But for the many situations where you will need to use ARIA, there are a couple of things to keep in mind…

## “A role is a promise”

This piece of code:

```html
<div role="button">do something</div>
```

is **a promise** that _you_, the author of this code, have added the required JavaScript that provides the keyboard interactions expected for a button. And this promise is like a binding contract. If you break it, you may create a barrier to access and cause usability problems.

ARIA roles do not affect the visual styles of an element, nor do they affect the DOM or add behavior to an element. Adding an interactive role does not make the `<div>` interactive. You need to add the styles and keyboard interactivity of the button role to the `<div>` to fulfill the promise that you made by using that role, because not fulfilling the promise breaks user expectations of your component, often making it unusable.

Before using a role on an element, especially an interactive role, think about what you’re promising the user, and whether or not you’re fulfilling that promise. If you can use a native HTML element with all the accessibility information built in, do that. If you need a button, use a `<button>` element.

```html
<!-- use this -->

<button>Do something</button>

<!-- instead of this -->
<div role="button">Do something</div>
```

But if you **absolutely have to** roll-up your own custom widgets, or use ARIA roles to override other HTML implicit semantics, make sure you fulfill the promises you make to your users.

## ARIA is a polyfill for HTML semantics

ARIA is a only polyfill for HTML semantics. You’ll hear me say this over and over again.

We usually reach for polyfills (such as JavaScript polyfills) only when support for a certain feature we need is missing in some browsers. Polyfills are a last resort, not a tool to reach for by default.

When you use semantic HTML as it is intended, you’ll find that, on most days, you need ARIA much less than you think!

Instead of relying on ARIA attributes to convey semantics, try to convey as much accessibility information as you can using the semantics built into HTML, and only reach for ARIA when you need more semantics than HTML offers to describe the components you’re creating.

When you do use ARIA, make sure you:

- know what the attributes do and don’t do,
- follow the rules of ARIA use,
- implement the necessary accessibility behavior,
- test, test, test your components using various browsers and assistive technology combinations.
- And, preferably, perform usability testing with disabled assistive technology users to ensure that they can use the components you’re creating.
