# Building an accordion component

In this chapter, we will walk through the process of choosing an implementation for an accordion component. An accordion is a component that can be implemented either using native HTML controls (with the help of a _little_ ARIA and JavaScript), or as a custom ARIA widget. So it is a great case study to talk about the thought process that goes into building a UI component from scratch, as well as what accessibility and usability considerations go into choosing one implementation approach over the other.

This chapter builds upon everything we covered in [the Disclosure Widgets chapter.](https://practical-accessibility.today/chapters/disclosure-widget/) So, if you haven’t watched (or read) it yet, I highly recommend you pause here and go do so before continuing with this chapter.

## What is an accordion?

An accordion is **a group of collapsible sections of content.** It is often used to save space on webpages by collapsing sections of content by default, and expanding them on demand.

So, at its core, **an accordion is a group of disclosure widgets.**

Typically, in an accordion, **only one disclosure widget is open at a time.** What this means is that the disclosure widgets in an accordion are, conceptually, (sort of) “aware” of each other’s state. This “awareness” is what makes the grouping of disclosure widgets behave as an accordion. (We’ll elaborate more what this means in practice in another section.)

So, technically, an accordion is more than just a series of disclosure widgets. An accordion is a series of disclosure widgets **that are related, and can be identified as a group.** And these widgets are **also expected to _behave_ as a group.**

As such, when you want to create an accordion, it’s not enough to _just_ create a series of disclosure widgets and style them to look like one. You will want to semantically convey the relationship between these widgets to screen reader users, as well as implement the necessary behavior for an accordion.

This means that, to create an accordion from a series of disclosure widgets, you will need to do three things:

1. group the widgets together to establish a relationship between them and expose that relationship to screen readers,
2. give the group a label that communicates its purpose, and
3. add the expected accordion behavior to the group.

Now let’s elaborate on what it takes to do this.

## Creating an accordion using `details & summary`

We learned in the previous chapter that `<details>` & `<summary>` can be used to create a native HTML disclosure widget. And that it comes with semantics (roles, states, and properties) as well as interactive behavior built in.

So, to create an accordion, start with a series of native `<details>` disclosure widgets.

### Grouping the disclosure widgets

To communicate the relationship between the disclosure widgets to screen readers, you can either expose them as a **group**, or **as a (landmark) region.**

### What is the difference between a group and a landmark region in ARIA?

We have talked about landmarks in depth in the [landmark regions chapter](https://practical-accessibility.today/chapters/landmark-regions/). We mentioned that there are eight types of landmark regions defined by eight ARIA roles, and that there are HTML elements that implicitly map to most of the landmark roles by default.

Among the eight landmark roles is the generic [region landmark role](https://www.w3.org/TR/wai-aria-1.2/#region), which is defined in the ARIA specification as “a perceivable section containing content that is relevant to a specific purpose and sufficiently important that users will likely want to be able to navigate to the section easily and to have it listed in a summary of the page. Such a page summary could be generated dynamically by a user agent or assistive technology.”

The HTML `<section>` element maps to the region role when it is given an accessible name. This means that you can use a named `<section>` to group together content that you deem important enough to surface as its own landmark so that the user can quickly access it when they need it.

On the other hand, ARIA also provides an additional role that can be used to group content on a page: the group role.

[The group role](https://www.w3.org/TR/wai-aria-1.2/#group) represents a set of user interface elements which are not intended to be included in a page summary or table of contents by assistive technologies.

So the group role can also be used to group and identify a set of elements on the page. But the principal difference between a group and a region is that the group is not included in the summary or “outline” of the page, and the user can therefore not navigate to it using screen reader shortcuts. We will demonstrate this difference using a screen reader shortly.

So, to create an accordion, you can expose the disclosure widgets either as a group or a region.

### Exposing the disclosure widgets as a group

To expose the accordion as a group, you can repurpose a generic `<div>` and assign it a group role:

```html
<div role="group">
  <details>
    <summary>Disclosure widget 1</summary>
    <p>disclosure widget 1 content.</p>
  </details>
  <details>
    <summary>Disclosure widget 2</summary>
    <p>disclosure widget 2 content.</p>
  </details>
  ..
</div>
```

A group also needs a name to identify its purpose (otherwise it’ll be just a collection of items that could be grouped together for any reason).

Most accordions are typically preceded by a heading that describes their purpose. Using `aria-labelledby`, you can expose the heading as an accessible name to the group:

```html
<div role="group" aria-labelledby="group-label">
  <h2 id="group-label">[ Group label ]</h2>

  <details>
    <summary>Disclosure widget 1</summary>
    <p>disclosure widget 1 content.</p>
  </details>
  <details>
    <summary>Disclosure widget 2</summary>
    <p>disclosure widget 2 content.</p>
  </details>
  ..
</div>
```

If the accordion isn’t preceded by a heading, you can give it an accessible name using a visually-hidden text node (like a `<span>`):

```html
<div role="group" aria-labelledby="group-label">
  <span id="group-label" class="visually-hidden"
    >[ Group label ]</span
  >

  <details>
    <summary>Disclosure widget 1</summary>
    <p>disclosure widget 1 content.</p>
  </details>
  <details>
    <summary>Disclosure widget 2</summary>
    <p>disclosure widget 2 content.</p>
  </details>
  ..
</div>
```

Using [a utility class](https://practical-accessibility.today/chapters/hiding-techniques/#providing-screen-reader-only-accessible-text) which we will learn all about in [the hiding techniques chapter](https://practical-accessibility.today/chapters/hiding-techniques/), you can hide the `<span>` visually while making sure it remains accessible to screen readers.
