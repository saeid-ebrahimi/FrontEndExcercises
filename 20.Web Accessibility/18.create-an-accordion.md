# Building an accordion component

In this chapter, we will walk through the process of choosing an implementation for an accordion component. An accordion is a component that can be implemented either using native HTML controls (with the help of a _little_ ARIA and JavaScript), or as a custom ARIA widget. So it is a great case study to talk about the thought process that goes into building a UI component from scratch, as well as what accessibility and usability considerations go into choosing one implementation approach over the other.

This chapter builds upon everything we covered in [the Disclosure Widgets chapter.](https://practical-accessibility.today/chapters/disclosure-widget/) So, if you haven’t watched (or read) it yet, I highly recommend you pause here and go do so before continuing with this chapter.

## What is an accordion?

An accordion is **a group of collapsible sections of content.** It is often used to save space on webpages by collapsing sections of content by default, and expanding them on demand.

So, at its core, **an accordion is a group of disclosure widgets.**

Typically, in an accordion, **only one disclosure widget is open at a time.** What this means is that the disclosure widgets in an accordion are, conceptually, (sort of) “aware” of each other’s state. This “awareness” is what makes the grouping of disclosure widgets behave as an accordion. (We’ll elaborate more what this means in practice in another section.)

So, technically, an accordion is more than just a series of disclosure widgets. An accordion is a series of disclosure widgets **that are related, and can be identified as a group.** And these widgets are **also expected to _behave_ as a group.**

As such, when you want to create an accordion, it’s not enough to _just_ create a series of disclosure widgets and style them to look like one. You will want to semantically convey the relationship between these widgets to screen reader users, as well as implement the necessary behavior for an accordion.

This means that, to create an accordion from a series of disclosure widgets, you will need to do three things:

1. group the widgets together to establish a relationship between them and expose that relationship to screen readers,
2. give the group a label that communicates its purpose, and
3. add the expected accordion behavior to the group.

Now let’s elaborate on what it takes to do this.

## Creating an accordion using `details & summary`

We learned in the previous chapter that `<details>` & `<summary>` can be used to create a native HTML disclosure widget. And that it comes with semantics (roles, states, and properties) as well as interactive behavior built in.

So, to create an accordion, start with a series of native `<details>` disclosure widgets.

### Grouping the disclosure widgets

To communicate the relationship between the disclosure widgets to screen readers, you can either expose them as a **group**, or **as a (landmark) region.**

### What is the difference between a group and a landmark region in ARIA?

We have talked about landmarks in depth in the [landmark regions chapter](https://practical-accessibility.today/chapters/landmark-regions/). We mentioned that there are eight types of landmark regions defined by eight ARIA roles, and that there are HTML elements that implicitly map to most of the landmark roles by default.

Among the eight landmark roles is the generic [region landmark role](https://www.w3.org/TR/wai-aria-1.2/#region), which is defined in the ARIA specification as “a perceivable section containing content that is relevant to a specific purpose and sufficiently important that users will likely want to be able to navigate to the section easily and to have it listed in a summary of the page. Such a page summary could be generated dynamically by a user agent or assistive technology.”

The HTML `<section>` element maps to the region role when it is given an accessible name. This means that you can use a named `<section>` to group together content that you deem important enough to surface as its own landmark so that the user can quickly access it when they need it.

On the other hand, ARIA also provides an additional role that can be used to group content on a page: the group role.

[The group role](https://www.w3.org/TR/wai-aria-1.2/#group) represents a set of user interface elements which are not intended to be included in a page summary or table of contents by assistive technologies.

So the group role can also be used to group and identify a set of elements on the page. But the principal difference between a group and a region is that the group is not included in the summary or “outline” of the page, and the user can therefore not navigate to it using screen reader shortcuts. We will demonstrate this difference using a screen reader shortly.

So, to create an accordion, you can expose the disclosure widgets either as a group or a region.

### Exposing the disclosure widgets as a group

To expose the accordion as a group, you can repurpose a generic `<div>` and assign it a group role:

```html
<div role="group">
  <details>
    <summary>Disclosure widget 1</summary>
    <p>disclosure widget 1 content.</p>
  </details>
  <details>
    <summary>Disclosure widget 2</summary>
    <p>disclosure widget 2 content.</p>
  </details>
  ..
</div>
```

A group also needs a name to identify its purpose (otherwise it’ll be just a collection of items that could be grouped together for any reason).

Most accordions are typically preceded by a heading that describes their purpose. Using `aria-labelledby`, you can expose the heading as an accessible name to the group:

```html
<div role="group" aria-labelledby="group-label">
  <h2 id="group-label">[ Group label ]</h2>

  <details>
    <summary>Disclosure widget 1</summary>
    <p>disclosure widget 1 content.</p>
  </details>
  <details>
    <summary>Disclosure widget 2</summary>
    <p>disclosure widget 2 content.</p>
  </details>
  ..
</div>
```

If the accordion isn’t preceded by a heading, you can give it an accessible name using a visually-hidden text node (like a `<span>`):

```html
<div role="group" aria-labelledby="group-label">
  <span id="group-label" class="visually-hidden"
    >[ Group label ]</span
  >

  <details>
    <summary>Disclosure widget 1</summary>
    <p>disclosure widget 1 content.</p>
  </details>
  <details>
    <summary>Disclosure widget 2</summary>
    <p>disclosure widget 2 content.</p>
  </details>
  ..
</div>
```

Using [a utility class](https://practical-accessibility.today/chapters/hiding-techniques/#providing-screen-reader-only-accessible-text) which we will learn all about in [the hiding techniques chapter](https://practical-accessibility.today/chapters/hiding-techniques/), you can hide the `<span>` visually while making sure it remains accessible to screen readers.

### Exposing the disclosure widgets as a landmark region

If the accordion contains important information that a screen reader user may benefit from navigating to more quickly, you can use a named `<section>` element to expose the accordion as a page landmark.

Most important regions of content on a page are usually preceded with a heading that describes the region. So, using the `aria-labelledby` attribute again, you can provide an accessible name to the `<section>`:

```html
<section aria-labelledby="group-label">
  <h2 id="group-label">[ Group label ]</h2>
  <details>
    <summary>Disclosure widget 1</summary>
    <p>disclosure widget 1 content.</p>
  </details>
  <details>
    <summary>Disclosure widget 2</summary>
    <p>disclosure widget 2 content.</p>
  </details>
  ..
</section>
```

## Adding accordion behavior using JavaScript

`<details>` and `<summary>` come with the keyboard interactions for expanding and collapsing our panels built in. But each `<details>` behaves as an independent widget. If one disclosure widget is expanded, the other widgets in the group won’t collapse, because they are not “aware” of each other’s state. And there is no native functionality in HTML for this behavior. So it is on you to manage this state so that if one disclosure widget is open, the previously opened widget is closed. Otherwise, the grouping of disclosure widgets is not an ‘accordion’.

Since the browser bakes keyboard interactions into the individual disclosure widgets for us, all we need to do is to add a small script. This script:

1. Queries all the `<details>` inside our group.
2. Then, for each widget: when the widget is activated,
3. it loops through all the widgets in the accordion (except the one that was just activated), and
4. closes those widgets (by removing the open attribute from the `<details>` element).

```javascript
let group = document.querySelector(
    "[data-accordion]"
  ),
  //get all the <details> widgets in the group
  widgets = group.querySelectorAll("details");

// for each widget...
widgets.forEach(function (widget, index) {
  // ...when the widget is clicked/activated...
  widget.addEventListener("click", function () {
    // ...loop through all other widgets...
    for (i = 0; i < widgets.length; i++) {
      // ...except the current one...
      if (i == index) continue;

      // ...and close them.
      widgets[i].removeAttribute("open");
    }
  });
});
```

Note that I am using a `data-*` attribute on the group as a hook in the script. I prefer using data attributes instead of classes to keep my class declarations to a minimum and exclusive to my CSS (as part of a “separation of concerns” approach).

This is all you need to create a fully-functional accordion using `<details>` and `<summary>`.

And here is a video demonstrating how the accordion is announced when it is navigated to using VoiceOver with Safari on macOS. I have two accordions on this page. The first accordion that we marked up using a `<div role="group">` with the visually-hidden label, and the second one that we marked up using a named `<section>`. VoiceOver announces the start and end of each accordion. It announces the first accordion as a group, with the group’s label. And it announces the second accordion as a region. And when I pull up VoiceOver’s Web rotor, you will see that the second accordion (which has an implicit region role) is listed in the page’s Landmarks list.

You may have noticed that when I navigated through the first accordion with the visually-hidden label, VoiceOver announces the presence of the visually-hidden `<span>` again. Ideally, this should not be the case. To avoid this, you can use the HTML `hidden` attribute to hide the text node referenced in `aria-labelledby`.

```html
<!-- Instead of this: -->
<div role="group" aria-labelledby="group-label">
  <span id="group-label" class="visually-hidden"
    >[ Group label ]</span
  >

  ..
</div>

<!-- Do this: -->
<div role="group" aria-labelledby="group-label">
  <span id="group-label" hidden
    >[ Group label ]</span
  >

  ..
</div>
```

When the node is hidden using the `hidden` attribute, it will not be accessible to screen readers. But since we are referencing this node in `aria-labelledby`, the browser will still expose it as an accessible name to the group. This way, we are hiding the text node and only exposing it for its intended purpose, and the hidden text no longer creates an additional reading stop for someone using the screen reader’s virtual cursor. We will learn more about how to hide elements and how they impact screen readers in the hiding techniques chapter.

## What if your accordion contains headings?

Sometimes accordions are designed to be made of a series of sections, each section preceded by a heading that describes the content within that section. Then, to conserve space, the content of each section is collapsed, and it is expanded when the heading “is activated”.

But the thing is: headings can’t be activated because they are not interactive elements.

What many developers will do to provide headings for their accordions is that they will place those headings inside the `<summary>` element of the accordion’s disclosure widgets. The problem with doing so is that the headings may no longer be exposed as headings when they are placed inside the `<summary>`.

```html
<!-- Do not do this -->
<section aria-labelledby="region-label">
    <h2 id="region-label">[ region label ]</h2>
    <details>
        <summary><h3>I am a heading</h3></summary>

        ...
    </details>

    <details>
        <summary><h3>I am another heading</h3></summary>

        ...
    </details>

    ...
</div>
```

We mentioned in [the Disclosure Widgets chapter](https://practical-accessibility.today/chapters/disclosure-widget/) that the `<summary>` element is mapped in most accessibility APIs to the button role. And we also mentioned in the [ARIA 101 chapter](https://practical-accessibility.today/chapters/aria/) an element with an implicit or explicit button role suppresses the semantics of all of that element’s children, as [per the ARIA specification](https://www.w3.org/TR/wai-aria-1.2/#button). This means that when the `<summary>` is exposed as a button, the heading may not be exposed. As a result, the heading may longer contributes to the page’s outline, and the user may no longer be able to explore and navigate to the heading(s) using their screen reader shortcuts.

_That being said_, browsers and assistive technologies sometimes override the behavior defined in the specification in an attempt to improve the user experience for AT users. We saw an example of that in [the Semantics chapter](https://practical-accessibility.today/chapters/html-semantics/) when we mentioned how VoiceOver removes list semantics to spare its users unnecessary announcements associated with lists when lists are over-used by developers.

In the case of headings contained inside buttons, not all browsers and assistive technologies respect the presentational behavior that buttons are meant to apply to their children.

VoiceOver (both iOS and macOS) currently exposes the presence of a heading placed inside a `<summary>`.

NVDA with Firefox also exposes the presence of headings inside `<summary>`. And so does Narrator paired with MSEdge.

On the other hand, JAWS, the most popular screen reader, currently does not announce the presence of the heading when it is placed inside `<summary>`. Neither does TalkBack with Chrome on Android.

Accessibility engineer Scott O’Hara has shared the results of testing `<summary>` with headings using various screen reader and browser combinations that I recommend checking out for more details and test cases that are useful to refer to in your own work. These test results further emphasize the importance of testing your work across different browser and screen reader combinations to make sure that something works (or does not work!) as expected. They are also a good reminder that sometimes things don’t work consistently across browsers and screen readers.

If you use `<details>` & `<summary>` to mark up an accordion that is structured using headings, many of your users may miss out on the presence of those headings.

To retain heading semantics, you don’t want to place them inside the `<summary>`. You also can’t place the `<summary>` inside the heading because then the `<summary>` will no longer be the first direct child of the `<details>`, and it will therefore no longer be used as the disclosure’s trigger. Here’s an example:

```html
<!-- Do not do this either. -->
<section aria-labelledby="region-label">
    <h2 id="region-label">[ region label ]</h2>
    <details>
        <h3><summary>I am a heading</summary></h3>

        ...
    </details>
    ...
</div>
```

Another approach some developers will take is overriding the heading semantics using role="button".

```html
<!-- don't do this -->
<h2 role="button" tabindex="-1">..</h2>
```

This approach defeats the purpose of using headings to begin with.

What you need to do instead is to wrap the disclosure widget’s trigger in a heading. This ensures that the heading semantics are retained. And since you can’t do that using the native disclosure widget, you will need to opt for a series of custom disclosure widgets to create your accordion instead. The markup for an accordion structured using headings and custom disclosure widgets may look like this:

```html
<section aria-labelledby="region_label">
  <h2 id="region_label">[ Region label ]</h2>

  <div class="disclosure-widget">
    <h3>
      <button
        aria-expanded="[ true | false ]"
        aria-controls="[ panel 1 ID ]">
        [ trigger label ]
      </button>
    </h3>
    <div id="[ panel 1 ID ]">...</div>
  </div>

  <div class="disclosure-widget">
    <h3>
      <button
        aria-expanded="[ true | false ]"
        aria-controls="[ panel 2 ID ]">
        [ trigger label ]
      </button>
    </h3>
    <div id="[ panel 2 ID ]">...</div>
  </div>

  ...
</section>
```

Like the custom solo disclosure widget we built in the previous chapter, each widget in the accordion has a trigger and a panel controlled by that trigger. The only difference here is that the button is wrapped in a heading that is used to structure the accordion.

Then, using JavaScript, you can wire up the accordion behavior. Since the buttons won’t do anything without JavaScript, it is best that you follow the same strategy we discussed in [the Disclosure Widgets chapter](https://practical-accessibility.today/chapters/disclosure-widget/) to progressively enhance the sections into interactive widgets. This ensures that the content will remain available to all users even when JavaScript doesn’t run. So you would start with a series of sections and their corresponding headings, and when the JavaScript runs, create and append the buttons inside the headings, add and manage ARIA attributes, as well as toggle the display of the sections when the triggers are activated.
