# Applied ARIA: creating a custom button component

The best way to demonstrate what ARIA does and doesn’t do is to put it into practice.

In this chapter, we’re going to walk through the process of building a custom button element using ARIA. By the end of the chapter, you will not only get a clearer understanding of what ARIA can and can’t do, but you will also hopefully appreciate the benefits of the native HTML `<button>` element, and the accessibility that it comes packed with.

Alright, so let’s get building!

## Building a custom button component from scratch

We’re going to be creating our custom button by repurposing the generic `<div>` element:

```html
<div>Do something</div>
```

We’re going to inspect the accessibility information for our custom button every step of the way to see how it is going to be exposed to a screen reader.

The `<div>` is a generic container that has no meaningful semantics. Depending on the browser, it is either going to be exposed as a generic container in the accessibility tree, or not exposed at all.

If we pull up the Chrome DevTools and inspect the `<div>` in the accessibility tree, you’ll notice that Chrome does indeed expose it as a generic container (it also has the generic role which is built into the `<div>`).

![div tag ARIA role]("./markdown-assets/14.1.div-role.webp")

### Creating visual affordances with CSS

Since a `<div>` is not a button, the browser doesn’t apply any default button styles to it, so it doesn’t look like a button at all. We can make it look like a button using a few lines of CSS:

```css
.btn {
  font: inherit;
  font-size: 1.25rem;
  font-weight: 500;
  line-height: inherit;
  display: inline-flex;
  padding: 0.5em 0.75em;
  margin: 0.5rem;
  background-color: var(
    --button-background-color
  );
  color: var(--button-text-color);
  border-radius: var(--border-radius);
}
```

```html
<div class="btn">Do something</div>
```

Our custom button now has the visual affordances of a button. But it still does not carry the semantics and accessibility information that indicates that it is a button to someone who can’t see it.

The CSS styles we applied have no effect on the semantics of the button because CSS styles do not provide semantic meaning to HTML elements. As a result, a blind screen reader user has no indication that this element is a button.

We need to create the same semantic affordances for screen reader users that we created using CSS. We’ll do that using ARIA.

## Providing semantic affordances with ARIA

To let screen readers know that this element is a button, we will explicitly instate button semantics by adding the button role to it:

```html
<div class="btn" role="button">Do something</div>
```

Now if we inspect the accessibility tree again, we’ll see that the browser now exposes the `<div>` as a button.

![div with ARIA role](./markdown-assets/14.div-role.webp)

Since our button needs an accessible name, the browser uses the text content between the opening and closing `<div>` tags as a name for our button.

Great, so now we’ve created a button that can be recognized as a button by sighted as well as blind users. But is our button really a button yet?

### The duck test

Let’s perform a duck test here. [The duck test](https://en.wikipedia.org/wiki/Duck_test) states that:

_**“If it looks like a duck, swims like a duck, and quacks like a duck, then it probably is a duck.”**_

Our button _looks_ like a button — both visually and semantically. But does it _quack…_ uhh… I mean behave like a button? We’ll see.

I’m going to add a native HTML `<button>` next to our custom button for comparison.

```html
<button>Alert me</button>
```

The native button comes with browser styles applied to it by default. But we want our buttons to look alike.

I could just go ahead and use the same btn class name on the <`button>` like I did on the `<div>`, but I won’t do that just yet. First, I want to share a useful quick tip with you.

Typically, when we want to style a button (or any other form control) from scratch, we prefer a minimal, clean slate — no default browser styles that we need to override or undo. Ideally, we would be able to remove all the default browser styles with just one **CSS declaration**, and then go ahead and apply our own custom styles to it.

That’s exactly what we can do with the `all: unset` declaration.

```css
button {
  all: unset;
}
```

When applied to a native control, `all: unset` unsets all the default browser styles on that control. When applied to the button, it strips the button of all the default button styles. The result is that the button looks like a simple string of text (similar to what the `<div>` looked like before we applied the button styles to it.) After unsetting all the default styles, you can go ahead and style the button any way you want with the same ease that you can style your `<div>`s.

The only thing you want to remember is to make sure that you unset all the default styles first, and then set your own styles afterwards in the cascade.

And keep in mind that this declaration will remove all default browser styles, including the default focus indicator, so you need to remember to add [focus styles](https://practical-accessibility.today/chapters/focus-indicators/) to the button, too.

_I wanted to highlight this particular declaration because one of the main reasons developers create custom buttons instead of using the native `<button>` is because they think that the native button is hard to style. But as you can see, you can create the exact same button styles using the native button as you would using a `<div>`, with the help of one powerful CSS declaration._

Now, using the btn class name, I’m going to apply our custom button styles to the native button:

```html
<button class="btn"></button>
```

The native button looks like we want it to look right now. It is also exposed as a button with an accessible name in the accessibility tree. Not only that, but the browser has exposed even more information about it — indicating that the button is focusable, and indicating whether it is currently focused or not.

![button in accessibility tree](/markdown-assets/14.3.button-accessibility-tree.webp)

Screenshot of the Chrome DevTools accessibility panel showing that the button element is exposed. The accessibility information also includes more attributes of the button indicating that it is focusable and currently focused.
We didn’t need to add any ARIA attributes or do anything on our end to expose this accessibility information. It all comes built into the `<button>` element. Excellent.

### Adding an action to the buttons

Now let’s make our buttons do something. After all, that’s what buttons are for, right? — triggering an action, such as opening a modal dialog, or expanding and collapsing a menu dropdown, and so on and so forth.

Using a little JavaScript, I’m going to get all the buttons that share the class name btn, and attach a click handler on each of them that will just trigger an alert that indicates that the button has been clicked — just for demonstration purposes.

```javascript
var btns = document.querySelectorAll(".btn");

btns.forEach((btn) => {
  btn.addEventListener("click", doSomething);
});

function doSomething() {
  alert("You clicked a button.");
}
```

If I click on the native button now, sure enough it triggers the alert. And if I click on our custom button, the click event is also fired and we get the alert.

Great.

But we’re not done yet.

Our button looks like a button, and it can trigger an action when it is clicked. But it is not fully accessible yet.

### Making the button operable by keyboard

Some screen reader users, sighted keyboard users, and users of assistive technologies that works through a keyboard or emulates keyboard functionality, will typically use the `tab` key to navigate to interactive controls on a page. So we need to make sure that our button is keyboard-operable, which is a baseline WCAG requirement.**If it’s not keyboard-accessible, then it’s not fully accessible.**

Now, to make navigating through the page better in this demo, I’m going to add two focusable elements: a link before the two buttons and one after them — just so we have something to tab to and from.

Now, if I press the `tab` key to navigate to our custom button, the keyboard focus should move to the button. But it doesn’t.

This is because there is nothing in the _implicit_ semantics of the `<div>` that tells the browser that this is an interactive control. The browser doesn’t treat our custom button as an interactive control. As far as the browser knows, the `<div>` is just a generic grouping element, so it doesn’t bind any interactive behavior to it. Even after we add the button role to it, the browser doesn’t add any interactivity to it.

Remember, **ARIA attributes only affect how an element is exposed in the accessibility tree**. They express what this things _is_ to assistive technologies, but they don’t affect the DOM, and they don’t add behavior.

The `role="button"` that we added to the `<div>` only affects how the `<div>` is presented to screen readers.

To make our button focusable, we need to use the tabindex attribute.

We will talk about the tabindex attribute in more detail in another chapter. But for now, all you need to know is that `tabindex="0"` adds an element to the natural tabbing order of the page. In other words, **when you add `tabindex="0"` to an element, the element becomes keyboard-focusable.**

```html
<div class="btn" role="button" tabindex="0">
  Do something
</div>
```

So if I press `tab` key now, our button receives keyboard focus.

And if I inspect the accessibility tree, I can see that the browser now adds the `focusable` attribute to the button’s accessibility information, indicating that it is focusable.

Now, let’s see if we can operate our button using keyboard.

If I press the `Space` or `Enter` key (or the return key on macOS) on the _native_ button, the browser fires the event handler that we attached to the button earlier. This is a nice thing about the native button: when you bind an action to the click event, the browser fires that action when the button is operated using keyboard, too.

Now if I tab back to our custom button and press the `Space` key nothing happens. If I press the return key, nothing happens either.

As expected, the browser doesn’t provide keyboard functionality for our custom button like it does for the native button. ARIA attributes add semantics, but they don’t add behavior. Any interactive behavior we want, we will need to implement it ourselves.

So now using JavaScript again, we’re going to have to listen for when a key is pressed, check if that key is the Space key or the Enter key, and bind our `doSomething()` function to it.

```javascript
btn.addEventListener("keydown", function (e) {
  if (e.keyCode === 13 || e.keyCode === 32) {
    doSomething();
  }
});
```

Now if I activate the custom button using the Space key or the Enter key, our function fires as it should.

But our work is not done yet.

### Matching custom keyboard interactions to native ones

We need to make sure that the keyboard interactions that we create match those of the native `<button>` element _exactly_, otherwise we’re going to be creating a mis-match between what the user expects and what we have built, thus breaking the user experience, and possibly creating a usability problem or a barrier to access.

Did you know that the way the Space and Enter keys work on a button is not really the same?

Accessibility consultant Adrian Roselli [has documented](https://adrianroselli.com/2022/04/brief-note-on-buttons-enter-and-space.html) how a native button fires when the Space and Enter keys are used. He notes that:

**A native `<button>` fires on key down when that key is Enter. If you hold down the `Enter` key, it continues to fire for as long you hold Enter (or something crashes). A native `<button>` fires on key up when that key is `Space`. If you do not release the Space, and also press `Tab` to move away from the control, the control will not fire.**

Skilled keyboard users are familiar with how buttons are activated, and may use this knowledge to confirm that something is interactive or not. And when you create a custom element, **you need to make sure that what you’re building matches user expectations.**

So now we will modify our script to activate the button on _key up_ when the `Space` key is pressed, and on _key down_ when the `Enter` key is pressed:

```javascript
btn.addEventListener("keydown", function (e) {
  // enter key
  if (e.keyCode === 13) {
    doSomething();
  }
});
btn.addEventListener("keyup", function (e) {
  // space key
  if (e.keyCode === 32) {
    doSomething();
  }
});
```

To demonstrate the difference between the two I’m going to console-log a message that fires when I hold down each of the keys.

```javascript
btn.addEventListener("keydown", function (e) {
  // enter key
  if (e.keyCode === 13) {
    // doSomething();
    console.log("action triggered on enter");
  }
});
btn.addEventListener("keyup", function (e) {
  // space key
  if (e.keyCode === 32) {
    // doSomething();
    console.log("action triggered on space");
  }
});
```

Now if I press and hold the Enter key, the event fires for as long as I am holding the key.

If I press and hold the Space key, the event fires only once: when I stop pressing.

### Disabling the custom button

There’s actually even more that the native button offers for free that you have to handle yourself. For example, the native button can be disabled using the HTML disabled attribute.

```html
<button disabled>Alert me</button>
```

If you create a custom button, you’re going to have to express that the button is disabled not only by making it look disabled, but also by ensuring that the disabled state is conveyed to screen reader users using the aria-disabled attribute.

```html
<div
  class="btn btn--disabled"
  role="button"
  tabindex="0"
  aria-disabled="true">
  Do something
</div>
```

```css
.btn--disabled {
  /* disabled button styles */
}
```

So, you see, there’s quite a lot you have to keep in mind and implement yourself when you go down the path of building custom alternatives to native controls. You need to make sure the user experience matches what the user expects, otherwise your control will be ‘broken’.

And that’s not even all you need to do! You still need to check to see if your control is touch-operable, and can be used with mobile assistive technologies. You also need to ensure it looks good in Forced Colors modes such as Windows High Contrast mode (which we will learn all about in [another chapter](https://practical-accessibility.today/chapters/forced-colors-mode/)).

## Custom Control Accessible Development Checklist

The [Using ARIA guide](https://www.w3.org/TR/using-aria/) provides a checklist of [requirements for custom controls](https://www.w3.org/TR/using-aria/#ariachecklist). These requirements include ensuring that the custom control is:

**focusable**
Can you get to the control via the keyboard?

**keyboard operable**
Can you use the control with the keyboard?

**touch operable**
Can you use the control with touch gestures? With assistive technology enabled?

**expected operation**
Can you operate the control using the standard keys and/or touch gestures for the control type? (which is what we did by ensuring the button works as expected with the `Space` and `Enter` keys)

**clear indication of focus**
Can you easily see it when the control has focus?

**label**
The control has a text label that is exposed as an accessible name in accessibility APIs

**role**
The control has an appropriate role exposed in accessibility APIs

**states and properties**
The control has any UI states and properties that it has exposed in accessibility APIs

**color contrast**
The control label/description/icon is perceivable/usable for low vision users

**high contrast mode**
The control is perceivable/usable when High Contrast Mode is enabled (e.g. Windows HC mode)

Any time you create a custom control, you need to check that you’re meeting all of these requirements. If the answer to any of them is ‘No’ then you will need to consider fixing the component before release, or at least documenting the issues to inform other developers that your custom control will not be usable by some people due to limited accessibility support.

## Outro

The purpose of this chapter was to:

1. demonstrate how ARIA might be used,
2. demonstrate what it can and can’t do,
3. and to show the benefits of using a native HTML control over a custom one whenever possible.

Because of how powerful ARIA is, it can cause as much damage as it can do good. To make sure it is used responsibly, the W3C have created practical guides which demonstrate how to use and not to use ARIA.
