# What is the accessibility tree?

When you write HTML and CSS, how do you know how your code is going to be exposed to assistive technologies like screen readers? How do you know what information screen readers are getting about your components? How do you know if you’re exposing the right information that the user needs to understand and navigate your page? What if a component is missing a critical piece of information that the user absolutely needs to understand and operate it?

It would be great if we had a way to inspect the accessibility information of our elements just like we can inspect the styles and behavior using the browser DevTools, right?

Well, we do have a way to do that. We can do that via the **accessibility tree.**

The accessibility tree is the structure that carries accessibility information about your page and exposes it to assistive technologies like screen readers. It **plays a key role in understanding just how accessible your work is. And understanding it is critical to creating accessible web content.**

In this chapter, you will learn everything you need to know about the accessibility tree and the information it carries. You will also learn **how to inspect the accessibility tree in the browser DevTools** to get important and practical insights into the accessibility of every element on the page. Using these insights, you can find and fix important accessibility issues that would otherwise create barriers to access for your users.

It all starts with your HTML markup, which the browser uses to generate the DOM tree.

## From HTML to the DOM tree

The DOM tree is a tree-style representation of all the page’s HTML elements and their relationships.

![From HTML to the DOM tree]("./markdown-assets/07.1.From HTML to the DOM tree.webp")

The markup we write defines parent-child relationships between the different elements that make up the page. So the browser parses the HTML and creates **a tree of objects** that captures the parent-child relationships defined in our markup.

**All the page’s HTML elements are represented in the DOM tree.** This includes the `<html>` root element, the `<head>`, `<body>`, `<div>`s, `<p>`s, `<h2>`s, and every other HTML element used on the page.

Combined with presentation styles provided in CSS, the DOM tree is then painted into a visual user interface (UI) that sighted users use to navigate and interact with the content. But not all users can see what’s on the screen.

![DOM tree to Visual UI]("./markdown-assets/07.2.From DOM tree to Visual UI.webp")

People who can’t see the screen need **an alternative representation of the page that describes the various elements** of the page to them. This alternative representation must contain **accessibility information about the elements of the page**.

Not _all_ HTML elements ‘carry’ information that is relevant to assistive technologies. There are a lot of elements that are not essential for the understanding of the page. So, modern browsers expose the accessibility information that is relevant in **a separate tree structure**. We refer to this tree as _the accessibility tree_.

## The accessibility tree

Like the DOM tree, the accessibility tree is **a tree of objects**. Each object represents an element on the page and contains **accessibility information** about that element. This information includes what the element is, its properties, and how it relates to other elements on the page.

![The accessibility tree]("./markdown-assets/07.3.The accessibility tree.webp")

The accessibility tree is a structure parallel to the DOM tree. “Parallel” does not necessarily mean there is a 1:1 match between the nodes of these two trees. The accessibility tree is typically **a subset of the DOM tree**, because (as we mentioned earlier) not all elements in the DOM carry information that is relevant to accessibility.

For example, `<div>`s and `<span>`s are “generic” elements which are not always exposed in the accessibility tree by default. They are not exposed because they don’t carry useful information (or meaningful semantics) that assistive technology users need to understand the page. There are many other HTML elements which are also generic. They too are often ignored in the accessibility tree, because they do not carry semantics important for accessibility. Other elements may not be reported in the accessibility tree because they have been explicitly hidden (using HTML, CSS, or ARIA).

The browser parses the HTML markup of a page and uses the **semantics as well** as the styles applied to an element to determine if it is important to accessibility. Elements that are important to understanding and navigating the page are exposed as objects in the accessibility tree. For example, the browser will include `<button>`s, `<input>`s, and other form controls, as well as headings, lists, landmarks, and other important UI components.

Unlike the DOM tree, **the accessibility tree is not painted into a visual UI**. Assistive technologies like screen readers use the information in the accessibility tree to understand and present interface elements to their users (using Text-to-Speech or a braille display, for example).

![07.4.the accessibility tree vs dom tree]("./markdown-assets/07.4.the accessibility tree vs dom tree.webp")

## What kind of information does the accessibility tree contain?

Typically, there are four main pieces of information that the browser exposes about an element in the accessibility tree:

![What kind of information does the accessibility tree contain]("./markdown-assets/07.5.What kind of information does the accessibility tree contain.webp")

### role – What kind of thing is it?

The role is what the element is. It is its purpose. For example, is it a button? a link? a list? a nav bar? a heading? A role lets a screen reader user know **what something is, which is also an indication of how that thing is to be used.**

### name – How can we refer to this thing?

The **accessible name (accName) identifies an element within an interface.** If a button has a text label, this will typically be its name. For example, a button with the text "Submit" will have "Submit" as its accessible name. The accessible name identifies the button and should help indicate what it does.

### description – How do we further describe this thing?

Sometimes an element may have a short description that provides more useful information to the user. For example, a text input field may have a short description of what the expected input looks like.

### state – Does it have a state? If yes, what is its current state?

For example, is the button pressed? is the checkbox checked, unchecked, or undetermined? States are usually dynamic and respond to user interaction, and will be announced to the user when a state change happens.

The accessibility tree also exposes object:

- properties (e.g. a button is focusable) and
- relationships (e.g. is it tied to another element on the screen? is it part of a group? is it labelled or described by another element?)

Roles typically come from an HTML element’s semantics. These are called _implicit_ roles.

Roles (as well as states and properties) can also be set using ARIA attributes. You can override an element’s implicit role by **explicitly** defining a new role using ARIA.

Accessible names and descriptions are **only included in the accessibility tree if we provide them in our markup**. If we don’t provide an accessible name for a UI element or control, no name will be exposed to screen readers. The element then can’t be identified and the user may not know what it does.

Some CSS properties can also affect accessibility information. Not only can you hide the presence of an element altogether from the accessibility tree (for example, using `display: none` will hide an element’s presence from the accessibility tree), some properties may also modify element semantics. We will see more examples of that in other chapters.

So the accessibility information provided in the accessibility tree is affected by:

1. the semantics of the HTML elements used,
2. the styles applied to those elements,
3. and any ARIA attributes used on those elements.

This means that the code you write **could potentially create barriers to access** when you don’t write it with accessibility in mind.

Throughout the chapters of the course, we will take deep dives into different aspects of your code that are used to determine the accessibility information of an element, from semantic HTML, to ARIA attributes (roles, states, and properties), accessible names and descriptions, and the effect of CSS on the accessibility of an element. You will deeply understand what makes an element or component accessible, and how to avoid creating barriers to access when you write HTML and CSS.

## Inspecting the accessibility tree in browser DevTools

You can inspect what accessibility information is exposed about an element in the accessibility tree using most browser DevTools. By inspecting the accessibility tree, you can get important insights into how your content will be exposed to and presented by assistive technologies.

My go-to DevTools for inspecting the accessibility tree are the Chromium DevTools (available in both Chrome and Edge).

One of the most important things I want you to take away from this section is that the information the browser exposes in the accessibility tree is the information that screen readers get about the page. **Even though screen readers _can_ access the DOM, they often don’t**. They interact with the information that is important to accessibility (rather than the entire DOM), and that information is made available to them by the browser in the accessibility tree.

## The accessibility tree may not look the same across all browsers and platforms

The accessibility tree for a page may not look the same across all browsers and platforms. This means that **the way screen readers announce the page’s content to their users may differ across browsers and platforms. (And that’s OK!)**

When modern browsers parse HTML markup, they provide accessibility information about HTML elements (in the accessibility tree) using:

1. the elements used in the markup, and
2. the Accessibility API Mappings (AAMs) of those elements.

**Accessibility API Mappings define which ARIA role each HTML element is mapped to.**

Accessibility APIs (AAPI) are software provided natively by operating systems. They facilitate communicating accessibility information about a user interface to screen readers.

![Accessibility API Mapping]("./markdown-assets/07.6.Accessibility API Mapping.webp")

![Operating systems and Accessibility API(s) they provide]("./markdown-assets/07.7.Operating systems and Accessibility API(s) they provide.jpg")

**An Accessibility API defines what ARIA role each HTML element maps to**. (That’s why they are called _Accessibility API Mappings_). The browser refers to the AAPI’s mappings to set the role of an HTML element in the accessibility tree.

The [HTML Accessibility API Mappings specification]("https://www.w3.org/TR/html-aam-1.0/") contains a list of all HTML elements and the roles they are mapped to, if any. For your day-to-day work, you will want to reference a more [developer-friendly list of role mappings](https://www.w3.org/TR/html-aria/#docconformance) in the ARIA in HTML specification.

If you explore the AAPI mappings, you’ll notice that some elements have role mappings and others don’t. (The ones that don’t may be excluded from the accessibility tree.) And some elements have role mappings that differ slightly across platforms and AAPIs. What this means is that **how your content is announced may differ by platform and screen reader and browser combination**. Different screen readers may sometimes announce elements differently. This isn’t a bug; it’s by design. When that happens, you don’t need to do anything to “fix” these announcements; and you certainly do not want to try to force your own announcements on them.

How an element is exposed and announced depends on the browser, platform and screen reader combination you’re using.

**Each browser produces a _unique_ accessibility tree** based on the code you write and the accessibility API that it’s generating the tree for.

![how AAPI works]("./markdown-assets/07.8.how AAPI Works.webp")

A modern browser typically implements support for one or multiple AAPIs on the platform that it runs on.

When the browser implements support for an Accessibility API, it refers to the accessibility mappings for that API, and generates a unique accessibility tree for that API based on the role mappings.

The steps to expose the content you create to a screen reader user look something like this:

1. You write some HTML (and CSS).
2. The browser (e.g. Safari) parses your code and creates a DOM tree. The DOM tree is painted into a visual UI that sighted users can interact with.
3. In parallel, the browser uses the AAMs for the AAPI of the platform it is on (e.g. NSAccessibility on macOS) to generate a unique accessibility tree.
4. The screen reader (e.g. VoiceOver on macOS) gets information about the elements on the page via the accessibility tree, and then announces that information to the user.

![How HTML and CSS map to DOM and Accessibility tree]("./markdown-assets/07.9.How HTML and CSS map to DOM and Accessibility tree.webp")

## What HTML elements are included in the accessibility tree?

We mentioned earlier that the accessibility tree is a subset of the DOM tree, because not all HTML elements are included in the accessibility tree.

For an element to be included in the accessibility tree, it needs to:

1. map to a meaningful role, and
2. not be hidden in a way that removes it from the accessibility tree.

Conversely, an element will be excluded from the accessibility tree if it:

1. is not mapped to a meaningful role, or
2. is explicitly removed from the accessibility tree using HTML, CSS, or ARIA.

So, once again, **how you write your HTML and CSS will determine how and if an element is included in the accessibility tree**, and, by extension, whether or not it is going to be accessible. Throughout the entire course, you will learn how the markup and styles you write affect the information included in the accessibility tree.

Most **semantic HTML elements come with roles and accessibility information baked in**. This means that when you use native HTML elements, you provide useful accessibility information that works across all platforms. This is one of the benefits of using semantic HTML, which we will take a very deep dive into in the next chapter. We will learn about what makes semantic HTML accessible, and how CSS and ARIA attributes play a role in modifying the element’s role mappings in the accessibility tree.
