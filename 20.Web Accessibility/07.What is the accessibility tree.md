# What is the accessibility tree?

When you write HTML and CSS, how do you know how your code is going to be exposed to assistive technologies like screen readers? How do you know what information screen readers are getting about your components? How do you know if you’re exposing the right information that the user needs to understand and navigate your page? What if a component is missing a critical piece of information that the user absolutely needs to understand and operate it?

It would be great if we had a way to inspect the accessibility information of our elements just like we can inspect the styles and behavior using the browser DevTools, right?

Well, we do have a way to do that. We can do that via the **accessibility tree.**

The accessibility tree is the structure that carries accessibility information about your page and exposes it to assistive technologies like screen readers. It **plays a key role in understanding just how accessible your work is. And understanding it is critical to creating accessible web content.**

In this chapter, you will learn everything you need to know about the accessibility tree and the information it carries. You will also learn **how to inspect the accessibility tree in the browser DevTools** to get important and practical insights into the accessibility of every element on the page. Using these insights, you can find and fix important accessibility issues that would otherwise create barriers to access for your users.

It all starts with your HTML markup, which the browser uses to generate the DOM tree.

## From HTML to the DOM tree

The DOM tree is a tree-style representation of all the page’s HTML elements and their relationships.

![From HTML to the DOM tree]("./markdown-assets/07.1.From HTML to the DOM tree.webp")

The markup we write defines parent-child relationships between the different elements that make up the page. So the browser parses the HTML and creates **a tree of objects** that captures the parent-child relationships defined in our markup.

**All the page’s HTML elements are represented in the DOM tree.** This includes the `<html>` root element, the `<head>`, `<body>`, `<div>`s, `<p>`s, `<h2>`s, and every other HTML element used on the page.

Combined with presentation styles provided in CSS, the DOM tree is then painted into a visual user interface (UI) that sighted users use to navigate and interact with the content. But not all users can see what’s on the screen.

![DOM tree to Visual UI]("./markdown-assets/07.2.From DOM tree to Visual UI.webp")

People who can’t see the screen need **an alternative representation of the page that describes the various elements** of the page to them. This alternative representation must contain **accessibility information about the elements of the page**.

Not _all_ HTML elements ‘carry’ information that is relevant to assistive technologies. There are a lot of elements that are not essential for the understanding of the page. So, modern browsers expose the accessibility information that is relevant in **a separate tree structure**. We refer to this tree as _the accessibility tree_.

## The accessibility tree

Like the DOM tree, the accessibility tree is **a tree of objects**. Each object represents an element on the page and contains **accessibility information** about that element. This information includes what the element is, its properties, and how it relates to other elements on the page.

![The accessibility tree]("./markdown-assets/07.3.The accessibility tree.webp")

The accessibility tree is a structure parallel to the DOM tree. “Parallel” does not necessarily mean there is a 1:1 match between the nodes of these two trees. The accessibility tree is typically **a subset of the DOM tree**, because (as we mentioned earlier) not all elements in the DOM carry information that is relevant to accessibility.

For example, `<div>`s and `<span>`s are “generic” elements which are not always exposed in the accessibility tree by default. They are not exposed because they don’t carry useful information (or meaningful semantics) that assistive technology users need to understand the page. There are many other HTML elements which are also generic. They too are often ignored in the accessibility tree, because they do not carry semantics important for accessibility. Other elements may not be reported in the accessibility tree because they have been explicitly hidden (using HTML, CSS, or ARIA).

The browser parses the HTML markup of a page and uses the **semantics as well** as the styles applied to an element to determine if it is important to accessibility. Elements that are important to understanding and navigating the page are exposed as objects in the accessibility tree. For example, the browser will include <button>s, <input>s, and other form controls, as well as headings, lists, landmarks, and other important UI components.

Unlike the DOM tree, **the accessibility tree is not painted into a visual UI**. Assistive technologies like screen readers use the information in the accessibility tree to understand and present interface elements to their users (using Text-to-Speech or a braille display, for example).
