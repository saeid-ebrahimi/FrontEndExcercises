Mistakes happen, and sometimes with the best of intentions in mind.

Some of the most common accessibility mistakes among beginners is misusing ARIA labelling attributes (or even the native HTML title attribute) with the intention of improving the user experience for screen reader users, but resulting in the complete opposite of that.

In this chapter, we will learn about the algorithm that determines how the various naming techniques that we learned about in [the previous chapter](https://practical-accessibility.today/chapters/accName-techniques/) work together. Or, to be more accurate, we will learn about how naming “conflicts” are resolved when more than one technique is used. With this information, you’ll not only know how to avoid common accessibility mistakes yourself, but you’ll be able to fix any such mistakes in your codebase(s) more conscientiously.

When the browser is translating the DOM into an [accessibility tree](https://practical-accessibility.today/chapters/the-accessibility-tree/), there is a priority for methods that the browser will use to determine the accessible name (and description) of an element in the tree.

## The Accessible Name and Description Computation algorithm

When more than one naming mechanism is used on an element, **the browser uses** [an algorithm](https://www.w3.org/TR/accname-1.1/#mapping_additional_nd_te) **called “Accessible Name and Description Computation” to determine which accessible name “wins”.** The Accessible Name and Description Computation algorithm is defined in the [“Accessible Name and Description Computation”](https://www.w3.org/TR/accname-1.1/) specification. The “tl;dr” of the algorithm looks something like this:

When the browser seeks to determine the accessible name of an element:

1. It checks whether the element has an `aria-labelledby` attribute. If it does, and if the ID in the attribute is a valid reference to an element on the page, it uses the referenced element’s computed text to provide the accessible name for the element.
2. Otherwise (if `aria-labelledby` is not present) it checks if the element has an `aria-label` attribute. If it does, it uses the value of the `aria-label` attribute as an accessible name.
3. Otherwise, and unless the element is [marked as presentational](https://practical-accessibility.today/chapters/hiding-techniques/#suppress-an-element%E2%80%99s-semantics-with-the-role-attribute%3A-presentation-and-none) using `role="presentation"` or `role="none"` (in which case the element [does not accept an accName anymore](https://www.w3.org/TR/wai-aria-1.1/#namefromauthor)), the browser checks if the element can get its name:
   1. from an HTML attribute (such as title or alt),
   2. from another element (such as `<label>` or `<legend>`),
   3. or from its contents.

What this means is that, **when determining the accessible name of an element, ARIA takes precedence over native HTML semantics.** If no ARIA attributes are used, the browser will “fall back” to native HTML methods. This is why we mentioned in the previous chapter that `aria-label` and `aria-labelledby` will override the element’s content when the browser computes the accName of the element. And this is also why it is important to understand what ARIA attributes do and what impact they have on the usability of a component.

But what happens when you provide two accessible names to an element using two native HTML methods? Or if you use two attributes that both contribute to the accName computation of the element? For example, if you have both a `title` and an alt on an image, which is an example of markup commonly generated by some Content Management Systems (CMS):

```html
<!-- Don’t do this. -->
<img
  src="..."
  alt="A long line of people at a supermarket, wearing masks and maintaining safe distance between them."
  title="A long line of people at a supermarket, wearing masks and maintaining safe distance between them." />
```

Or if you have a title set on a link:

```html
<!-- Don’t do this -->
<a href="/team/" title="Meet our team!">Team</a>
<!-- What is the accessible name of the link? -->
```

When you use two HTML methods (such as two attributes) that both contribute to the accName computation of the element, the browser also applies an order of priority to choose the accName from one of the methods used. And, in some cases, one of these attributes may be used as an accDesc for the element instead…

Here’s what the algorithm looks like for some common user interface controls and elements…

## Accessible name computations for common user interface controls and elements

In the case of an `<img>`, the order is:

1. Use `aria-labelledby`.
2. Otherwise, use `aria-label`.
3. Otherwise, use `alt`.
4. Otherwise, use `title`.
5. If none of the above yield a usable text string, there is no accessible name.

According to the algorithm, the `title` attribute is used to provide the accName of the `<img>` when the `alt` attribute is absent. But don’t rely on `title` to provide an accName for images because the `title` attribute is not a substitute for the alt attribute.

When the image is broken, browsers usually print out the value of the alt attribute in its place. This means that the image’s text description will be available within the context that it is used in, even if the image itself doesn’t appear. But the contents of `title` are not treated the same way by all browsers.

![Safari, Chrome and Firefox displaying two broken images. One of the broken images has an alt attribute set, and the other has a title attribute only.](/markdown-assets/23.1.image-with-alt.webp)
_Chrome and Safari display the contents of the alt and title attributes when the image doesn't appear. Firefox only prints the contents of the alt attribute._

When both an `alt` and a `title` attribute are used on an `<img>`, and with the absence of `aria-describedby` on it, the content of the `title` attribute should be announced as a description to the image. However, it is currently not consistently exposed as an accDesc across different browser and screen reader combinations. JAWS does not announce the contents of the `title` attribute as an accDesc to the image.

Furthermore, using both `title` and alt on an `<img>` can cause unnecessary duplicate announcements when both the `title` and the `alt` have the same value, which is a very common occurrence in CMS-generated code.

Generally, with all the [issues associated with using the `title` attribute](https://www.24a11y.com/2017/the-trials-and-tribulations-of-the-title-attribute/), it is best to avoid using it. Use alt to give the image an accName when it needs one. (We will talk more about when an image needs an accName in the [accessible images chapter](https://practical-accessibility.today/chapters/images/)). And when the image you’re using needs additional context or descriptions, wrap it in a `<figure>` and use the `<figure>`’s `<figcaption>` to provide it.

Speaking of `<figures>`…

When computing the accName for a `<figure>`, the steps are:

1. Use `aria-labelledby`.
2. Otherwise, use `aria-label`.
3. Otherwise, use `<figcaption>`.
4. Otherwise, use `title`.
5. If none of the above yield a usable text string, there is no accessible name.

These steps will [soon change](https://github.com/w3c/html-aam/pull/359) so that `<figcaption>` no longer contributes to the accName computation of the `<figure>`:

1. Use `aria-labelledby`.
2. Otherwise, use `aria-label`.
3. Otherwise, use `title`.
4. If none of the above yield a usable text string, there is no accessible name.

Instead of the `<figure>` being labelled by the `<figcaption>`, the relationship between them will change so that `<figcaption>` provides additional _details_ to the `<figure>`, similar to what `aria-details` establishes on an element. In other words, the contents of `<figcaption>` will become **additional information** related to the `<figure>`, as opposed to the `<figure>`'s accName. In effect, this is equivalent to this (associating the `<figcaption>` with the `<figure>` using `aria-labelledby`):

```html
<figure aria-labelledby="caption_id">
  ..
  <figcaption id="caption_id"></figcaption>
</figure>
```

changing to this (associating the `<figcaption>` with the `<figure>` using `aria-details`):

```html
<figure aria-details="caption_id">
  ..
  <figcaption id="caption_id"></figcaption>
</figure>
```

This is a welcome change. It allows for more practical uses of `<figure>` and `<figcaption>`. For example, you may place a video inside a `<figure>`, and provide the transcript of the video in its `<figcaption>`.

```html
<figure>
  <video
    src="../video.mp4"
    width="100%"
    controls></video>
  <figcaption>
    <!-- video transcript may go here -->
  </figcaption>
</figure>
```

If `<figcaption>` still provided an accName to the `<figure>`, the transcript would be flattened to a (probably very long) string of text and announced as the accName of the `<figure>`, which, as you can imagine, would not have been a good user experience.

In the case of an `<iframe>`, the accName computation order is:

1. Use `aria-labelledby`.
2. Otherwise, use `aria-label`.
3. Otherwise, use `title`.
4. If none of the above yield a usable text string, there is no accessible name.

We’ve already talked about using `title` to provide an accName to an `<iframe>` in [the previous chapter](https://practical-accessibility.today/chapters/accName-techniques/). And we mentioned that `title` is currently the most reliable method of providing an announced accessible name for an `<iframe>`.

```html
<!-- title is the currently most reliable method for providing an announced accName to an iframe -->
<iframe
  src=".."
  frameborder="0"
  title="[ frame accName ]"></iframe>
```

According to [tests shared by Steve Faulkner](https://html5accessibility.com/stuff/2021/08/26/named-and-framed/), when the accName of the `<iframe>` is provided using the `title` attribute, it was more likely to be announced by screen readers than when it was provided using ARIA. So, use `title` to provide an accName to your `<iframe>`s when they need one.

In the case of a `<fieldset>`, the order is:

1. Use `aria-labelledby`.
2. Otherwise, use `aria-label`.
3. Otherwise, use (the first) `<legend>`.
4. Otherwise, use `title`.
5. If none of the above yield a usable text string, there is no accessible name.

In the case of most of the common `<input>` elements (`type="[ text | password | email | url | tel | number | search ]`", `<select>` and `<textarea>` elements), the order is:

1. Use `aria-labelledby`.
2. Otherwise, use `aria-label`.
3. Otherwise, use associated `<label>` element(s). (If more than one `<label>` is associated, the values of the labels are concatenated by DOM order, delimited by spaces.)
4. Otherwise, use `title`.
5. Otherwise, use `placeholder`.
6. If none of the above yield a usable text string, there is no accessible name.

In the case of `<input type="[ button | submit | reset ]">`, the order is:

1. Use `aria-labelledby`.
2. Otherwise, use `aria-label`.
3. Otherwise, use associated `<label>` element(s). (If more than one `<label>` is associated, the values of the labels are concatenated by DOM order, delimited by spaces.)
4. Otherwise, use the `value` attribute.
5. For input `type=submit`: If previous steps do not yield a usable text string, the accName is a localized string of the word “submit”.
6. For input `type=reset`: If previous steps do not yield a usable text string, the accName is a localized string of the word “reset”.
7. Otherwise, use `title`.
8. If none of the above yield a usable text string, there is no accessible name.

For all of these three input types, if the value of the value attribute is not used as an accName to the input — for example, when `aria-labelledby` or `aria-label` is present, this value should be used as an accDesc to the input. For example, the accName of this `<input type="submit">` is “Submit” (because `aria-label` takes priority over value in the algorithm), and the value of the value attribute, “Send away”, will be used as an accDesc for the input:

```html
input type="Submit" value="Send away"
aria-label="Submit">
```

When value and `aria-label` have the same value, `aria-label` is redundant. On the other hand, if they have different values, this creates a mismatch between the visible label of the input (provided by the value attribute) and its name (provided in `aria-label`). This, in turn, creates a usability issue for assistive technology users like speech control users. Furthermore, in the case of this code example here, it creates a violation of [SC 2.5.3 Label in Name](https://www.w3.org/WAI/WCAG21/quickref/#label-in-name), because the text of the label (“Send away”) is not contained in the text of the input’s name. So be careful when multiple naming methods are present on an element, and how they impact the accessibility and usability of your components.

In the case of sectioning and grouping elements (like `<section>`, `<nav>`, `<header>`, etc.), the order is:

1. Use `aria-labelledby`.
2. Otherwise, use `aria-label`.
3. Otherwise, use `title`.
4. If none of the above yield a usable text string, there is no accessible name.

In the case of `<a>` (with `href`), the order is:

1. Use `aria-labelledby`.
2. Otherwise, use `aria-label`.
3. Otherwise, use element’s content.
4. Otherwise, use `title`.
5. If none of the above yield a usable text string, there is no accessible name.

According to the algorithm, just like when the `title` attribute is used on an image, when `title` is present on a link, it should be used as an accDesc for the link if the link gets its accName from one of the methods of higher priority. For example, the accDesc of this link should be “Opens in a new window”:

```html
<a
  href="#"
  target="_blank"
  title="Opens in a new window">
  The ARIA specification

  <svg
    width="32"
    height="32"
    viewBox="0 0 32 32"
    aria-hidden="true">
    <path
      d="M6 2v24h24v-24h-24zM28 24h-20v-20h20v20zM4 28v-21l-2-2v25h25l-2-2h-21z"
      fill="currentColor"></path>
    <path
      d="M11 8l5 5-6 6 3 3 6-6 5 5v-13z"
      fill="currentColor"></path>
  </svg>
</a>
```

But `title` is also currently not consistently announced as an accDesc when it is used on links. And, once again, with all the issues associated with it, it is best to avoid using it. Provide the accName of a link using the link’s content. And when the link requires a description (like if you want to indicate that it opens in a new window), I recommend using a visually-hidden text node inside the link as a text alternative to the icon (assuming of course that you are using an icon to visually indicate that the link opens in a new window).

```html
<a href="#" target="_blank">
  The ARIA specification

  <span class="visually-hidden"
    >(Opens in a new window)</span
  >
  <svg
    width="32"
    height="32"
    viewBox="0 0 32 32"
    aria-hidden="true">
    <path
      d="M6 2v24h24v-24h-24zM28 24h-20v-20h20v20zM4 28v-21l-2-2v25h25l-2-2h-21z"
      fill="currentColor"></path>
    <path
      d="M11 8l5 5-6 6 3 3 6-6 5 5v-13z"
      fill="currentColor"></path>
  </svg>
</a>
```

Even though `aria-describedby` and `aria-description`
would be the most appropriate way to provide this
description, they are not consistently announced
in all browser and screen reader combinations.
And, as we mentioned in the previous chapter,
whether or not an accDesc is announced depends on
the user’s mode of navigation, too. So if you want
to guarantee that the description is announced,
use a visually-hidden text node instead. This way
it will be announced as part of the accName of the
link. Always perform your own testing, and reach
for the most robust solution.
In the case of `<button>`, the order is:

1. Use `aria-labelledby`. Otherwise,
2. use `aria-label`.
3. Otherwise, use `<label>`.
4. Otherwise, use element’s content.
5. Otherwise, use `title`. If none of the above yield a usable text string, there is no accessible name.

You may have noticed something different in this last one. Did you
know that the `<button>`
is a [labelable element](https://www.w3.org/TR/2011/WD-html5-author-20110809/forms.html#category-label)? Labelable elements
are elements that can get their accessible
name from the `<label>` element using the for and `id` association.
Even though it’s not very common, the `<button>` element can, too, get its accessible name from a `<label>` element. So, this rare snippet of code
is actually valid:

```html
<label for="myButton">Click me</label>
<button id="myButton"></button>
```

In fact, you _may_ have already noticed this in previous chapters whenever we
inspected a button in the browser DevTools.
