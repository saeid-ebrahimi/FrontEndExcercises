There is more than one way you can provide an accessible name (accName) to elements that are allowed to have one — **either using native HTML, or with the help of ARIA attributes.**

As you’re going to learn in this chapter, there are at least three or four methods that you can use to provide an accName to most elements. Knowing and understanding these methods will allow you to choose the method that is most appropriate for your components.

Many automated accessibility auditing tools will warn you when an element is missing an accessible name. This is particularly true for interactive elements. Being knowledgeable of the various naming methods **and their order of priority** (which we will cover in [the next chapter](https://practical-accessibility.today/chapters/accName-computation/)) will allow you to quickly go through these warnings and fix them more easily.

At this point in the course, you already know that native HTML should almost always take priority over ARIA. So that’s what we’re going to start with: providing accNames using native HTML methods.

## Providing accessible names using HTML

How you write the HTML for a component will determine how the browser will get the accName of that component.

The accName can be derived:

- **from an element’s content,**
- **from an attribute,** or
- **from another element.**

### Using the element’s content

Some elements, such buttons and links, get their names from their content.

For example, the accessible name for this button is “Download PDF”:

```html
<button>Download PDF</button>
```

And the accessible name for this link is “Chia Seeds Pudding recipe”:

```html
<a
  href="https://www.eatingbirdfood.com/basic-chia-seed-pudding/"
  >Chia Seeds Pudding recipe</a
>
```

When the label of an interactive element is provided using its content, and unless that label is visually hidden, the label and the accName of the element will match (as is the case for the button and the link in this example), which makes the element more accessible and usable by someone navigating using speech control. This makes it the most ideal way to provide an accName to interactive elements that can get their name from their contents. We will learn more about using speech control to navigate content on the web in [another chapter.](https://practical-accessibility.today/chapters/label-in-name/)

If you use the DevTools to inspect how these elements are exposed in the accessibility tree, you’ll notice that Chrome indicates that the name is derived from the element’s `content`.

You will also notice that it shows you other sources that the name could have been derived from. These sources (or methods) are **listed in their order of priority.** These methods are what we are learning about in this chapter. And their order of priority is what we will learn about in the next chapter.

### CSS pseudo-content and the accessible name

When an element’s accessible name is derived from its content, most browsers will include any pseudo-content in the name.

So **if you add a string of text using CSS `::before` or `::after` pseudo-elements, this string of text is going to be included as part of the accessible name** in most browsers.

For example, the accessible name for this link is “Learn about accessibility on MDN (Opens in a new Window)”.

```html
<a
  href="https://developer.mozilla.org/en-US/docs/Web/Accessibility"
  target="_blank"
  >Learn about accessibility on MDN</a
>
```

```css
a[target="_blank"]::after {
  content: " (Opens in a new Window)";
  /* etc. */
}
```

So be careful when you use CSS pseudo-content to add decorative content to elements, as this content may end up being announced by a screen reader. If you’re using CSS pseudo-elements to add decorative icons or even emojis, for example, these icons and emojis may create weird accName announcements. Generally speaking, you want to be careful and considerate of screen reader users by using emojis judiciously. And when you do use them, make sure that the emoji’s alternative text does indeed describe the purpose you are using it for.

If you need to provide decorative icons to elements, **prefer using an inline `<svg>` instead.** SVG is the most flexible and adaptive way to create icons on the Web. If the icon is decorative, you can and should hide it from screen reader users using the `aria-hidden` attribute.

### Using another element

Some elements may get their accessible name from other elements. For example, a form input field gets its accessible name from a `<label>` element when the label is programmatically associated with it using the for and id attributes:

```html
<!-- the for attribute associates the label with the input, making sure it is used as an accessible name -->
<label for="email">Email address</label>
<input
  type="email"
  id="email"
  autocomplete="email" />
```

Without this programmatic association, the `<label>` element would not provide a name for the input, and the name would, therefore, not have one.

And this is a common mistake made on many websites today. For example, this input field has no accessible name:

```html
<label>Your name</label> <input type="text" />
```

While the input’s label will be visible, and a sighted user can associate it with the input using visual cues, a screen reader will not announce a name for the input because the label is not programmatically associated with it. So a screen reader user won’t know what information this field expects. This is also a violation of **Success Criterion 1.3.1 Info and Relationships (Level A)** which states that "_Information, structure, and relationships conveyed through presentation can be programmatically determined or are available in text._"

As you can probably guess by now, this very common markup pattern has the same problem:

```html
<span>Your name</span> <input type="text" />
```

In fact, the `<label>` in the previous example is, technically, no more useful than a `<span>`. If you remember from a [the HTML semantics chapter](https://practical-accessibility.today/chapters/html-semantics/), the `<label>` does not map to a meaningful role by default. It is only useful to assistive technology users when it is explicitly associated with a control using the for attribute.

The `<label>` element is not the only element that provides an accessible name for another element.

When the first child of a `<fieldset>` group is a `<legend>`, the browser uses the contents of the `<legend>` as an accName for the group:

```html
<!-- The group’s accName is "Shipping address" -->
<fieldset>
  <legend>Shipping address</legend>

  ...
</fieldset>
```

Similarly, the `<caption>` element provides an accessible name for its containing `<table>`.

### Using an attribute

Some HTML elements get their accessible name from an attribute. For example, the accessible name of some form controls such as `<input type="submit">` is derived from its value attribute. The accessible name of the input field in this example is “Send message”:

```html
<input type="submit" value="Send message" />
```

And the accessible name of an `<img>` is derived from its alt attribute. The accessible name of the image in this example is “A cat sleeping on a bed.”:

```html
<img
  src="./path/to/image.png"
  alt="A cat sleeping on a bed." />
```

We will learn all about providing accessible names to images in [the Accessible Images chapter.](https://practical-accessibility.today/chapters/images/)

#### The title attribute

There’s another attribute that can be used to provide an accessible name to most HTML elements: the title attribute. But you generally should not use the title attribute to provide accessible names to elements. The only exception to this is `<iframe>`s:

```html
<iframe
  src=".."
  frameborder="0"
  title="[ frame accName ]"></iframe>
```

title is currently [the most reliable method of providing an announced accessible name for an `<iframe>`.](https://html5accessibility.com/stuff/2021/08/26/named-and-framed/) And using title to provide an accessible name to `<iframe>`s is currently the only unproblematic use case for it.

Depending on how it is used, the title attribute has accessibility and usability issues. Accessibility engineer Scott O’Hara has documented these issues in an excellent and comprehensive article called [“The Trials and Tribulations of the Title Attribute”.](https://www.24a11y.com/2017/the-trials-and-tribulations-of-the-title-attribute/) If you want to learn about the current state of the title‘s accessibility support, want to know of a few instances where it actually may be useful, and generally want to get a better understanding of why this native HTML tooltip continually fails to live up to expectations, I highly recommend reading Scott’s article. The article was published in 2017, and even though it is still mostly relevant, you should perform your own testing in order to make sure that you’re getting (or not getting!) the results that you need across all relevant browser and screen reader combinations.

One of the main takeaways from Scott’s article is: **don’t use the `title` attribute to provide accessible names to elements when you can use other methods to do so**. Even the [HTML specification](https://html.spec.whatwg.org/multipage/dom.html#the-title-attribute) recommends against using the `title` attribute:

**Relying on the title attribute is currently discouraged as many user agents do not expose the attribute in an accessible manner as required by this specification (e.g., requiring a pointing device such as a mouse to cause a tooltip to appear, which excludes keyboard-only users and touch-only users, such as anyone with a modern phone or tablet).**

In his article, [Using the HTML title attribute](https://www.tpgi.com/using-the-html-title-attribute-updated/), Steve Faulkner also notes that _"If you want to hide content from mobile and tablet users as well as assistive tech users and keyboard only users, use the `title` attribute"_. In other words, `title` can create usability issues that you probably want to avoid in your work.

Since the `title` attribute is _not_ a recommended way to provide an accessible name to elements, we won’t be diving any deeper into its usage in this course.

## Providing accessible names using ARIA

**You almost always want to provide accessibility information using native HTMLwhen you can do that**. But there are instances when you may need to use ARIA attributes, either to:

- explicitly associate an element with another when there is no native HTML way to do so,
- use multiple elements as an accessible name for another, or
- fix accessible names in an existing codebase without changing the markup. For example, you want to provide accNames to elements that don’t have one, but you can’t do that by changing the markup of those elements.

There are two ARIA attributes that **can be used to provide or override an element’s accessible name:** `aria-labelledby` and `aria-label`.

### Using `aria-labelledby`

**The `aria-labelledby` attribute is used when the text you want to use as an accessible name is already present elsewhere on the page.**

aria-labelledby accepts one or more IDs referencing the element(s) that the browser should use to provide an accessible name to the element it is used on.

In the following example, the value of `aria-labelledby` is the ID of the heading that is used to label each of the navigation landmarks:

```html
<nav aria-labelledby="heading_ID">
  <h3 id="heading_ID">Categories</h3>
  ..
</nav>

<nav aria-labelledby="heading2_ID">
  <h3 id="heading2_ID">Find us elsewhere</h3>
  ..
</nav>
```

There is no native HTML way to expose a heading as an accessible name for a landmark region. So `aria-labelledby` can be used to fill this gap.

Just like you can use a heading to provide an accName to a region, you may also use other elements to provide accessible names. For example, you may use a button within a search facility to provide an accessible name to the input field within the same facility:

```html
<input
  type="search"
  aria-labelledby="search-btn" />
<button id="search-btn">Search</button>
```

Since both the button and the input serve a similar purpose within the facility, the button’s label does double duty as the accessible name for the input field. This markup has the advantage of being minimal and more maintainable, too. We will see more examples similar to this one where we will use aria-labelledby to create more maintainable and DRY (Don’t Repeat Yourself) code in upcoming chapters.

At this point it is worth mentioning that when aria-labelledby is used to provide an accessible name to an element, it takes the highest priority over all other naming techniques when the browser computes the accName of an element.

```html
<!-- Even though the <label> is associated with the input, the input's accName is still derived from the button because aria-labelledby takes priority -->
<label for="search-input"
  >Find something on this site...</label
>
<input
  type="search"
  id="search-input"
  aria-labelledby="search-btn" />
<button id="search-btn">Search</button>
```

We will learn all about the algorithm the browser uses to compute an element’s accessible name, as well as the order of priority for the different naming methods in [the next chapter.](https://practical-accessibility.today/chapters/accName-computation/)

### Using aria-label

You can also provide an accName to an element using the `aria-label` attribute.

The `aria-label` attribute is similar in effect to `aria-labelledby` in that it provides an accName for the element that it is used on. But unlike `aria-labelledby` which uses another element’s computed text as an accessible name, the `aria-label` attribute takes a string of text as a value, and this string becomes the accessible name for the element.

In the following example, the value of `aria-label` provides an accessible name for a button that doesn’t otherwise have one:

```html
<!-- This button os treated as empty; it gets its accName from the aria-label attribute; otherwise, it would not have one. -->
<button aria-label="Settings">
  <i></i>
</button>
```

`aria-label` has a lower priority in the accName computation algorithm than `aria-labelledby`. This means that the accName for this input field is "Full name”, not “Your name”:

```html
<!-- The accName for this input field is derived from the aria-lablledby attribute which takes priority over aria-label and other naming methods -->

<span id="name-label">Full Name</span>
<input
  type="text"
  aria-labelledby="name-label"
  aria-label="Your Name" />
```

**`aria-label` and `aria-labelledby` have similar behavior in screen readers and the Accessibility API, `but aria-label` should be reserved for when there is no visible text on the page to reference or when keeping track of id values would be too difficult.**
**— The [Using ARIA document](https://www.w3.org/TR/using-aria/#label-support)**

#### 1. aria-label does not translate well

The value of the `aria-label` attribute is not translated well by automated translation services. Most of these services currently overlook the content of ARIA attributes. This means that “content buried in `aria-label` [ and other ARIA attributes ] can end up being read to users in a language different than their own. The very thing we are adding to help screen reader users can be excluding them instead.”, as accessibility consultant Adrian Roselli says in his article [“aria-label Does Not Translate"](https://adrianroselli.com/2019/11/aria-label-does-not-translate.html).

Adrian’s article contains tests he conducted using the most relevant translation services and using the most popular browsers (Firefox, Chrome, and MSEdge). The results of those tests indicate that you should not rely on `aria-label` to provide an accName to your elements.

Whenever possible, provide accessible names using native HTML methods—such as the element’s content, or native HTML elements like the `<label>` element. This has the benefit of immediately supporting [SC 2.5.3 Label in Name (Level A)](https://www.w3.org/WAI/WCAG21/quickref/#label-in-name). For example, provide the accName for a button using the button’s content:

```html
<!-- The accName of the button is "Send Message", which matches its visible label and conforms to WCAG SC 2.5.3 Label in Name (Level A) -->
<button type="submit">Send Message</button>
```

If the element you’re providing an accessible name for does not have a visible label (as it the case for icon buttons, for example), you can use a visually-hidden text node (such as a `<span>`) inside the element as an accessible name. You can hide the text label visually either using the `visually-hidden` utility class, or the HTML hidden attribute.

```html
<button>
  <span class="visually-hidden"
    >Compose Message</span
  >
  <svg viewBox=".." aria-hidden="true">...</svg>
</button>

<!-- OR -->
<button aria-labelledby="btn-label">
  <span id="btn-label" hidden
    >Compose Message</span
  >
  <svg viewBox=".." aria-hidden="true">...</svg>
</button>
```

As we mentioned in the [hiding techniques chapter](https://practical-accessibility.today/chapters/hiding-techniques/), an element that is hidden using the hidden attribute can be used to provide an accName to another element when it is referenced using `aria-labelledby`.

One advantage to using the hidden attribute over the `visually-hidden` utility class is that the text label will remain visually-hidden even when your CSS is not used (such as in reader modes, for example). It also has the benefit of not adding an additional reading stop for someone using the screen reader’s virtual cursor. We will elaborate more on these points when we learn more about the various methods to provide an accessible name to an icon button in the [icon buttons chapter.](https://practical-accessibility.today/chapters/accessible-icon-buttons/)

#### 2. aria-label and aria-labelledby don’t work on every element

Just like other ARIA attributes, `aria-label` and `aria-labelledby` are permitted on some elements, but not on others.

We mentioned [in the previous chapter](https://practical-accessibility.today/chapters/accName/#not-all-elements-can-have-a-name) that some ARIA roles are Name Prohibited. This means that `aria-label` and `aria-labelledby` are not allowed on those elements.

```html
<!-- <div>s are name prohibited, so this is invalid. Don't do this -->
<div aria-label="some name"></div>
```

The `aria-label` and `aria-labelledby` attributes also [do not work consistently with all HTML elements](https://www.tpgi.com/short-note-on-aria-label-aria-labelledby-and-aria-describedby/). So, you want to make sure you’re using them on the right elements to make sure you get the result that you need.

The [Using ARIA document](https://www.w3.org/TR/using-aria/#practical-support-aria-label-aria-labelledby-and-aria-describedby) provides more detailed screen reader support for using `aria-label` and `aria-labelledby` on various types of elements that I recommend you check out for more information.

#### 3. `aria-label` and `aria-labelledby` will override the element’s content

`aria-labelledby` and `aria-label` have the highest priority in the accName computation of an element. This means that the accName provided by `aria-label` or `aria-labelledby` **will override the element’s content in the accName computation**. This has a dangerous side effect that many developers are not aware of.

For example, the accessible name for this link is exposed as “Please contact one of the event organizers for more information”. The content of the link provide the visible label for the link. But with `aria-label` present, the content is not used as an accName for the link. As a result, a sighted screen reader user interacting with the link will hear a name that does not match what they see on the screen. And when a speech control user wants to activate the link, they will speak a name that does not exist, which means that they will no longer be able to activate the link by speaking its name.

```html
<a
  href="https://...."
  aria-label="Please contact one of the event organizers for more information"
  >Rules of conduct</a
>
```

This is important to keep in mind because sometimes `aria-label` is misused to provide additional descriptions or instructions for an element, in which case the element’s accName is no longer exposed, and its purpose may no longer be understood, resulting a confusing and frustrating user experience.

Do not use `aria-label` to provide descriptions to elements.

## Providing accessible descriptions using ARIA

When you need to provide descriptive text for an element, you can use the `aria-describedby` attribute.

### Using the `aria-describedby` attribute

The `aria-describedby` attribute is similar to `aria-labelledby`, except that it is used to provide an accessible description (**accDesc**) to an element instead of an accName. It also accepts one or more IDs of elements that together provide an accDesc to the element it is used on.

```html
<label for="passw0rd">Password</label>
<input
  type="password"
  id="passw0rd"
  aria-describedby="passw0rd-description" />

<p id="passw0rd-description">
  You password should be at least 8 characters
  long and contain at least one special character.
</p>
```

As we mentioned in the previous chapter, accessible descriptions differ from accessible names in how they are announced by screen readers.

**The descriptive content referenced in aria-describedby is flattened to a string of text.** This string is then appended, as descriptive text, after the accessible name and role of an element have been announced by the screen reader.

If the description contains structured content such as links, lists, or even images, the semantics of these elements will be lost when the description is flattened to a string of text. Only the alt attribute of an image will be announced, and there will be no announcements made of any links within the descriptive content.

Here’s an example showing a password field hint which uses a structured list to indicate the password requirements. Notice how NVDA announces the contents of the descriptive text without relaying the presence of the list. I’m also using an `<img>` to add the icon for demonstration purposes. The alt-text of the image is “Instructions”. NVDA will announce the alt-text of the image, but not the role of the image.

![using accDesc](./markdown-assets/22.1.using-accDesc.mp4)

_In this video, I am using NVDA to demonstrate how descriptive content that contains structure and semantics is announced as a flat string of text by NVDA with Chrome on Windows._

Most importantly, **descriptions may not always be announced by screen readers** Depending on the screen reader and browser combination used, as well as the user’s mode of navigation, the description may still be missed. So do your best to ensure the descriptive content is always accessible by other means, and don’t rely on ARIA alone to expose it. Adrian Roselli has [thoroughly documented](https://adrianroselli.com/2022/04/accessible-description-exposure.html) _"how `aria-describedby` is exposed to users across 8 interaction methods, 7 operating systems, and 8 screen readers"_, including videos and a sample for you to test. I recommend you check his findings out and perform your own testing for the latest accDesc exposure details.

### Using the aria-description attribute

ARIA 1.3 defines a new attribute called `aria-description`. `aria-description` is not currently fully implemented in all browsers, so it is not ready for wide adoption yet.

The `aria-description` and `aria-describedby` properties have the same purpose: providing an accDesc to an element. But unlike `aria-describedby` that references one or more elements already available in the DOM, `aria-description` accepts a string of text as an accDesc for the element it is used on. For example, the accDesc of the link in the following example is “Opens in a new window”.

```html
<a
  href="#"
  target="_blank"
  aria-description="Opens in a new window">
  The ARIA specification

  <svg
    width="32"
    height="32"
    viewBox="0 0 32 32"
    aria-hidden="true">
    <path
      d="M6 2v24h24v-24h-24zM28 24h-20v-20h20v20zM4 28v-21l-2-2v25h25l-2-2h-21z"
      fill="currentColor"></path>
    <path
      d="M11 8l5 5-6 6 3 3 6-6 5 5v-13z"
      fill="currentColor"></path>
  </svg>
</a>
```

**If descriptive text is available in the DOM, use `aria-describedby` instead of `aria-description`.** This ensures that what the screen reader may announce matches what a sighted screen reader user sees on the screen.

Like descriptive content referenced by `aria-describedby`, the content of `aria-description` will typically be appended, as descriptive text, after the accessible name and role of an element have been announced by screen readers.

Like `aria-label`, `aria-description` may not translate well. So, use it with caution, and prefer providing descriptive text using aria-describedby whenever you can.
