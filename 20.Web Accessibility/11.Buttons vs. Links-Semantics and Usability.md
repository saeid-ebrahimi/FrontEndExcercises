What an element is determines how it can be used. Semantics convey what an element is, and therefore, how it can be used. And the semantics of a link and a button are not the same.

Links and buttons are both interactive elements, but that’s pretty much all they have in common. And yet they are frequently confused, misused, or used interchangeably – sometimes creating mild confusion, and other times completely breaking user expectations.

In this chapter, I want to clarify the difference between links and buttons, and why it is important. By the end of this chapter, you will be able to make a more informed decision about whether to use a link or a button for your components, as well as fix any possible inaccessible implementations in your current project(s).

And for those few instances where you may need to do so, we will cover requirements for accessibly enhancing links into buttons, as well as “disabling” links when needed.

Now, there’s a lot of information we could cover about links and buttons. In this chapter, we’ll focus on the difference between them from an accessibility standpoint. I have included links to articles from the Web community to dive deeper into other aspects of each if you’re keen to learn more.

## Buttons

![Buttons](./markdown-assets/11.1.Buttons.webp)

**Buttons trigger actions**. On the Web, they are used to trigger programmable actions on the page. Programmable actions are actions that require JavaScript to work. As such, **a button requires JavaScript to do something**—such as opening a dialog, changing sections of content on the page, changing content layout, and so on and so forth. The only exception to this statement is a button within a form, in which case the button may submit the form.

```html
<button class="dialog-trigger">
  Open Dialog
</button>
```

An HTML `<button>` has an implicit button role. It comes with semantics and behavior baked into it. All browsers provide implicit button keyboard support. This means that a button is, by default:

- **Focusable** (it will receive focus when the user tabs through the page with a keyboard). Being focusable means that you don’t need to add a tabindex="0" to your buttons), and
- **keyboard operable** — it can be activated using Space and Enter (Return) keys.
  Native HTML buttons **can also be disabled using the `disabled` attribute**:

```html
<button disabled>I am disabled</button>
```

Probably the most important characteristic of a button is that, unless it’s within a form,**it won’t do anything without JavaScript**. Buttons don’t have any inherent behavior. To make a button do something, you’ll need to implement its interactive behavior yourself using JavaScript.

And that’s pretty much it.

Links, on the other hand, are very different.

## Links

![Links](./markdown-assets/11.2.Links.webp)

While buttons perform actions, **links take you places**. That is the main differentiating factor between buttons and links.

_Technically,_ links can do much more than take you places. You can use a link to download a document:

```html
<a href="myfile.pdf" download
  >Download the book (PDF)</a
>
```

send an email via an email app:

```html
<a href="mailto:hello@sarasoueidan.com"
  >Send me an email</a
>
```

or even dial a phone number:

```html
<a href="tel:+1(555)5309">(555) 5309</a>
```

**What makes all of this possible is the href attribute**. The href attribute is what makes a link what it is — and quite literally so.

According to [the HTML living standard](https://html.spec.whatwg.org/multipage/text-level-semantics.html#the-a-element):

**If the `<a>` element has an href attribute, then it represents a hyperlink (a hypertext anchor) labeled by its contents.**

**If the `<a>` element has no href attribute, then the element represents a placeholder for where a link might otherwise have been placed, if it had been relevant, consisting of just the element’s contents.**

An `<a>` element has an implicit link role **only if it has an href attribute**. Anchors without href attributes have no ARIA role mappings, and are therefore not exposed in the accessibility tree.

```html
<!-- this anchor is exposed as a link in the accessibility tree -->
<a href="#">I have an implicit link role.</a>

<!-- this anchor is NOT a link and is not exposed in the accessibility tree -->
<a>I have no role mapping.</a>
```

In other words: An anchor without an href attribute is not a link.

```html
<a>I am not a link</a>
```

An anchor element without an href attribute is **not even focusable** in most browsers. It is removed from the tabbing order of the page, so a user navigating the page with a keyboard will not be able to focus on it. So, from now on, when we talk about links, we are referring to anchors that have an href attribute.

**The `href` attribute defines the destination of the link**. Depending on the value of the href attribute, a link may take you to a new page, or to an element or section within the same page:

```html
<!-- link to a page on sarasoueidan.com -->

<a href="https://sarasoueidan.com/blog/"
  >Sara’s blog</a
>

<!-- link to a section with an ID of "links" on the same page -->

<a href="#links">Links</a>
```

A link is, by default:

- **Focusable** (unless the href attribute is absent); so, just like buttons, you don’t need to add tabindex="0" to your link to make it tabbable)
- **Keyboard operable** — it fires on Enter (only)

There are other features that make links special:

- When you hover over a link, most browsers will show the value of the link’s href attribute in the status bar;
- You can right-click on the link to get a bunch of options for things to do with the link;
- A link can be opened in a new tab/browser window.

Most importantly, **links don’t require JavaScript to do what they do**. They are **inherently capable** of redirecting the user to other places. This ability comes built into them. You don’t need to utilize any JavaScript to make links do what they do.

## Can you disable links?

Unlike a button, **a link cannot be disabled using the HTML disabled attribute**. [According to the specification](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#concept-fe-disabled), the disabled attribute only works on form controls. But there is a way you can work your way around it (if necessary) for when you want to let the user know that they can go somewhere… just not yet — for example, if you have links to next steps in a multi-step form, but the user isn’t supposed to go to the next step before completing the current one.

Since the href attribute is what makes an anchor an interactive link, the anchor becomes non-interactive when you remove the href attribute. So if you want to disable a link, the first think you want to do is to remove the href attribute. This will strip away the link semantics, and the browser will no longer provide the link’s interactive behavior, so it can no longer be activated (by mouse, keyboard or other assistive technologies).

```html
<a class="link--disabled">Step 2</a>
```

That being said, when you remove the href attribute and it is no longer exposed as a link, screen reader users won’t know that it’s a (disabled) link anymore. If you inspect the link in the accessibility tree, you’ll see that it is not exposed as a link.

What we want to do is tell screen reader users that this is a disabled link (a link that is disabled). So we need to instate this semantic information using ARIA attributes.

role="link" will re-instate the link semantics on the anchor; and since the disabled attribute is not allowed on hyperlinks, we can convey the disabled state to screen reader users using the aria-disabled attribute:

```html
<a
  class="link--disabled"
  role="link"
  aria-disabled="true"
  >Step 2</a
>
```

This anchor element will now be announced as a disabled/dimmed link by screen readers, and the absence of the href attribute ensures that it cannot be activated. So, it is technically now a disabled link.

## Choosing between a link and a button

Considering the differences in semantics as well as in behavior between links and buttons, choosing one or the other depends on what exactly you are creating.

When you need to choose between a link and a button (outside the context of a form), it helps to ask yourself these questions:

- Does the element take the user to another page or a section within the page? If the URL changes when the element is clicked, then what you want is a link: `<a href=".."></a>.`
- Does the element change something on the current page (for example: does it change the layout, or open a dialog, or present them with a new view)? If the answer is yes, you probably need a button.
- Can you right-click the element to open it in a new Window? If not, then it’s probably not a link.
- Does the element do anything without JavaScript?

Since buttons require JavaScript to do something, a good rule of thumb is to consider if the element you’re creating can do anything without JavaScript. If the answer is no, then you probably want a button.

On the other hand, links are meant to work without JavaScript, and have a meaningful target defined in the href attribute. If the href is not meaningful (for example, if it’s just a `<a href="#">`), then you probably want to use a button.

```html
<!-- you *probably* want a button here -->
<a href="#">do something</a>
```

## Enhancing a link into a button

There are some legitimate use cases for when a link may be enhanced into a button. If you use progressive enhancement to enhance static content into interactive widgets, enhancing a link into a button is something you may find yourself doing every now and then.

By default, a link:

- has an implicit link role, and
- can be activated using the Enter key only.

Whereas a button:

- has a button role, and
- can be activated using the Enter and Space keys.

In order to turn a link into a button, you need to provide all the necessary accessibility information of a button, as well as implement the expected keyboard behavior of a button. This means that you will need to:

1. override the link semantics with button semantics using ARIA attributes (so that the link is exposed as a button via the accessibility tree),
2. prevent the default link behavior,
3. trigger an alternative action using JavaScript, and
4. implement the expected button keyboard behavior. The user must be able to activate the button using the Enter key as well as the Space key, while taking into consideration [the difference between how these two are fired](https://adrianroselli.com/2022/04/brief-note-on-buttons-enter-and-space.html) on a button.

## Instate button semantics onto the link

Using the ARIA role attribute, we you can expose a link as a button by giving it a button role:

```html
<a href="#" role="button">..</a>
```

When you do that, the browser will assign the button role to the link in the accessibility tree. This means that the link will be exposed as a button to screen readers.

As I mentioned before, we will take a deep dive into ARIA attributes in another chapter, but what you need to know at this point is that this is all the ARIA role attribute does. It does not add button behavior to the link. It does not actually make the link become a button. It only changes the role that the browser exposes about the element in the accessibility tree.

In order to make the link behave like a button, you’ll need to add the expected keyboard interactions of a button yourself.

## Trigger an action when the anchor is clicked

Using JavaScript, you can attach an event handler to the anchor so that it triggers an action when it is clicked:

```html
var btn =
document.querySelectorAll('a[role="button"]');
btn.addEventListener('click', doSomething);
function doSomething(e) { e.preventDefault();
alert('Chirp chirp!'); }
```

## Implement full keyboard functionality of a button

A link can be activated using the Enter key _by default_. The browser provides this functionality for the `<a href="">` element out of the box. And, as a bonus, when you attach an event handler to the click event, the browser will fire that handler when the link is activated using keyboard, too. This means that the anchor will now trigger its action when it is activated using the Enter key.

But a button should be operable using the Enter as well as the Space key. So, just like we attached an event handler on click, we will also want to attach an event handler so that it triggers the action when the Space key is pressed:

```html
btn.addEventListener("keydown", function(e) { if
(e.keyCode === 32) { doSomething(e); } });
```

This brings us to the interesting part: Did you know that the way the `Space` and `Enter` keys work on a button is not really the same?

Accessibility consultant Adrian Roselli has documented [how a native button fires when the `Space` and `Enter`](https://adrianroselli.com/2022/04/brief-note-on-buttons-enter-and-space.html) keys are used. He notes that:

`A native <button> fires on key down when that key is Enter. If you hold down the Enter key, it continues to fire for as long you hold Enter (or something crashes). A native <button> fires on key up when that key is Space. If you do not release the Space, and also press Tab to move away from the control, the control will not fire.`

In order to match the expected keyboard behavior for a button, you will need to adjust the anchor’s keyboard interaction so the user can activate it on key up when the Space key is pressed, and on key down when the Enter key is pressed:

```html
btn.addEventListener("keydown", function(e) { //
enter key if (e.keyCode === 13) { doSomething(e);
} }); btn.addEventListener("keyup", function(e) {
// space key if (e.keyCode === 32) {
doSomething(e); } });
```

So, you see, you have quite a bit of manual work to do in order to properly enhance a link into a button.

Using a link to perform button things is probably not something you want to do unless it is part of a thoughtfully-designed, progressively-enhanced strategy. We will see a practical use case for enhancing a link into a button in [another chapter](https://practical-accessibility.today/chapters/dropdown-navigation/), in which we enhance a simple site navigation into an interactive drop-down navigation.

If and when you do enhance a link into a button, remember that **not all assistive technologies get their accessibility information via the accessibility tree**. So even when you override the link’s implicit semantics and expose it as a button to screen readers, other ATs like Forced Colors modes will use the inherent semantics of the link to present it to the user. This means that even though the link is exposed as a button to screen readers, and even if you give it the visual affiances of a button, you’ll still need to provide additional styles that specifically target Forced Colors modes (such as Windows High Contrast Mode) to ensure that the link is also visually presented as a button in those environments. We will learn all about styling content for Forced Colors Modes in [another chapter](https://practical-accessibility.today/chapters/forced-colors-mode/).

## Outro

Buttons and links are two primitive and foundational HTML elements. While they are both interactive elements, they are different elements that serve a different purpose.

You know by now that **semantic information is vitally important to someone who isn’t using the screen**. As a responsible developer, your job is to ensure that the controls you’re building are understandable by the user, so that they know how to operate your application or navigate your website.

Using an element with the wrong semantics **breaks the user’s expectations of what will happen if they interact with that element**. It can also create confusion when the user tries to operate the element a certain way but can’t.

Much of the confusion with choosing links or buttons among developers comes from the fact that:

1. Either the developer doesn’t know the semantic difference between links and buttons and the impact those semantics have on the user experience, or
2. the design doesn’t clearly identify the purpose of a link or a button, so the developer is left to choose one over the other without enough context.

So the first step to create accessible web products is to understand HTML semantics, and their impact on the user experience, particularly for users of assistive technologies.

If you’re a designer, **consider defining interactive behavior in your design mockups or specifications.** When you’re designing a clickable element, ask yourself: what does this element do on the page? What happens when the user clicks/taps/presses this element? does it take the user to another page or section on the page? or does it perform an action on the page?

If the element behaves like a button, style it like a button. If the element is a link, avoid styling it to look like a button if you can. And make sure to annotate your designs so that developers know what it is exactly that they are implementing.
