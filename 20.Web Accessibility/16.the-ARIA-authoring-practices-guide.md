# The ARIA Authoring Practices Guide (is not a copy-paste cookbook)

One of the most frequently asked questions in the web community when it comes to ARIA is: how do I know which ARIA attributes I should use when I build a custom component or widget?

To be completely honest with you, the answer is: It depends. It depends on what you’re building. It depends on the context of what you’re building. And on your design and constraints, if you have any. It may even depend on how reliant your component can be on JavaScript!

The same component may have different accessibility requirements depending on how and where it is used. This is why even components from libraries that are promoted as being fully accessible, may not be as usable or accessible in every context they are used in. Most components will often need to be modified to fit into the context they are used in.

I’d be lying to you if I said that there is a place you can go to to find everything you need for building a custom HTML component. Because that place doesn’t exist yet. However, there is a W3C website that provides a little of what you would look for in a situation like this. This website is called the ARIA Authoring Practices Guide (APG). The APG is a very useful but also commonly misunderstood and mis-used accessibility reference…

## What is the ARIA Authoring Practices Guide (APG)?

The ARIA Authoring Practices Guide is, well, **a guide about using ARIA to create custom user interface components or widgets.** It contains demonstrations for common UI patterns that either have no native representation in HTML at all, or that are recreations of HTML patterns using ARIA. For example, there is a Tabs component, which has no HTML element to represent it. And there is a custom checkbox component, which provides guidance on creating a custom checkbox using ARIA.

The APG’s primary purpose is **to demonstrate how to use ARIA to implement (common to complex) widgets in accordance with the ARIA specification.** This is why the demos all use ARIA rather than their native HTML counterparts (when they are available).

Each pattern in the guide has a dedicated page that demonstrates how the pattern _might_ be implemented. Each page contains:

- the list of ARIA attributes used on the pattern,
- expected keyboard interactions for the pattern,
- the markup used to create the pattern, and
- links to CSS and JavaScript files, as well as
- a functional live demo.

There is a currently a total of **29 patterns** demonstrated in the APG. And while this collection may look like a great pattern library to incorporate in your work, you should probably not just go ahead and do that. Because these patterns come with a caveat.

## What is the ARIA Authoring Practices Guide not?

You see, **the APG is not a specification**. It is, therefore, non-normative. It does not list requirements that you must follow in your work. You may implement a switch component for example or an accordion widget using markup that is different from the markup suggested in the APG. (I do that!) In fact, in some cases, it may even be better if you don’t follow the patterns provided in the APG. It really comes down to what you’re building.

### The APG patterns are not production-ready

Many of the pattern implementations provided in the APG are not production-ready. Not all of them have been fully tested (especially not across mobile devices). Some of them are straight-forward and ready for production; others are not. The purpose of these patterns is **to demonstrate how to interpret and implement the features of the ARIA specification**; so part of their purpose is **for testing** to see where implementation gaps may be (in browsers or Assistive Technologies (AT)).

From the guide:

**Testing assistive technology interoperability is essential before using code from this guide in production. Because the purpose of this guide is to illustrate appropriate use of ARIA 1.2 as defined in the ARIA specification, the design patterns, reference examples, and sample code intentionally do not describe and implement coding techniques for working around problems caused by gaps in support for ARIA 1.2 in browsers and assistive technologies. It is thus advisable to test implementations thoroughly with each browser and assistive technology combination that is relevant within a target audience.**

There is no guidance within APG on how to work around bugs or implementation gaps (nor is there meant to be). It is on you to perform your own testing and remediate any issues before using any of the code examples in production.

The guide goes on to say that:

**Currently, this guide does not indicate which examples are compatible with mobile browsers or touch interfaces. While some of the examples include specific features that enhance mobile and touch support, some ARIA features are not supported in any mobile browser. In addition, there is not yet a standardized approach for providing touch interactions that work across mobile browsers.**

Most pattern example pages even include a heads-up at the beginning of the page that states that:

**Note: This is an illustrative example of one way of using ARIA that conforms with the ARIA specification.**

- **There may be support gaps in some browser and assistive technology combinations, especially for mobile/touch devices. Testing code based on this example with assistive technologies is essential before considering use in production systems. […]**
- **Robust accessibility can be further optimized by choosing implementation patterns that maximize use of semantic HTML and heeding the warning that No ARIA is better than Bad ARIA.**

The last point is basically a reminder that **using native HTML elements is almost always better than rolling out your own custom implementations** if the native elements provide all the accessibility you need.

In addition to reaching for built-in HTML elements, it may sometimes be useful to modify a design pattern to make it more usable. For example, when you’re providing a list of options for the user to choose from, using a group of radio buttons instead of a custom select dropdown if possible is a more robust solution. Under-engineered solutions are typically more robust and more usable.

## So, what does all of this mean?

There is a common misconception among developers that if you’ve followed and implemented the ARIA Authoring Practices then your patterns are accessible as a result.

I see too many developers referencing and re-using the APG patterns in their projects without testing them, because they assume that just because this is a website associated with the W3C then it must be a standard that they can follow to guarantee that their work is accessible. But the APG is not a standard. It is not even an official W3C recommendation.

Some of the patterns in the APG are straight-forward and ready for production. Others are not. The purpose of the patterns is to demonstrate how to interpret and implement the features of the ARIA specification… so part of their purpose is actually for testing to see where implementation gaps may be (in browsers or AT).

As such, **the APG is not a copy-paste cookbook**. You shouldn’t use the code examples it provides as-is. You will need to do your own testing and possibly make modifications to the code to make sure it works as expected for all your users. And, as we mentioned before, the components provided in the APG may need to be customized to fit into the context in which you are using them.

For example, if you use an accordion component and that accordion uses headings (with buttons) to mark up the accordion toggles, you want to make sure that the heading levels in the accordion fit well into the heading structure of the page, and adjust them if they don’t.

But this isn’t to say that the APG isn’t useful. **The APG is a useful reference if you know what you’re getting from it, and what you’re not.** I like to refer to the patterns it includes for when I need **a starting point** for my own implementations. Sometimes it provides all the guidance I need for simple patterns, and sometimes I need to do more research and consult other accessibility folks in the community for further insight; and I always, always try to get assistive technology users to test the patterns I am working on, and provide feedback on them.

The APG is an important resource and this course would be incomplete (and I would probably get a lot of questions) if I didn’t talk about it. But it is also my responsibility to shed the light and emphasize — as much as I can — that **this guide is just a guide**, and that it is not perfect.

The workflow that I recommend for creating custom ARIA widgets includes one or more of the following strategies:

1. Reaching for HTML elements whenever possible.
2. Simplifying the interaction patterns whenever you can.
3. Knowing your ARIA attributes.
4. Consulting the APG for custom widgets.
5. Researching other implementations of a pattern.
6. Testing your implementation across ATs and with AT users.

## Outro

As we mentioned in previous chapters, you can only confidently say that something works by observing people succeed in using it. Use the tools and resources that are available to you, but **use them as they are intended**.
