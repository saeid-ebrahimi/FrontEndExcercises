# The ARIA Authoring Practices Guide (is not a copy-paste cookbook)

One of the most frequently asked questions in the web community when it comes to ARIA is: how do I know which ARIA attributes I should use when I build a custom component or widget?

To be completely honest with you, the answer is: It depends. It depends on what you’re building. It depends on the context of what you’re building. And on your design and constraints, if you have any. It may even depend on how reliant your component can be on JavaScript!

The same component may have different accessibility requirements depending on how and where it is used. This is why even components from libraries that are promoted as being fully accessible, may not be as usable or accessible in every context they are used in. Most components will often need to be modified to fit into the context they are used in.

I’d be lying to you if I said that there is a place you can go to to find everything you need for building a custom HTML component. Because that place doesn’t exist yet. However, there is a W3C website that provides a little of what you would look for in a situation like this. This website is called the ARIA Authoring Practices Guide (APG). The APG is a very useful but also commonly misunderstood and mis-used accessibility reference…

## What is the ARIA Authoring Practices Guide (APG)?

The ARIA Authoring Practices Guide is, well, **a guide about using ARIA to create custom user interface components or widgets.** It contains demonstrations for common UI patterns that either have no native representation in HTML at all, or that are recreations of HTML patterns using ARIA. For example, there is a Tabs component, which has no HTML element to represent it. And there is a custom checkbox component, which provides guidance on creating a custom checkbox using ARIA.

The APG’s primary purpose is **to demonstrate how to use ARIA to implement (common to complex) widgets in accordance with the ARIA specification.** This is why the demos all use ARIA rather than their native HTML counterparts (when they are available).

Each pattern in the guide has a dedicated page that demonstrates how the pattern _might_ be implemented. Each page contains:

- the list of ARIA attributes used on the pattern,
- expected keyboard interactions for the pattern,
- the markup used to create the pattern, and
- links to CSS and JavaScript files, as well as
- a functional live demo.

There is a currently a total of **29 patterns** demonstrated in the APG. And while this collection may look like a great pattern library to incorporate in your work, you should probably not just go ahead and do that. Because these patterns come with a caveat.

## What is the ARIA Authoring Practices Guide not?

You see, **the APG is not a specification**. It is, therefore, non-normative. It does not list requirements that you must follow in your work. You may implement a switch component for example or an accordion widget using markup that is different from the markup suggested in the APG. (I do that!) In fact, in some cases, it may even be better if you don’t follow the patterns provided in the APG. It really comes down to what you’re building.
