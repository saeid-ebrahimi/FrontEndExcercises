Navigation is the art and science of determining the position of a ship, plane or other vehicle, and guiding it to a specific destination. And navigation on websites serves a very similar purpose.

In this chapter, we’re going to build a simple, minimal site navigation. We’re going to [enhance this navigation into a fly-out navigation](https://practical-accessibility.today/chapters/drop-down-navigation/) (a.k.a. drop-down navigation) and then [into an off-canvas navigation](https://practical-accessibility.today/chapters/off-canvas-navigation/) in other chapters. But for the purposes of this chapter, we’re going to keep it minimal.

The objective of this chapter is to demonstrate how semantic information is carried from HTML elements, through the accessibility tree, to screen readers, and how this information helps a screen reader user understand and navigate page content similar to how a sighted user can.

**Semantic information is vitally important to someone who isn’t using the screen.** So we’re going to be thinking about the information that’s available to sighted users, and making it available semantically via HTML elements.

## Choosing the right HTML elements

When you create a new component, the first thing you want to do is to **choose an HTML element that describes what it is you are creating to someone who can’t see it**, so that assistive technologies can expose these important semantics.

Whether you’re creating a site-wide navigation, breadcrumbs, a secondary navigation in a sidebar or footer, or even a table of contents, the semantics shared between all of these components is that they are a form of navigation. They help the user determine their current position on the website, as well as go to other locations. So, we need to choose an HTML element that has navigation semantics built into it.

The HTML element that represents a navigation component is the `<nav>` element, so that’s what we’re going to start with:

```html
<nav></nav>
```

The `<nav>` element has **an implicit navigation role**. If you inspect the accessibility tree, you can see that the `<nav>` element has already been exposed to screen readers using its implicit role.

`navigation` is a type of **landmark region**. Using the navigation landmark not only helps users identify a navigation as what it is, but it enables them to move between the navigation and other key landmarks on the page more efficiently (which is something we will discuss in more detail in the [next chapter](https://practical-accessibility.today/chapters/landmark-regions/)). If you use a `<div>`, for example, to create your navigation, it will not be exposed as a landmark region anymore.

By definition, a navigation provides links to specific pages on the website, or even links to sections of content within the same page (depending on the type of navigation you’re creating). So, our navigation component will contain a collection of links that take people to specific pages on the website:

```html
<nav aria-label="Site">
  <a href="/products/">Products</a>
  <a href="/team/">Team</a>
  <a href="/press/">Press</a>
</nav>
```

Links have an implicit role of `link`. By using links — not buttons, for example — a screen reader user knows what to expect when they activate one of these links. They know that activating the link will take them places. Some screen reader users may have their screen readers configured to announce the URL of the link so that they get an idea of where the link takes them to.

Since we’re using these semantic elements the way they are intended, the browser makes the semantic information that we just provided available in the accessibility tree. The `<nav>` element tells a screen reader that this is a navigation. And the links indicate that they will take the user places.

Using a screen reader, we can see that our navigation is exposed as a landmark region, so the user can quickly navigate to it using a shortcut.

If we had used a `<div>` to create our navigation, it would not have been exposed as one, and the user wouldn’t be able to navigate to it as efficiently. Additionally, the links, while accessible, will lack **a context that identifies their purpose on the page.**

So, we now have our navigation landmark with a collection of links inside of it.

Technically, this could be enough. But there’s a way we can dramatically improve the experience for assistive technology users even further.

## Creating structure inside the navigation

The purpose of semantics is to convey meaning **as well as structure** — both affordances that are visually conveyed to sighted users by means of design elements like layout and spacing. Our goal is to convey the same affordances to blind users via our markup.

Looking at the navigation, a sighted user can perceive how many items the list contains. We can create semantic structure in our markup that conveys the same information to a blind user by grouping our links into a list:

```html
<nav>
  <ul>
    <a href="/products/">Products</a>
    <a href="/team/">Team</a>
    <a href="/press/">Press</a>
  </ul>
</nav>
```

Lists provide information about **how many elements there are in the navigation, as well as their order;** and this relationship can be carried over to screen reader users.

So now when the user navigates to one of these links, instead of just announcing the link and navigation landmark, the screen reader can announce the order of this link within the list, as well as the total number of list items, and by proxy, the number of links available. Both the order of the link within the list as well as the number of items in the list are pieces of information available for sighted users, and now we’ve made them available to screen reader users too.

All the information that is announced by the screen reader was made available to the user by our choice of semantic elements.

Another benefit to using a list is that now the user has an additional way to get to the site navigation faster.

With the structure we have created, the user can:

- navigate to the navigation using landmarks;
- see the navigation links within the list of links exposed by the screen reader;
- navigate to the navigation using list shortcuts;

… in addition to their other navigation methods.

The order of the links relative to each other doesn’t really matter in our navigation, so using an unordered list is appropriate.

But if we were building a breadcrumb navigation, for example, where the order of the links matters, we would have chosen an ordered list to semantically represent the list instead:

```html
<nav>
  <ol>
    <li><a href="..">Home</a></li>
    <li><a href="..">Products</a></li>
    <li><a href="..">Sustainable Kitchen</a></li>
  </ol>
</nav>
```

Since both `<ul>` and `<ol>` map to the same role (list), choosing one over the other may not affect how the list items are announced by a screen reader. But we still want to make a habit of choosing the element that semantically represents what we are creating.

## Labelling multiple navigations on the page

Both breadcrumb and site-wide navigations have the same semantics and are marked up using the same element: the `<nav>` element. And they will both show up as ‘Navigation’ landmarks in something like the VoiceOver Web Rotor.

Sighted users are able to differentiate between these two navigations using the visual cues in the visual user interface. A blind user will need semantic information that identifies them for them.

You can identify each navigation by giving it a unique label. A unique label identifies the purpose of each navigation.

By labelling the main site navigation “Site”, and the breadcrumbs navigation “Breadcrumbs”, a blind screen reader user can now identify the two types of navigation and their purpose:

```html
<nav aria-label="Site">
  <ul>
    <a href="/products/">Products</a>
    <a href="/team/">Team</a>
    <a href="/press/">Press</a>
  </ul>
</nav>

<!-- ... -->

<nav aria-label="Breadcrumbs">
  <ol>
    <li><a href="..">Home</a></li>
    <li><a href="..">Products</a></li>
    <li><a href="..">Sustainable Kitchen</a></li>
  </ol>
</nav>
```

Instead of using aria-label, you can create a visually-hidden label in the markup and associate it with the nav instead:

```html
<nav aria-labelledby="site-nav-label">
  <span id="site-nav-label" hidden>Site</span>
  <ul>
    <a href="/products/">Products</a>
    <a href="/team/">Team</a>
    <a href="/press/">Press</a>
  </ul>
</nav>

<!-- ... -->

<nav aria-labelledby="breadcrumbs-label">
  <span id="breadcrumbs-label" hidden
    >Breadcrumbs</span
  >
  <ol>
    <li><a href="..">Home</a></li>
    <li><a href="..">Products</a></li>
    <li><a href="..">Sustainable Kitchen</a></li>
  </ol>
</nav>
```

Using the VoiceOver Web rotor, you can see both navigations listed and labelled so the user can jump straight to the one that they want.

Note that you don’t want to use the word “navigation” in the navigation’s label, otherwise you will end up with duplicate announcements of the word “Navigation”.

We will learn more about providing accessible labels to landmark regions as well as to all elements that need them in [another chapter.](https://practical-accessibility.today/chapters/accNames-and-descriptions/)

## Styling with CSS

Semantics provide the first and arguably most important layer of information. But we usually want to customize how our content looks on the page using CSS.

As we mentioned in [the HTML semantics chapter](https://practical-accessibility.today/chapters/html-semantics/), depending on the browser and screen reader used, **CSS may sometimes affect how semantic elements are exposed and announced by screen readers.**

When we change the layout of the navigation list (`<ul>, <ol>`) using Flexbox or Grid, for example, we typically also remove the default list markers using `list-style: none`.

```css
/_ In some versions of Safari,
this
  declaration
  will
  remove
  list
  semantics
  _/
  ul {
  list-style: none;
}
```

Some older versions of Safari on macOS will remove list semantics when you remove the default list markers. When that happens, VoiceOver no longer announces the list, nor the number of items in the navigation.

Newer versions of Safari (including Safari 16+) will remove list semantics unless the list is contained within a navigation landmark. In other words, if you use a meaningless `<div>` to create your navigation instead of the `<nav>` element, not only will the navigation not be exposed as a navigation landmark region anymore, but VoiceOver will also remove list semantics and all the useful information that comes bundled with it.

We do want to expose how many items there are in the navigation because it is helpful.

Since we are using the `<nav>` element, the list semantics are preserved and announced as expected in the latest versions of Safari.

For older versions of Safari, we can re-instate the list semantics using the role attribute, by explicitly adding the `list` role to it:

```html
<nav aria-labelledby="site-nav-label">
  <span id="site-nav-label" hidden>Site</span>
  <ul role="list">
    <a href="/products/">Products</a>
    <a href="/team/">Team</a>
    <a href="/press/">Press</a>
  </ul>
</nav>
```

This ensures that the list and the number of items in the navigation are properly exposed to your users. Then you can go forth and safely style the list any way you want in your CSS knowing that it will retain its semantics.

## Conveying state

There’s one piece of information that is missing from our navigation that we haven’t yet conveyed semantically: **state**.

We mentioned before that navigation is called navigation because it helps guide people to specific destinations _as well as_ **determine their current position**.

A link identifying the current page is visually styled to indicate that it is the current page. Using semantics in our markup, _we want to convey stateful information_ similar to what sighted users can see. _But there is no native HTML attribute that indicates or identifies the current element within a set of elements._

We can convey state in HTML using [ARIA attributes](https://practical-accessibility.today/chapters/aria/). ARIA attributes provide stateful and semantic information where HTML semantics fall short. We will learn all about ARIA attributes in [another chapter](https://practical-accessibility.today/chapters/aria/). For the purposes of this chapter, suffice it to say that the `aria-current` attribute can be used on a link to indicate that this is the “current” link in a set of links.

To indicate that an item is the current item within a navigation, you can either use the true value or the page value. The difference between the two is that, when you use page, a screen reader will say “link, current page” instead of just “link, current”, which is more appropriate for our purpose.

```html
<nav aria-labelledby="site-nav-label">
  <span id="site-nav-label" hidden>Site</span>
  <ul role="list">
    <a href="/products/" aria-current="page"
      >Products</a
    >
    <a href="/team/">Team</a>
    <a href="/press/">Press</a>
  </ul>
</nav>
```

We can now use the aria-current attribute as a styling hook in our CSS! This is one of my favorite ways to use ARIA attributes in my work.

Instead of using a dedicated current class name, we can hook into the ARIA attribute to style the current page’s link. The benefit of doing that is that it helps enforce accessibility on our links, by making sure the current link is only styled when it has an aria-current attribute set on it:

```css
a[aria-current="page"] {
  /* current link styles */
}
```

## Outro

Stateful information is but one piece of accessibility information that can be supplemented using ARIA attributes.

Semantics should provide three main pieces of information:

- the role of an element, which describes what the element is/does
- the name of an element, which identifies the element and its purpose
- the state of the element (where applicable), which determines the current state of the element.

Collectively, this information tells the user what they’re interacting with and allows them to choose what to do next in terms of interacting with the content.

Many HTML elements come with built-in accessibility information by default. But there are instances where you may need to create custom interactive components that have no equivalent semantics in HTML (such as grids, Tabs, etc.).

When HTML semantics fall short, we can supplement the accessibility information using ARIA attributes. And in the next chapter, we’re going to take a deep dive into what ARIA attributes are, and everything you need to know about using them responsibly in your own projects.
