In an ideal world, users will know exactly what to fill in each form field, and they will do so without making mistakes. But there are many reasons why a user may either provide improperly-formatted information in a field, or leave one blank. When that happens, a programmatic error usually occurs, and **we should help them understand not only what went wrong, but also how to fix it.**

Form validation is the process in which we check the validity of the information provided by the user. And if the information is either missing or incorrectly formatted, we provide feedback to let the user know what went wrong, and how to fix it.

How we handle form validation can either make or break a user’s experience with a form. To improve the user experience, it is on us to:

1. Make sure the user knows that a field is required (or mandatory);
2. Provide clear instructions to help them understand input requirements;
3. Clearly notify them when there are improperly-formatted or missing information in the form;
4. Clearly indicate _which_ fields are invalid; and
5. provide clear error messages to guide them how to correct them.

In this and the next chapter, we will cover the programmatic implementation of these steps of form validation as they relate to assistive technology users in general, and screen reader users in particular.

## Client-side vs. server-side validation

Form validation can be done on the client side (i.e. in the browser) or on the server side.

Validating on the client side essentially means checking the validity of the information entered by the user **before sending the data to the server**. This can be done either during or after the user has finished typing in a field, or when the user submits the form.

Validation on form submit happens by intercepting the form submission and notifying the user of the presence of incorrect information so that they can fix it before the data is submitted to the server.

Client-side validation is an initial check and an important feature of good user experience; by catching invalid data on the client side, the user can fix it straight away. If it gets to the server and is then rejected, a noticeable delay may be caused by a round trip to the server and then back to the browser. So, client-side validation is better for improving the perceived performance of the page.

Because it happens in the browser, client-side validation is relatively easy to bypass. Almost anyone who knows how to open the browser DevTools can also probably bypass client-side validation, especially if you use native HTML constraint validation (which we will talk about in the next section). (I’ve done this before, so I know others might, too. 🤭) This is why validation should also be done on the server side, too. **Client-side validation is not a substitute for server-side validation.**

## Native HTML5 constraint validation

Every form field has a purpose and expects a certain type and format of input. For example, an email field requires a valid email address; there might be requirements for the password field such as the use of special characters or a minimum number of characters; and a text field might have a limit on how many characters can be entered.

HTML provides a bunch of **attributes** that you can use to define constraints on the type of input expected in certain form fields. Modern browsers can use these attributes to check if the input provided by the user matches the constraints you’ve defined.

- the `required` attribute indicates that a form field is mandatory;

```html
<!-- indicates that the field is mandatory -->
<input type="email" required />
```

If the user tries to submit the form without providing the required information, the browser will prevent form submission and display a message indicating that the field is required (unless you tell it not to. We’ll talk more about this shortly.)

- the `pattern` attribute accepts a JavaScript regular expression and defines the pattern that the entered data needs to match to be considered valid. For example, it can be used to define the pattern that the email input field needs to match to be considered valid.

```html
<!-- defines the pattern that the input needs to match to be valid -->
<input
  type="email"
  required
  pattern="^[\w]{1,}[\w.+-]{0,}@[\w-]{1,}([.][a-zA-Z]{2,}|[.][\w-]{2,}[.][a-zA-Z]{2,})$" />
```

If the email value the user provides does not match the pattern you defined in the `pattern` attribute, the browser will display an error message indicating that it doesn’t. (We’ll talk more about this message in a minute.)

- the type attribute specifies whether the data needs to be a number, an email address, or some other specific preset type.

```html
<!-- indicates that the input type is number -->
<input type="url" name="website" />
```

- the `minlength` and `maxlength` attributes specify the minimum and maximum length of the text value allowed in an input field;

```html
<!-- specifies the min and max allowed length of the entered input -->
<input type="text" maxlength="20" minlength="2" />
```

- the `min` and `max` attributes specify the minimum and maximum values allowed for numerical inputs;

```html
<!-- specifies the min and max allowed number value -->
<input type="number" min="0" step="5" max="100" />
```

If the data entered in a form field follows the constraints specified by these attributes, it is considered valid. If not, it is considered invalid, and the browser may prevent form submission and display an error message where it is needed. This error message is browser-dependent, and it comes with default browser styles that are not customizable with CSS.

When you use the native validation, you can use CSS selectors such as [the `:invalid` state selector](https://developer.mozilla.org/en-US/docs/Web/CSS/:invalid) to style fields when they fail to validate:

```css
input:invalid {
  background-color: ivory;
  border: 2px solid red;
  ...;
}
```

Other similar validation pseudo-classes are `:required`, `:optional`, and `:valid`.

Built-in form validation is convenient, to say the least, but unfortunately it is does not come without its issues. In some cases, it degrades the usability of the form and the user’s ability to fix invalid fields.

In most browsers, **the default messages don’t indicate what the expected pattern is**. So the browser may repeatedly tell the user that the field is invalid and that they should provide the correct format, **without telling them what that format is.**

For example, here is how Firefox displays the error message associated with a required email input field when the form is submitted: first when the field is left empty, then when I entered an address that does not match the expected pattern that I defined in the `pattern` attribute.

[The error message does not provide any useful information as to what the expected format is. It does not communicate what needs to be done to fix it. It only says to “match the requested format” without indicating what that format is.](/markdown-assets/32.1.pattern-usage.mp4)

If you use the `pattern` attribute, **you cannot rely on the browser to show the user what the pattern is**. _You_ need to let the user know what the expected input format is in text, either as part of the field’s accessible name, or in the field’s description. (More on this in another section.) If you don’t, you could fail [SC 3.3.2 Labels or Instructions (Level A)](https://www.w3.org/WAI/WCAG21/quickref/?showtechniques=331#labels-or-instructions):

> **Labels or instructions are provided when content requires user input.**

…and [SC 3.3.3 Error Suggestion (Level AA)](https://www.w3.org/WAI/WCAG21/quickref/?showtechniques=331#error-suggestion):

> **If an input error is automatically detected and suggestions for correction are known, then the suggestions are provided to the user, unless it would jeopardize the security or purpose of the content.**

Default browser error messages may be difficult to see by someone who has low vision and needs to use page zoom to use the page. As Adrian Roselli notes in his article [“Avoid default form validation”](https://adrianroselli.com/2019/02/avoid-default-field-validation.html), most default browser error messages don’t respect page zoom — they don’t zoom with the rest of the page’s content.

Furthermore, the error messages in Chrome are currently non-persistent — they disappear after a short timeout (which is currently 5 seconds). This means that the information that the user needs to correct their information may disappear right when they need it.

For all of these reasons, you should **avoid native form validation** and roll your own validation instead. For that, you’re going to need to use JavaScript.

## Suppressing the default form validation

Before you roll your own validation, you want to suppress the browser’s default error messages in order to replace them with your own custom ones.

You can turn off the browser’s automatic form validation by adding [the novalidate attribute](https://html.spec.whatwg.org/multipage/forms.html#element-attrdef-form-novalidate) to the containing `<form>` element:

```html
<!-- setting the novalidate attribute on the form stops the form from showing its own error message bubbles, and allows you to instead display the custom error messages in the DOM in some manner of your own choosing -->
<form action=".." novalidate></form>
```

You can also turn it off by using the `formnovalidate` attribute on the form submission button (or `<input type="submit">`):

```html
<form action="..">
  ..
  <!-- “don't validate the form when I’m pressed” -->
  <button type="submit" formnovalidate>
    Submit
  </button>
</form>

<!-- or -->

<form action="..">
  ..
  <!-- “don't validate the form when I’m pressed” -->
  <input
    type="submit"
    formnovalidate
    value="Submit" />
</form>
```

Now you’re in control of validating the form using JavaScript, and providing and displaying your own custom error messages.

Using the JavaScript [Constraint Validation API](https://developer.mozilla.org/en-US/docs/Learn/Forms/Form_validation), you can customize and enhance the native form validation. It offers methods to override when validation occurs, create custom error messages, as well as provide custom validation that’s not possible using HTML alone.

You can also roll your own custom JavaScript API instead, or use one of the many available JavaScript form validation libraries (as long as they are accessible, of course).

Implementing custom form validation using JavaScript is outside the scope of this course. We will only focus on the markup required to make the form validation accessible.

In the following sections, we’ll learn about the HTML and ARIA attributes that you will need to convey input requirements and validity to your users.

## Identifying required fields

The best kind of form validation is the preventive kind. Your first goal should be to prevent errors from occurring by helping the user know **what fields need to be filled in,** and clearly indicating any constraints on the information they must enter if there are any.

> **“The best form validation practice? “Avoid the need for throwing any error. Be preventive.”**
>
> — [A Definite Guide to Sensible Form Validations](https://html.form.guide/best-practices/form-validations-definitive-guide/)

[SC 3.3.2 Labels or Instructions (Level A)](https://www.w3.org/WAI/WCAG22/quickref/#labels-or-instructions) states that "_Labels or instructions are provided when content requires user input._"

Labels and instructions in a form help minimize user error, and improves the usability of the form.

One way to meet this criterion is to **clearly indicate which form fields are required** so that users know what information they need to provide before submitting the form.

### A quick note on marking required versus optional fields

Marking required and optional fields in a form is a controversial area of form usability. There are many opinions when it comes to indicating which fields are required versus which ones are optional.

The general consensus, though, is that **required fields should always be clearly indicated.**

Ideally, the form should only contain required fields.\*\* If a form has a lot of optional fields, it means that the user is being asked for a lot of unnecessary information.

That being said, many forms _do_ contain optional fields, especially checkout form on e-commerce websites, for example.

If a form contains optional fields, clearly mark those as well. A [usability study conducted by the Baymard Institute](https://baymard.com/blog/required-optional-form-fields) found that _"failing to explicitly mark both required and optional fields [in checkout forms] leads to unnecessary validation errors, user confusion over which fields they must complete, a slower checkout process, and even abandonments."_

As the Nielsen Norman group states in [an article about marking required fields in forms,](https://www.nngroup.com/articles/required-fields/) marking the optional fields is helps lighten the user’s cognitive load, as they no longer need to look around to infer that a field is optional based on the other fields being marked as required.

You may come across other opinions online. For example, some professionals suggest that you should only mark optional fields because the form should ideally only contain mandatory fields, so you’d mark the ones that are not mandatory in this case because the assumption is that all the fields are otherwise required. I can imagine this approach also having its own usability issues, depending on where this approach is used.

There definitely ins’t one size that fits all. What works for one form may not work for another. And only usability tests will help you decide which approach is better for your form(s).

The least user error-prone approach is likely going to be to indicate both required and optional fields. So, for simplicity’s sake, we’re going to continue this chapter with the assumption that both required and optional fields should be marked.

## Indicating fields are required to all users

You should indicate that a field is required (or optional) to _all_ users.

The most inclusive and robust approach to indicating that a field is required is to indicate it **in text** in the input’s `<label>`:

```html
<label for="email"
  >Your email address (Required)</label
>
<input type="email" id="email" />
```

This ensures that _all_ users will know that the field is required, regardless of what assistive technology they use. Sighted users will see the word “Required”, and it is also available to screen reader users as it will be announced as part of the field’s accessible name.

Similarly, mark optional fields using the word “Optional” in the field’s label:

```html
<label for="job-title"
  >Job title (Optional)</label
>
<input type="text" id="job-title" />
```

### Quick note on using asterisks to indicate required fields

It is a common practice to use an asterisk (usually a red one) in a field’s label to visually indicate that a field is required.

**Avoid using asterisks to mark fields as required.** Not all users know what the asterisk stands for. If you do use as asterisk, include instructions at the top of the form to let the user know that required fields are marked with an asterisk:

```html
<p>
  Required fields are marked with an asterisk
  (<abbr class="req" title="required">*</abbr>).
</p>
```

But **avoid using asterisks to mark required fields if you can.** Even if you include instructions that indicate what the asterisk means, some users might miss them, especially since many users tend to skip over instructions and not read them. Furthermore, as designer [Adam Silver](https://adamsilver.io/) says: _"good design doesn’t need to be explained."_

Additionally, screen readers typically announce the asterisk as “star”.

If you have to use an asterisk instead of the word “Required”, the [W3C suggests](https://www.w3.org/WAI/WCAG21/Techniques/html/H90.html) that you may use [the `<abbr>` element](https://html.spec.whatwg.org/multipage/text-level-semantics.html#the-abbr-element) to style the asterisk so that it is more visible. The `<abbr>` element represents an abbreviation or acronym. The optional `title` attribute can provide an expansion for the abbreviation or acronym when a full expansion is not present. You can use that to provide the meaning of the asterisk:

```html
<p>
  Required fields are marked with an asterisk
  (<abbr class="req" title="required">*</abbr>).
</p>

<form>
  <label for="firstname">
    First name
    <abbr class="req" title="required">*</abbr>:
  </label>
  <input
    type="text"
    name="firstname"
    id="firstname" />

  ...
</form>
```

Note that the W3C example also notes that you must still define the meaning of the asterisk at the start of the form, even if you use this markup pattern.

However, this still doesn’t prevent the asterisk from being announced as a “Star” in most screen readers. If anything, the announcement now becomes even more verbose in VoiceOver on macOS, for example, which now announces the “Required“ value in the `title` attribute, the “Star” inside the element, and also exposes the `<abbr>` element as a group.

Avoid using an asterisk to indicate required fields. (Yes, I realize I’ve said this three times by now.) If you do use one and you want to avoid announcing it as a “star” by screen readers, you can hide it from screen readers using `aria-hidden="true"`:

```html
<label for="email"
  >Your email<span aria-hidden="true"
    >*</span
  ></label
>
```

When you do that, you need to make sure that you **programmatically indicate that the field is required** to screen reader users using HTML or ARIA.

## Programmatically marking fields as required

You can programmatically indicate that a field is required to screen reader users using the HTML `required` attribute, or its equivalent ARIA attribute `aria-required`:

```html
<label for="email"
  >Your email<span aria-hidden="true"
    >*</span
  ></label
>
<input type="email" id="email" required />

<!-- or -->

<label for="email"
  >Your email<span aria-hidden="true"
    >*</span
  ></label
>
<input
  type="email"
  id="email"
  aria-required="true" />
```

Both `aria-required` and `required` will **only programmatically** indicate that a field is required. This means that not _all_ users will know that it is required.

If you do use either of these attributes to indicate a field is required, you should still explicitly indicate that it is required **in text**—for example, either using instructions above the form, or using the word “Required” in the field’s label.

Using text is particularly important when an error occurs. [SC 3.3.1 Error Identification (Level A)](https://www.w3.org/WAI/WCAG21/quickref/?showtechniques=331#error-identification) states that _"if an input error is automatically detected, the item that is in error is identified and the error is described to the user in text."_ One of the benefits of using text is that it helps people with cognitive, language, and learning disabilities who have difficulty understanding the meaning represented by icons and other visual cues.

### Should you use `aria-required` or `required`?

The general rule of thumb is to reach for native HTML elements and attributes and only reaching for ARIA when there are no native equivalents for the semantics you need. But there’s more to consider when choosing `aria-required` over the `required` attribute.

Both `aria-required` and `required` have very good support in the most relevant browser and screen reader pairings. If all you want to do is programmatically indicate that a field is required, you can technically use either of the attributes.

```html
<!-- Both implementations will announce a field as required by screen readers -->

<!-- 1 -->
<label for="email"
  >Your email address<span aria-hidden="true"
    >*</span
  ></label
>
<input type="email" id="email" required />

<!-- 2 -->
<label for="email"
  >Your email address<span aria-hidden="true"
    >*</span
  ></label
>
<input
  type="email"
  id="email"
  aria-required="true" />
```

The main deciding factor for choosing between `aria-required` and `required` currently has more to do with **usability**.

When you use the HTML `required` attribute, some browsers and screen reader pairings will announce the required field as **invalid by default, even before the user starts typing anything in it,** which is not a favorable user experience. So, I personally prefer to use `aria-required` instead of the `required` attribute. You can prevent this behavior (or at least make it consistent across screen readers) using the `aria-invalid` attribute. We’ll talk more about this in another section.

### Indicating a group of fields is required

Most form fields can be programmatically marked as `required` using the required and/or `aria-required` attributes. But what if you have **a group** of, say, radio buttons, for example, and the user is required to choose one of the options provided in the group? how do you indicate that?

If you use the required (or `aria-required`) attribute on each radio button, a screen reader may announce each of the options as required, **making it sound like all of the options must be selected.** That’s not right.

What you want to do instead is to **mark their containing group** as required. This will indicate that the user is expected to select an option in this group.

We’ve learned in [the previous chapter](https://practical-accessibility.today/chapters/forms/) that the `<fieldset>` element is the most appropriate semantic element to group and label related fields together:

```html
<fieldset>
  <legend>Choose a T-shirt color:</legend>

  <label for="black"
    ><input
      type="radio"
      name="color"
      value="black"
      id="black" />Black</label
  >
  <label for="purple"
    ><input
      type="radio"
      name="color"
      value="purple"
      id="purple" />Purple</label
  >
  <label for="green"
    ><input
      type="radio"
      name="color"
      value="green"
      id="green" />Green</label
  >
</fieldset>
```

So, theoretically, we would be able to programmatically mark the `<fieldset>` as required using the required attribute:

```html
<!-- This markup is NOT VALID -->
<fieldset required>
  <legend>Choose a T-shirt color:</legend>

  <label for="black"
    ><input
      type="radio"
      name="color"
      value="black"
      id="black" />Black</label
  >
  <label for="purple"
    ><input
      type="radio"
      name="color"
      value="purple"
      id="purple" />Purple</label
  >
  <label for="green"
    ><input
      type="radio"
      name="color"
      value="green"
      id="green" />Green</label
  >
</fieldset>
```

However, **this markup is not valid** because the `required` attribute is not allowed on the `<fieldset>` element. Neither is `aria-required`.

Even though some browser and screen reader pairings _may_ announce a `<fieldset>` as required using this markup, not all screen readers will.

This markup is invalid, and it actually makes sense that it is, because a `<fieldset>` maps to the group role, and the group role represents a [document structure](https://www.w3.org/TR/wai-aria-1.1/#document_structure_roles) element. Document structure elements are not interactive. Whereas a required element has to be an interactive element (that can accept user input), right? So, the required property doesn’t make sense on a structural element.

Okay so then what’s the alternative?

When an element or a feature is not available in HTML, we reach for ARIA to fill the gap.

Since the `<fieldset>`’s built-in role doesn’t allow us to use the required and `aria-required` attributes, we can override it with an ARIA role that does.

The ARIA role that represents a group of radio buttons is `radiogroup`.

The radiogroup role [supports](https://www.w3.org/TR/wai-aria-1.1/#radiogroup) the `aria-required` attribute, but the `required` attribute is not allowed on an element with a `radiogroup` role. This means that when we override the `<fieldset>`’s role with the radiogroup role, we need to programmatically mark the group as required using the `aria-required` attribute:

```html
<!-- this is valid 👍🏻 -->
<fieldset role="radiogroup" aria-required="true">
  ...
</fieldset>

<!-- this is not ⚠️ valid -->
<fieldset role="radiogroup" required>
  ...
</fieldset>
```

Something to keep in mind here is that the radiogroup role represents "_a group of radio buttons […] that can only have a single entry checked at any one time._" This means that you cannot use it to mark a group of, say, checkboxes, for example, as required. If you need to indicate that a group of checkboxes (or other form fields) is required, you may indicate it in the group’s accessible name.

```html
<!-- example borrowed from https://www.w3.org/WAI/WCAG21/Techniques/html/H90.html -->
<fieldset>
  <legend>
    I am interested in the following (Please
    select at least one):
  </legend>

  <input
    type="checkbox"
    id="photo"
    name="interests"
    value="ph" />
  <label for="photo">Photography</label>

  <input
    type="checkbox"
    id="watercol"
    name="interests"
    checked="checked"
    value="wa" />
  <label for="watercol">Watercolor</label>

  <input
    type="checkbox"
    id="acrylic"
    name="interests"
    checked="checked"
    value="ac" />
  <label for="acrylic">Acrylic</label>
  ...
</fieldset>
```

## Providing helpful hints and instructions (where they are needed)

In addition to marking mandatory fields as required, you also want to assist the user in filling the required information in _correctly_ by **providing helpful instructions where they are needed.**

As we mentioned before, some form fields (such as email fields, phone numbers, etc.) expect a specific data format, and it is important that the user knows what that format is in order for them to fill the correct information and prevent errors from occurring. This is part of the error prevention strategy we mentioned earlier.

Providing examples of expected data formats help users with cognitive, language and learning disabilities to enter information correctly.

Form instructions [can be provided as part of the field’s label](https://www.tpgi.com/simple-inline-error-message-pattern/) if they short.

```html
<label for="passw0rd">
  Password (Required)
  <span
    >Your password should be at least 6 characters
    long</span
  >
  <input type="password" id="passw0rd" />
</label>
```

As we mentioned in the previous chapter, accessible names should be short and succinct, so longer hints and instructions (including error messages) should ideally be provided as additional descriptions outside the label, and programmatically associated with the input using `aria-describedby`. For example:

```html
<label for="passw0rd">Create a password</label>
<input
  type="password"
  id="passw0rd"
  aria-describedby="passw0rd-requirements" />
<div id="passw0rd-requirements">
  <p>You password should be:</p>
  <ul>
    <li>
      At least 12 characters — the more
      characters, the better.
    </li>
    <li>
      A mixture of both uppercase and lowercase
      letters.
    </li>
    <li>A mixture of letters and numbers.</li>
    <li>
      Including at least one special character,
      e.g., ! @ # ? ]
    </li>
  </ul>
</div>
```

As we mentioned in [the accessible names and descriptions chapter](https://practical-accessibility.today/chapters/accName/), instructions associated with the input using `aria-describedby` are appended, as descriptive text, after the accessible name and role of an element have been announced by screen readers.

The description is presented to the user as a flat string of text. If the description contains structured content such as lists or links (such as our example here), the structure and semantics are lost when the content is announced to the user.

Screen readers will typically pause after the name and role of the control have been announced, and before they announce the accessible description. This creates a more elegant experience than announcing both the name and description as one piece of text.

## Indicating a field is invalid

So we’ve indicated that a field is required, and we’ve indicated _what_ format each field expects.

If/When the user leaves a required field empty or enters information that does not match the expected format, an “input error” occurs.

The WCAG 2.0 definition of “input error” says that it is “information provided by the user that is not accepted” by the system. Some examples of information that is not accepted include information that is required but omitted by the user and information that is provided by the user but that falls outside the required data format or allowed values.

When that happens, **you want to clearly indicate which fields are invalid, and why.** This is a requirement to conform with [SC 3.3.1 Error Identification (Level A)](https://www.w3.org/WAI/WCAG21/quickref/#error-identification), which states that:

> **If an input error is automatically detected, the item that is in error is identified and the error is described to the user in text.**

**There is no native HTML attribute to indicate that a field is invalid.** So this is another one of those instances where ARIA attributes are used to polyfill state information missing in HTML.

[The `aria-invalid` attribute](https://w3c.github.io/aria/#aria-invalid) is used to **programmatically indicate** that a field is invalid, so that screen readers announce it to their users.

When a field is invalid, set `aria-invalid` to `true` on that field:

```html
<!-- this field is invalid -->
<input
  type="email"
  aria-required="true"
  aria-invalid="true" />
```

The ARIA specification states that _"if the user has not attempted to submit the form, authors SHOULD NOT set the `aria-invalid` attribute on required widgets simply because the user has not yet entered data."_ So, when the field is no longer invalid, consider removing the `aria-invalid` completely instead of settings its value to `false`.

```html
<!-- when the field is valid, consider removing aria-invalid completely -->
<input type="email" aria-required="true" />
```

You can use the `aria-invalid` attribute as a styling hook in your CSS to tie the visual styles of the invalid field to its semantic state:

```css
/* style invalid fields */
input[aria-invalid="true"] {
  border: 2px solid red;
  ...;
}
```

We mentioned earlier that using the `required` attribute causes some browser and screen reader pairings to announce a field as invalid by default. You can avoid this behavior by using the `aria-required` attribute instead. If you choose to use the `required` attribute, you will want to make sure the state of the field is announced consistently across screen readers.

If the field is required but you don’t want it to be announced as invalid by default, set the `aria-invalid` attribute to `false`:

```html
<!-- field is required but not invalid yet; prevent screen readers from announcing it as invalid by default -->
<input
  type="text"
  required
  aria-invalid="false" />
```

If and when the field is required and invalid, set aria-invalid to true:

```html
<!-- field is required and invalid -->
<input type="text" required aria-invalid="true" />
```

When a field is invalid, it is visually styled to indicate that it is invalid, typically using the color red.

People who have certain types of color blindness will be unable to determine the input’s state based on color alone. You should not use color alone to convey information, otherwise you would be in violation of [SC 1.4.1 Use of Color (Level A).](https://www.w3.org/WAI/WCAG21/quickref/#use-of-color) A visual indicator such as an icon can help identify invalid fields to sighted users.

## Providing error messages for invalid fields

When a field is invalid, you should **communicate to the user _why_ it is invalid in text, and how to correct it.**

To do that, you should **associate invalid fields with inline error messages** that inform the user what is required to correct them. In doing so, you conform to WCAG [**SC 3.3.3 Error Suggestion (Level AA),**](https://www.w3.org/WAI/WCAG21/quickref/#error-suggestion) which states that:

> **If an input error is automatically detected and suggestions for correction are known, then the suggestions are provided to the user, unless it would jeopardize the security or purpose of the content.**

Providing information about how to correct input errors allows users who have learning disabilities to fill in a form successfully. Users who are blind or have impaired vision can more easily understand the nature of the input error and how to correct it. And people with motion impairment can reduce the number of times they need to change an input value.

To associate error messages with their fields, you can use the `aria-describedby` attribute, similar to how you associate instructions with their fields. When a field is invalid, use `aria-describedby` to point to the ID of the element that contains the error message:

```html
<input
  type="email"
  aria-required="true"
  aria-invalid="true"
  aria-describedby="email_error" />
<p id="email_error">
  Please provide an email address.
</p>
```

ARIA provides an attribute called [aria-errormessage](https://w3c.github.io/aria/#aria-errormessage) which associates an error message with its form field.

`aria-errormessage` identifies the element (or elements) that provides an error message for an element. Unlike `aria-describedby` which associates a description with a field, `aria-errormessage` associates an error message with it.

```html
<input
  type="email"
  aria-required="true"
  aria-invalid="true"
  aria-errormessage="email_error" />
<p id="email_error">
  Please provide an email address.
</p>
```

One of the most important differences between aria-describedby and aria-errormessage is that **`aria-errormessage` _must_ be used in conjunction with `aria-invalid`**, and the error message should **only be announced when `aria-invalid` is `true`**. The error message must otherwise be hidden from all users.

> **When the value of an object is not valid, aria-invalid is set to true, which indicates that the message contained by elements referenced by aria-errormessage is pertinent.**
>
> — [**The ARIA specification**](https://w3c.github.io/aria/#aria-errormessage)

`aria-errormessage` therefore enforces the relationship between error message announcements and the fields being marked as invalid.

[Support for aria-errormessage](https://a11ysupport.io/tech/aria/aria-errormessage_attribute) is currently inconsistent across browsers and screen readers. Accessibility consultant Adrian Roselli has documented how a handful of browser and screen reader pairings announce error messages associated with form fields using `aria-describedby`, `aria-errormessage`, as well as using ARIA live regions (which we talk more about in the next chapter) in an article titled [”Exposing Field Errors”](https://adrianroselli.com/2023/04/exposing-field-errors.html). I recommend checking his test results out to get a clearer idea of how each of them behaves and what that means to error messages you implement for your own projects.

### Using an SVG icon to distinguish error messages from field descriptions

Error messages should be distinctive so visual focus is immediately drawn to them.

Error messages are usually styled using the color red to communicate urgency and importance. Since color should not be the only means of conveying information, you should add a visual indicator such as an icon (or even plain text!) to indicate that a description associated with a field is in fact an error message.

If you want to use an icon to indicate an error, embed the icon in the error message using an inline SVG. When you do, you can utilize the CSS currentColor keyword to match the icon’s color to the color of the text in the error message.

For example, in this code snippet, the SVG shape’s fill color is set to currentColor. This means that the shape will use the SVG’s color property value, which it inherits from its container (the error message):

```html
<p id="email_error">
  <svg
    width="1em"
    height="1em"
    viewBox="0 0 24 24"
    class="error-icon">
    <path
      d="M12.984 12.984v-6h-1.969v6h1.969zM12.984 17.016v-2.016h-1.969v2.016h1.969zM12 2.016q4.125 0 7.055 2.93t2.93 7.055-2.93 7.055-7.055 2.93-7.055-2.93-2.93-7.055 2.93-7.055 7.055-2.93z"
      fill="currentColor"></path>
  </svg>

  This email address does not exist.
</p>
```

```css
.error-icon {
  color: inherit;
}
```

Now the icon will always inherit the color of the text it sits next to.

This technique has the benefit of ensuring that the icon remains accessible in Forced Colors Mode, which we’re going to learn all about in [another chapter.](https://practical-accessibility.today/chapters/forced-colors-mode/)

Since the icon in error messages communicates meaningful information — an input error, it should have a text alternative that communicates the same purpose to screen reader users. You can give the SVG an accessible name using the `aria-label` attribute:

```html
<p id="email_error">
  <svg
    aria-label="Error:"
    width="1em"
    height="1em"
    viewBox="0 0 24 24"
    class="error-icon">
    <path
      d="M12.984 12.984v-6h-1.969v6h1.969zM12.984 17.016v-2.016h-1.969v2.016h1.969zM12 2.016q4.125 0 7.055 2.93t2.93 7.055-2.93 7.055-7.055 2.93-7.055-2.93-2.93-7.055 2.93-7.055 7.055-2.93z"
      fill="currentColor"></path>
  </svg>

  This email address does not exist.
</p>
```

Alternatively, you could hide the SVG from screen readers altogether and provide a visually-hidden, screen reader-only text label instead:

```html
<p id="email_error">
  <svg
    aria-hidden="true"
    width="1em"
    height="1em"
    viewBox="0 0 24 24"
    class="error-icon">
    <path
      d="M12.984 12.984v-6h-1.969v6h1.969zM12.984 17.016v-2.016h-1.969v2.016h1.969zM12 2.016q4.125 0 7.055 2.93t2.93 7.055-2.93 7.055-7.055 2.93-7.055-2.93-2.93-7.055 2.93-7.055 7.055-2.93z"
      fill="currentColor"></path>
  </svg>
  <span class="visually-hidden">Error: </span>
  This email address does not exist.
</p>
```

## Outro

One of the most critical pieces of form validation is deciding when and how to validate the form and display error messages. Should you validate the form and display error messages after the user submits the form? or while they are typing into a field? What if the submit button is disabled? Should you disable submit buttons? (Hint: the answer is No.) And how do you ensure the user knows which fields are invalid without them having to go through every single field?

We will discuss these questions and more in the second part of this chapter.
