In [a previous chapter,](https://practical-accessibility.today/chapters/navigation/) we created a simple site navigation to demonstrate the importance and benefits of using semantic HTML to create a comparable experience for blind screen reader users. In this chapter, we’re going to enhance that flat navigation into a drop-down navigation.

We’re going to discuss not only one but three different markup patterns that you could use to create such a navigation, depending on your requirements or restrictions, if you have any.

This chapter builds upon everything we covered in [the Disclosure Widget chapter.](https://practical-accessibility.today/chapters/disclosure-widget/) So, if you haven’t watched (or read) that chapter yet, I suggest you pause here and go do so before continuing with this one.

I’m also going to assume that you watched [the HTML semantics chapter,](https://practical-accessibility.today/chapters/html-semantics/) [the buttons vs links chapter,](https://practical-accessibility.today/chapters/buttons-vs-links/) and [the accessible icon buttons](https://practical-accessibility.today/chapters/accessible-icon-buttons/) chapter. We will be basing some of our implementation decisions in this chapter on concepts and techniques covered in those chapters.

A drop-down navigation is navigation that contains links that are nested two or more levels deep. The accessibility considerations we will discuss apply to all levels of nested navigations. So, for simplicity’s sake, we are going to demonstrate how to create a two-level navigation.

We’ll start with the simple site navigation that we created in [the previous chapter](https://practical-accessibility.today/chapters/navigation/), and we’re going to add a nested list of items as children to the “Products” item:

```html
<nav aria-labelledby="nav-label">
  <span hidden id="nav-label">Site</span>
  <ul>
    <li>
      <a href="/products/" aria-current="page"
        >Products</a
      >

      <ul role="list">
        <li><a href="/kitchen/">Kitchen</a></li>
        <li><a href="/bathroom/">Bathroom</a></li>
        <li>
          <a href="/personal-care/"
            >Personal Care</a
          >
        </li>
      </ul>
    </li>
    <li><a href="/team/">Team</a></li>
    <li><a href="/press/">Press</a></li>
  </ul>
</nav>
```

So, we’ll be working with three ‘top-level’ items (“Products”, “Team”, “Press”), and a list of nested items under the “Products” item.

With this markup, we have all our navigation items in place, the next step is to make the navigation interactive.

## What makes a drop-down navigation a drop-down navigation?

The main difference between a drop-down navigation and a flat navigation is that the drop-down navigation contains one (or more) items that, when activated, will toggle the display of more navigation items.

In other words, the core functionality of a drop-down navigation is in showing and hiding nested items when their ‘parent’ item is activated.

So, essentially, what makes a drop-down navigation what it is, is that some of its items–these ‘parents’—are **disclosure widgets.**

The markup of the navigation must convey these semantics so that it is understood by assistive technology users.

## Drop-down navigation markup & behavior

Every item in the navigation that toggles the display of other items is a disclosure widget. The item that toggles the display of additional items is the disclosure trigger, and the list of items revealed is what we called the disclosure widget’s ‘panel’ in [the disclosure widget chapter.](https://practical-accessibility.today/chapters/disclosure-widget/) We’re just going to refer to it as the ‘nested list’ or, simply, the ‘dropdown’ for each disclosure widget in this chapter.

By definition, a disclosure widget is a _button_, not a link. So, unless the navigation item that toggles the display of a nested list is required to take the user to a separate page (which is a pattern we will discuss in another section), this item must be a button, not a link.

So, the markup for our navigation needs to change to reflect that. The ‘Products’ hyperlink should become a `<button>`:

```html
<nav aria-labelledby="nav-label">
  <span hidden id="nav-label">Site</span>
  <ul>
    <li>
      <button
        aria-expanded="[ true | false ]"
        aria-controls="products-list">
        Products
        <svg
          width="1em"
          height="1em"
          viewBox="0 0 24 24"
          aria-hidden="true">
          <path
            fill="currentColor"
            d="M5.293 9.707l6 6c0.391 0.391 1.024 0.391 1.414 0l6-6c0.391-0.391 0.391-1.024 0-1.414s-1.024-0.391-1.414 0l-5.293 5.293-5.293-5.293c-0.391-0.391-1.024-0.391-1.414 0s-0.391 1.024 0 1.414z"></path>
        </svg>
      </button>
      <ul role="list" id="products-list">
        <li><a href="/kitchen/">Kitchen</a></li>
        <li><a href="/bathroom/">Bathroom</a></li>
        <li>
          <a href="/personal-care/"
            >Personal Care</a
          >
        </li>
      </ul>
    </li>
    <li><a href="/team/">Team</a></li>
    <li><a href="/press/">Press</a></li>
  </ul>
</nav>
```

To visually indicate the expanded/collapsed state of the button, I’m using an inline `<svg>` (an image of a chevron) inside the button. The icon will animate when the button’s state changes.

Like the custom disclosure widget we built in [the disclosure widget chapter](https://practical-accessibility.today/chapters/disclosure-widget/), the button will have an `aria-expanded` attribute indicating that the content it controls is expanded (when `true`) or collapsed (when `false`). And the `aria-controls` attribute creates a programmatic association between the button and the list it controls.

Then, to toggle the display of the nested list and update the value of the `aria-expanded` attribute on the button, you can use a short script similar to the one we created and used in the disclosure widget chapter.

To make sure that the navigation works for all users even those on slow internet connections and/or those who don’t have JavaScript enabled, we’re going to follow the same progressive enhancement approach that we did in that chapter.

Instead of providing the disclosure widgets in the markup by default, we start with a static version of the navigation — where “Products” is wrapped in a text node (such a `<span>`) rather than a button:

```html
<nav aria-labelledby="nav-label">
    <span hidden id="nav-label">Site</span>
    <ul>
        <li data-has-children>
            <span>
                Products
            <span>
            <ul role="list">
                <li><a href="/kitchen/">Kitchen</a></li>
                <li><a href="/bathroom/">Bathroom</a></li>
                <li><a href="/personal-care/">Personal Care</a></li>
            </ul>
        </li>
        <li><a href="/team/">Team</a></li>
        <li><a href="/press/">Press</a></li>
    </ul>
</nav>
```

…and then replace the `<span>` with the disclosure widget’s button when the JavaScript runs.

With no JavaScript running, the navigation items are all visible by default. When JavaScript is enabled, the script runs and replaces the `<span>`s with `<button>`s, adds the necessary ARIA attributes, and hides the nested lists using the hidden attribute. Then, when a button is activated, the script expands/collapses the nested list that it controls.

Using the `aria-expanded` attribute as a styling hook in CSS, you can animate the inline SVG icon to visually indicate its state.

```css
nav button[aria-expanded="true"] svg {
  transform: rotate(180deg);
}
```

Similarly, you can use the attribute to style the button itself when it is in an expanded or collapsed state.

To indicate the current page in the navigation, you can use `aria-current="page"` on the current link, and also use `aria-current` as a styling hook in your CSS.

Technically, this is all we need to make the navigation _technically accessible_. But we need to do a little more to make it more usable.

## Dismissing the open dropdown(s) using keyboard and mouse

Typically, when a dropdown is expanded, users expect to be able to dismiss it using the `Esc` key on their keyboard. This ensures that they don’t need to tab their way back to the disclosure toggle to collapse it. So you’re going to want to implement that using JavaScript.

When a dropdown is dismissed using the Esc key:

- focus should move back to the disclosure toggle that controls the dropdown;
- and the `aria-expanded` attribute should be updated to indicate that the dropdown is no longer expanded.

Similarly, mouse users expect the dropdown to be dismissed when they click anywhere outside of it. And the `aria-expanded` attribute on the toggle should also be updated when that happens to indicate that the dropdown has been collapsed.

Dropdowns should also be dismissed when keyboard focus moves outside the navigation — when the user tabs to another focusable element outside the navigation region. This ensures that the dropdown does not obscure parts of the page that the user navigates to. This is particularly important if there are interactive elements within those parts.

When an element receives focus, it must be clearly visible to the user so that they know what they are focusing on. The focusable element cannot be partially or completely obscured by other content on the page, otherwise you’d be in violation of [Success Criterion 2.4.12 Focus Not Obscured (Minimum)](https://www.w3.org/TR/WCAG22/#focus-not-obscured-minimum) and [2.4.13 Focus Not Obscured (Enhanced)](https://www.w3.org/TR/WCAG22/#focus-not-obscured-enhanced), respectively. If the dropdown in the navigation isn’t dismissed when the user tabs outside the navigation, you run the risk of violating these success criteria because there may be interactive elements that are obscured by the dropdown when it is expanded.

### What about arrow keys support?

Some website navigations may benefit from enabling arrow key support, particularly when the navigation is large, such as mega-drop-down navigations. Arrow key support enables users to navigate between the navigation items using Up, Down, Left and Right arrow keys.

Navigating using arrow keys is primarily for the benefit of keyboard users — particularly keyboard users not running a screen reader. Using arrow keys to navigate between items means that the navigation will contain less tab stops overall, which can make moving out of the navigation more efficient.

Arrow key support is optional for website navigation. It is not required for the navigation to be accessible. But implementing it may make the navigation more usable, especially if it contains dozens of items.

Since arrow keys support is not required, we will not be diving into its JavaScript implementation details.

If you want to implement arrow key support for your navigation, I recommend referring to the [“Disclosure Navigation Menu with Top-Level Links”](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/examples/disclosure-navigation-hybrid/) page in the ARIA Authoring Practices Guide. The drop-down navigation in this page is implemented by developer [Sarah Higley](https://sarahmhigley.com/), who documents how arrow key navigation works, and also includes a JavaScript file you can either use as-is, or adapt to your own projects.

There are also other markup patterns you may use to create a drop-down navigation…

## An alternative markup pattern

Some variations of drop-down navigations will require the parent item to be a link to a separate page.

If the parent item takes the user to a different page, it should be a link.

When you need the parent item to link to a separate page _and_ you need to toggle the display of nested links for that same item, you’re going to need both a link _and a separate_ disclosure widget — i.e. both a link _and_ a button.

![link and disclosure widget](/markdown-assets/26.2.drop-down-with-link.png)

A link can’t do double duty as a button.

If the “Products” item links to a separate Products page, it should remain a link. And we’re going to need to add a separate button associated with this link that will be responsible for toggling the display of the nested list.

This means that the markup for your navigation would look like this:

```html
<nav aria-labelledby="nav-label">
  <span hidden id="nav-label">Site</span>
  <ul role="list">
    <li>
      <!-- The link -->
      <a href="/products/">Products</a>
      <!-- + The disclosure widget -->
      <button
        aria-expanded="true"
        aria-controls="products-list">
        <svg
          width="1em"
          height="1em"
          viewBox="0 0 24 24"
          aria-hidden="true">
          <path
            fill="currentColor"
            d="M5.293 9.707l6 6c0.391 0.391 1.024 0.391 1.414 0l6-6c0.391-0.391 0.391-1.024 0-1.414s-1.024-0.391-1.414 0l-5.293 5.293-5.293-5.293c-0.391-0.391-1.024-0.391-1.414 0s-0.391 1.024 0 1.414z"></path>
        </svg>
      </button>

      <ul role="list" id="products-list">
        <li><a href="/kitchen/">Kitchen</a></li>
        <li><a href="/bathroom/">Bathroom</a></li>
        <li>
          <a href="/personal-care/"
            >Personal Care</a
          >
        </li>
      </ul>
    </li>
    <li><a href="/team/">Team</a></li>
    <li><a href="/press/">Press</a></li>
  </ul>
</nav>
```

The disclosure widget becomes an icon button that toggles the display of items that are nested under the link sitting next to it.

You know by now that there are several ways you can provide an accName to an icon button. But we won’t be using any of the techniques we discussed in the icon buttons chapter, though.

Since the icon button toggles the display of **items that are related to the link sitting next to it**, we can associate the button with the link by using the link’s name as an accName for the button, using `aria-labelledby`:

```html
<nav aria-labelledby="nav-label">
  <span hidden id="nav-label">Site</span>
  <ul role="list">
    <li>
      <a href="/products/" id="products"
        >Products</a
      >

      <button
        aria-expanded="true"
        aria-controls="products-list"
        aria-labelledby="products">
        <svg
          width="1em"
          height="1em"
          viewBox="0 0 24 24"
          aria-hidden="true">
          <path
            fill="currentColor"
            d="M5.293 9.707l6 6c0.391 0.391 1.024 0.391 1.414 0l6-6c0.391-0.391 0.391-1.024 0-1.414s-1.024-0.391-1.414 0l-5.293 5.293-5.293-5.293c-0.391-0.391-1.024-0.391-1.414 0s-0.391 1.024 0 1.414z"></path>
        </svg>
      </button>

      <ul role="list" id="products-list">
        <li><a href="/kitchen/">Kitchen</a></li>
        <li><a href="/bathroom/">Bathroom</a></li>
        <li>
          <a href="/personal-care/"
            >Personal Care</a
          >
        </li>
      </ul>
    </li>
    <li><a href="/team/">Team</a></li>
    <li><a href="/press/">Press</a></li>
  </ul>
</nav>
```

So the name of the link does double duty as the name of the icon button which toggles the display of its nested items.

The link is well-understood by all assistive technology users. And the icon button with the aria-expanded state attribute indicates that the button toggles the display of navigation items related the ‘Products’ category. The `aria-controls` attribute programmatically associates the button with the list it controls.

Just like the previous pattern, we can progressively-enhance this markup by creating and appending the button to the list item after the JavaScript runs.

### Minimum target size for the disclosure widget toggle

A very important thing to keep in mind with this pattern is that the size of the icon button needs to be large enough so that it’s easy for users to activate them.

[SC 2.5.5 Target Size (Level AAA)](https://www.w3.org/WAI/WCAG21/quickref/?showtechniques=255#target-size) requires that _"the size of the target for pointer inputs is at least 44 by 44 CSS pixels"_. The intent of this criterion is to ensure that interactive target sizes are large enough for users to activate them, even if the user is accessing content on a small handheld touch screen device, has limited dexterity, or has trouble activating small targets for other reasons. For instance, mice and similar pointing devices can be hard to use for these users, and a larger target will help them activate the target.

So, try to ensure the icon button meets this size requirement to avoid creating a barrier to access for your users.

### Indicating the current page

Another thing to keep in mind with this pattern is indicating the current item in the navigation.

In a drop-down navigation, when the current page is contained within a nested list, both the link representing the current page _as well as_ the parent item of this link are styled to indicate the user’s current location.

The `aria-current` attribute is used when an element within a set of related elements is visually styled to indicate it is the current item in the set. And since both the parent item and the current page item are visually styled to indicate the user’s location, `aria-current` can be used on both. But you want to differentiate between the link that represents the current page, and its parent.

For example, the ‘Products’ page in our example takes the user to the ‘Products’ page. If the user is currently on the ‘Kitchen’ page, you will indicate that the ‘Kitchen’ link is the current page using `aria-current="page"`:

```html
<nav aria-labelledby="nav-label">
  <span hidden id="nav-label">Site</span>
  <ul role="list">
    <li>
      <a href="/products/" id="products"
        >Products</a
      >

      <button
        aria-expanded="true"
        aria-controls="products-list"
        aria-labelledby="products">
        <svg
          width="1em"
          height="1em"
          viewBox="0 0 24 24"
          aria-hidden="true">
          <path
            fill="currentColor"
            d="M5.293 9.707l6 6c0.391 0.391 1.024 0.391 1.414 0l6-6c0.391-0.391 0.391-1.024 0-1.414s-1.024-0.391-1.414 0l-5.293 5.293-5.293-5.293c-0.391-0.391-1.024-0.391-1.414 0s-0.391 1.024 0 1.414z"></path>
        </svg>
      </button>

      <ul role="list" id="products-list">
        <li>
          <a href="/kitchen/" aria-current="page"
            >Kitchen</a
          >
        </li>
        <li><a href="/bathroom/">Bathroom</a></li>
        <li>
          <a href="/personal-care/"
            >Personal Care</a
          >
        </li>
      </ul>
    </li>
    <li><a href="/team/">Team</a></li>
    <li><a href="/press/">Press</a></li>
  </ul>
</nav>
```

`aria-current` comes with six pre-defined values: `true`, `false`, `page`, `step`, `location`, `date`, and `time`. And, [according to the specification](https://www.w3.org/TR/wai-aria-1.1/#aria-current), any value that isn’t one of these should be treated by ATs as `true`.

To indicate that the parent item is also ”active”, we can use the generic `true` value:

```html
<nav aria-labelledby="nav-label">
  <span hidden id="nav-label">Site</span>
  <ul role="list">
    <li>
      <a
        href="/products/"
        id="products"
        aria-current="true"
        >Products</a
      >

      <button
        aria-expanded="true"
        aria-controls="products-list"
        aria-labelledby="products">
        <svg
          width="1em"
          height="1em"
          viewBox="0 0 24 24"
          aria-hidden="true">
          <path
            fill="currentColor"
            d="M5.293 9.707l6 6c0.391 0.391 1.024 0.391 1.414 0l6-6c0.391-0.391 0.391-1.024 0-1.414s-1.024-0.391-1.414 0l-5.293 5.293-5.293-5.293c-0.391-0.391-1.024-0.391-1.414 0s-0.391 1.024 0 1.414z"></path>
        </svg>
      </button>

      <ul role="list" id="products-list">
        <li>
          <a href="/kitchen/" aria-current="page"
            >Kitchen</a
          >
        </li>
        <li><a href="/bathroom/">Bathroom</a></li>
        <li>
          <a href="/personal-care/"
            >Personal Care</a
          >
        </li>
      </ul>
    </li>
    <li><a href="/team/">Team</a></li>
    <li><a href="/press/">Press</a></li>
  </ul>
</nav>
```

This essentially says: “You are currently in Products. The current page is Kitchen.”

### What about hover states?

A lot of drop-down navigations you see on websites today show the nested navigation items when their parent item is hovered.

I personally don’t advocate for opening dropdowns on hover. In fact, I even advocate against opening drop-down navigations on hover, especially large ones like “megamenus”. Your research and requirements may encourage you to do so anyway. But in doing so, you increase the risk of violating [SC 1.4.13 Content on Hover or Focus (Level AA)](https://www.w3.org/WAI/WCAG21/quickref/?showtechniques=255#content-on-hover-or-focus).

As stated in [SC 1.4.13’s Understanding Page:](https://www.w3.org/WAI/WCAG21/Understanding/content-on-hover-or-focus.html)

> Additional content that appears and disappears in coordination with keyboard focus or pointer hover often leads to accessibility issues. Reasons for such issues include:
>
> 1. the user may not have intended to trigger the interaction
> 2. the user may not know new content has appeared
> 3. the new content may interfere with a user’s ability to do a task

The intent of SC 1.4.13 is to ensure that you implement hover interactions in such a way that the user can perceive the additional content, and dismiss it without disrupting their page experience.

If navigation dropdown opens on hover, you need to make sure that the semantic state matches the visual state. That is, when the drop-down opens on hover, you need to update the value of aria-expanded on the disclosure widget to reflect that it is open.

When the dropdown opens on hover, you also need to make sure the user can easily dismiss it without disrupting whatever they are doing on the page. One way to do that is by ensuring the dropdown closes when the user presses the `Esc` key.

The SC also requires that you ensure that the content that is shown on hover, can be hovered by the user with ease, while taking into consideration accessibility settings they may have enabled on their device. For example, if the user enlarges their mouse pointer, the pointer could obscure a significant area of the dropdown, making it difficult to see what they’re hovering on.

And there are also further timing considerations for _when_ to show a dropdown on hover. You need to programmatically distinguish between two different user intentions, as noted in [this article by the Nielsen Norman Group:](https://www.nngroup.com/articles/mega-menus-work-well/)

1. The user is just moving the mouse towards a target on the screen, and the mouse trajectory intersects 2.the link corresponding to the mega menu.
2. The user actually looks at the navigation categories and needs more information about them.

The second situation should trigger the mega menu, but the first should not.

To avoid opening a dropdown when it shouldn’t, you’ll need to adjust the response time to the hover event to make sure it doesn’t trigger the opening of the dropdown too soon.

If you build a navigation that shows nested items on hover, make sure you perform thorough usability testing with users of various types of assistive technologies to ensure that your dropdown does not create barriers to access for them.

And definitely **don’t build navigations that open _only_ on hover.** These navigations create barriers to access to many users, including users with a fine motor disability.

## Can you use _details_ and _summary_ to mark up the drop-down navigation instead of using a custom disclosure widget?

_Technically,_ yes. But you probably shouldn’t.

As you might remember from the disclosure widgets chapter, `<summary>` is not exposed the same way to assistive technologies across different platform accessibility APIs. And its announcements are inconsistent across browsers and screen reader combinations. Some of them will announce it as a ‘summary’ or a ‘disclosure triangle’, which does not exactly provide a clear indication to screen reader users of what will happen when the `<summary>` is activated.

While the contents of the navigation will be _technically accessible_ — as in, the content is there and available to be accessed by the user, they will be “functionally inaccessible”, as Scott O’Hara describes them.

Furthermore, as you already know by now, `<details>` is automatically expanded if/when the user uses Chromium browser’s in-page search functionality to search for a keyword. So, if someone searches for the word ‘Kitchen’ in our drop-down navigation, the dropdown will automatically expand and stay expanded, which is probably not what you want. If you use `<details>`, you’re going to need to explicitly override and prevent this behavior using JavaScript.

You will also need to add JavaScript to dismiss any expanded dropdowns when the Esc key is pressed or a click happens outside the dropdown.

So, while you _technically_ can use `<details>` and `<summary>` to to create the disclosure widgets in a drop-down navigation, using custom disclosure widgets and `<button>`s provides an overall more accessible user experience.

## What if you can’t use buttons?

What if you’re working with a navigation structure and markup that doesn’t allow the use of buttons? What if you’re working in a codebase where the navigation structure contains links and nested links, and you want to make the navigation more accessible but you can’t modify the markup?

A very common mistake developers will make is using the links as disclosure widgets instead of using buttons to toggle the display of the nested links without properly conveying the semantics and state, as well as implementing the required keyboard interactions to make this pattern work.

A very common mistake developers will do is to ‘nullify’ the link’s href value, and add an event listener that prevents the link’s default behavior and toggles the display of the nested links instead.

```html
<nav aria-labelledby="nav-label">
  <span hidden id="nav-label">Site</span>
  <ul role="list">
    <li>
      <a href="#" onclick="toggleDropdown()"
        >Products</a
      >

      <ul role="list" id="products-list">
        <li><a href="/kitchen/">Kitchen</a></li>
        <li><a href="/bathroom/">Bathroom</a></li>
        <li>
          <a href="/personal-care/"
            >Personal Care</a
          >
        </li>
      </ul>
    </li>
    <li><a href="/team/">Team</a></li>
    <li><a href="/press/">Press</a></li>
  </ul>
</nav>
```

This markup pattern is inaccessible. We mentioned in [the buttons vs links chapter](https://practical-accessibility.today/chapters/buttons-vs-links/) that quite often when you have a link with a nullified href value, what you really need is a button instead.

The anchor with the href attribute is exposed as a hyperlink. It basically says: “If you activate me, I’ll take you somewhere”. Only when the user activates it, it doesn’t take them anywhere.

When a link doesn’t take the user anywhere, it creates confusion. How do they know what the link does when they activate it?

This markup pattern breaks the user’s expectation of what’s going to happen when they activate the link; and it doesn’t clearly indicate what will happen when they do.

`aria-expanded` could, theoretically, be used to indicate that the link toggles the display of the dropdown. But even though `aria-expanded` is valid on a link, you should not do this.

`aria-expanded` indicates that the link toggles the display of something, but it still does not fix the usability issues associated with using a link to do button-y things. What should the user expect when they’re presented with a link, that can also toggle the display of something? Will activating the link expand/collapse that thing, or will it take them to a different destination?

Semantics convey purpose. And the semantics of the link in this markup are at odds with its behavior.

A link is not a button. It can become a button if it needs to, but it can’t be both a link and a button. And at this point, our link is trying to be both.

If you can’t use a button in your navigation to toggle the display of the nested links, or if you want to use the parent link as a ‘fallback’, you could enhance the link into a button. This is going to require ARIA and JavaScript.

### Enhancing a link into a button

To enhance a link into a button, you need to:

- expose it as a button to assistive technologies using ARIA (`role="button"`);
- and implement the expected keyboard behavior for a button;

…then you can go ahead and use aria-expanded and aria-controls on it the same way you would on a native `<button>`.

```html
<nav aria-labelledby="nav-label">
  <span hidden id="nav-label">Site</span>
  <ul role="list">
    <li>
      <a
        href="/products/"
        role="button"
        aria-expanded="[ true | false ]"
        aria-controls="products-list"
        >Products</a
      >

      <ul role="list" id="products-list">
        <li><a href="/kitchen/">Kitchen</a></li>
        <li><a href="/bathroom/">Bathroom</a></li>
        <li>
          <a href="/personal-care/"
            >Personal Care</a
          >
        </li>
      </ul>
    </li>
    <li><a href="/team/">Team</a></li>
    <li><a href="/press/">Press</a></li>
  </ul>
</nav>
```

We know that buttons and links are both operable by keyboard, but while links are activated using the Enter key, buttons can be activated using both the Enter key and the Space key.

Because we are using the `<a>` element to create our button, the browser is not going to provide a `<button>`’s keyboard behavior for us. The link can be activated using the Enter key, but you will need to make sure it can also be activated using the Space key, while taking into consideration the difference between how the Space and the Enter key are fired on a button — which is something we’ve already discussed in the [Applied ARIA – creating a custom button component](https://practical-accessibility.today/chapters/aria-button/) chapter.

## What about ARIA menu and menuitem roles?

If you’re new to accessibility, you will probably, at some point, hear about a set of ARIA attributes that are sometimes used by developers to mark up drop-down ”navigation menus”.

You may have noticed that I only _just_ used the term “menu”. I’ve been avoiding using this term the entire chapter. That’s because what we’ve been building so far is not a menu — at least not in accessibility and semantic terms.

**Site navigation is (probably) not a menu.**

The word “menu” in ARIA describes a specific type of menu _widget_. Menu widgets have the same purpose and functionality as native operating-system menus.

A menu is often **a list of common actions or functions that the user can invoke.** An example is the Finder Menu on macOS. Similar menus are available throughout applications on different operating systems. It usually consists of a main menu bar with pop-up menus. Items in pop up menus often have sub-pop-up menus. This may look like what a drop-down site navigation looks like, but the purpose, behavior, and interactions are not the same.

[menu Item usage](/markdown-assets/26.3.using-menuitem.mp4)

Semantically, a menu represents a list of menu items that trigger actions. It is not a list of navigation links that take the user places.

In ARIA, there are five roles that can be used to create operating-system-style action menus:

- menubar
- menu
- menuitem
- menuitemcheckbox
- menuitemradio

According to the specification:

> **The menubar role is used to create a menu bar similar to those found in Windows, Mac, and Gnome desktop applications. A menu bar is used to create a consistent set of frequently used commands.**

and:

> **A menu is often a list of common actions or functions that the user can invoke. The menu role is appropriate when a list of menu items is presented in a manner similar to a menu on a desktop application.**

There’s also the `toolbar` role which represents a collection of commonly used function buttons or controls represented in compact visual form. The `toolbar` is often a subset of functions found in a menubar, designed to reduce user effort in using these functions.

All of these roles, combined with other roles, are used to create operating-system-style menus. These roles come with specific, expected keyboard interactions. Menus must be operable using arrow keys, as well as Space and Enter keys, for example. And web **menus are expected to be operable in a similar manner.**

The ARIA Authoring Practices guide provides [guidance on the expected keyboard behavior for menus.](https://www.w3.org/WAI/ARIA/apg/patterns/menubar/examples/menubar-navigation/#kbd_label)

As you know by now, ARIA interactive widget roles don’t add interactivity to the elements that they are used. Native interactive HTML elements have keyboard behavior provided by the browser. But for ARIA interactive roles, you need to provide keyboard support to make sure that everything works as the user expects it to.

There are also rules to how the menu widget roles are used together. For example, a menuitem must be either a descendant of a menu or a group within a menu, or it must be owned by a menu (using `aria-owns`).

ARIA roles must also be used on the appropriate HTML elements. For example, if you have a list of items marked up using a list, and you’re using ARIA menu roles to enhance this list into a menu, you’ll need to be careful to apply the menuitem role to the links because they are the interactive element that will perform the action, not the list item.

The ARIA Authoring Practices Guide includes [a page that demonstrates how menu roles are used](https://www.w3.org/WAI/ARIA/apg/example-index/menubar/menubar-navigation.html) to create a desktop-style action menu. The page includes a live demo that you can test with a screen reader. When you use NVDA and tab into the menu widget, NVDA makes a short sound. This indicates that the screen reader has switched contexts.

Some ARIA roles automatically switch contexts for screen reader users. When that happens, screen readers essentially hand keyboard support back to the browser. This means that the screen reader is not going to handle any kind of keyboard navigation anymore. You have to implement the keyboard behavior that will enable the user to navigate and operate your widget. If you don’t, the user will get ‘stuck’ in your widget. This is even more problematic if the screen reader user is not an experienced one.

In other words, using menu widget roles may create an inconvenience for screen reader users by triggering application mode which disables their default navigation keys. And they will create a serious accessibility and usability problem if you don’t implement their expected keyboard behavior properly.

Menus require more complex keyboard implementations that are not needed and are probably even overkill for site navigation. The APG menu example page starts with word of caution:

> **CAUTION! Before considering use of the ARIA menubar pattern for site navigation, it is important to understand:**
>
> **The menubar pattern requires complex functionality that is unnecessary for typical site navigation that is styled to look like a menubar with expandable sections or “fly outs”. A pattern more suited for typical site navigation with expandable groups of links is the disclosure pattern. For an example, see Example Disclosure Navigation Menu.**

…which is what we have built in this chapter.

**Not all dropdowns are menus; nor should they be.** The only time I have personally used the menu and menuitem roles was when I worked with a client who was literally creating the Web version of an old Windows desktop application. The same functionality was carried from the desktop application to the Web — meaning that the menus were actual menus that triggered application actions.

Adrian Roselli has [an article](https://adrianroselli.com/2017/10/dont-use-aria-menu-roles-for-site-nav.html) in which he recommends against using menu and menuitem roles for the reasons I just mentioned; and he says in his article (and I agree) that:

> **A typical website is not an application. Sure, some claim to be “web apps”, and even make sweeping statements about how that is different than being a web page, but for the most part, websites, single-page applications (SPAs), blogs, news sites, and so on are not replicated installed native applications.**
>
> **As it stands today, using standard valid HTML for site navigation is a perfectly accessible method of navigating a site. The simplest pattern involves using the `<nav>` element, which acts as a landmark for screen readers and announces its purpose, nested `<ul>`s and `<li>`s for the navigation items, which provide a count and position within the list, and a proper `<a href="…">` for each link, which provides an accessible name and a keyboard stop.**

All this being said: If you do need to build an operating-system-style menu for a Web application, a good practice is to start with good underlying HTML, and enhancing that HTML with ARIA roles and states. Start with the same markup that you would use for a typical site navigation. And then **add ARIA as an enhancement via JavaScript** to enhance the navigation into a menu. If the JavaScript (and ARIA) fails or is not supported, the implicit semantics work as a fallback.

Léonie Watson gave a wonderful talk at Beyond Tellerrand in 2022 in which she demonstrates how semantics impact accessibility and her experience navigating the Web as a screen reader user. In her talk [“Bag of Spanners”](https://vimeo.com/708112296), she demonstrates how best to create a menu by enhancing a simple navigation using ARIA attributes. The entire talk is fantastic, so I highly recommend you watch it. ## Outro

If there’s only one takeaway you end this chapter with let is be that **more ARIA does not necessarily mean better accessibility.** ARIA is not the solution to everything. More often than not, the less ARIA you use, the better.

If you want to create a navigation for your website, use simple HTML with minimal ARIA.

Don’t over-engineer your components. The more you simplify your designs and components, the more usable they are likely going to be.
