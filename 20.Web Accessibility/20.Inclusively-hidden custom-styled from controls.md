# Case Study: Inclusively-hidden custom-styled form controls

Using native HTML controls has many practical benefits. Not _only_ do browsers provide keyboard interactions for free, but they also provide default styling for the different states of a control. For example, checkboxes and radio buttons have visual styles indicating when they are checked or selected. The browser also grays out (or dims) controls when they are disabled, and adjusts their colors to remain accessible in Forced Colors environments.

But default browser styles leave much to be desired. Not only are they inconsistent across browsers and platforms, but their aesthetics usually don’t match those of our design and brand. While it is possible to style form controls such as checkboxes and radio buttons more liberally [using CSS today](https://css-tricks.com/custom-styling-form-inputs-with-modern-css-features/), there may be times when using CSS alone is not enough. For example, if you want to create an animated checkbox like this one, which utilizes the [SVG line drawing technique](https://jakearchibald.com/2013/animated-line-drawing-svg/) to add a little more delight to the checkbox interaction:

`code`

Over the years, we’ve been hacking our way around form styling limitations by hiding the native controls and replacing them with what is essentially an image of the control. However, most of the implementations of this technique haven’t been entirely accessible.

In this chapter, we’re going to demonstrate how to hide a native form control while ensuring it remains accessible to users of assistive technologies — **particularly mobile screen reader users navigating by touch**. We will create a custom-styled checkbox to demonstrate the process, but **the technique we will learn is applicable to any other interactive form control** that you may want to replace with an image.

So, let’s get started!

## Setting the foundation in the markup

We’re going to use an inline `<svg>` image to create our custom checkbox styles.

Inlining the SVG is the most flexible way to embed it because it gives you full control over the contents of the SVG, so you can access and style them from your stylesheet. Plus, inline SVG is animatable, and it is more flexible in terms of adapting to Forced Colors modes like Windows Contrast Themes (which we will learn all about in [another chapter](https://practical-accessibility.today/chapter/forced-colors-mode/)).

We’re going to inline the `<svg>` after the checkbox in the markup so that it is easier to select and style using the CSS adjacent sibling selector (which we’re going to do in a few minutes).

To increase the checkbox’s interactive area, we’re going to place the checkbox (as well as the `<svg>`) inside its `<label>`.

```html
<label for="c-checkbox" class="c-custom-checkbox">
  <input type="checkbox" id="c-checkbox" />
  <svg
    width="32"
    height="32"
    viewBox="-4 -4 39 39"
    aria-hidden="true">
    <!-- The background -->
    <rect
      class="checkbox__background"
      width="35"
      height="35"
      x="-2"
      y="-2"
      stroke="currentColor"
      fill="none"
      stroke-width="3"
      rx="6"
      ry="6"></rect>
    <!-- The checkmark-->
    <polyline
      class="checkbox__checkmark"
      points="4,14 12,23 28,5"
      stroke="transparent"
      stroke-width="4"
      fill="none"></polyline>
  </svg>

  <span>Add an accessibility statement</span>
</label>
```

Since the `<svg>` is going to replace the checkbox **only visually, the checkbox itself needs to remain accessible to screen readers**. And since the checkbox is going to be exposed to screen readers, the `<svg>` can be hidden using `aria-hidden="true"` because its purpose, at this point, becomes purely presentational.

## Hiding the checkbox inclusively

With the `<svg>` in place, we now want to hide the checkbox while making sure it remains accessible to screen reader users. This is the main objective of this chapter.

Since we want to visually-hide the checkbox and make sure it remains screen-reader accessible, we will rule out all of the [hiding techniques](https://practical-accessibility.today/hiding-techniques/) that hide its presence from screen readers.

Most implementations utilize the `visually-hidden` utility class, which hides the checkbox visually without removing it from the accessibility tree.

Another common approach is to move the checkbox off-canvas — hiding it outside of the viewport using absolute positioning. This, too, removes it from view but does not remove it from the accessibility tree.

Both of these techniques accomplish the task of visually-hiding the checkbox while keeping it screen reader-accessible; **but neither of these techniques is inclusive of users navigating by touch.**

Screen readers on Android touch devices provide users with multiple ways to navigate the screen. One of these ways is [exploring by touch.](https://motorola-global-en-uk.custhelp.com/app/answers/indevice_detail/a_id/104169/p/30,6720,9299)

**Touch interface screen readers allow users to run their finger over the screen to hear what is directly underneath. This provides the user with a quick sense of an entire interface.**

— [Material Design Accessibility Guidelines](https://material.io/design/usability/accessibility.html#understanding-accessibility)

In other words, some mobile screen reader users explore pages on touch screens by literally **moving their finger on the page looking for interactive elements**.

When you create a checkbox (or any other interactive element, for that matter), a screen reader user navigating by touch will expect to ‘touch’ that checkbox as they move their finger across the screen. When they do, the screen reader announces the checkbox to them. And the way you hide it determines whether or not they will be able to do that.

As you can possibly imagine now, hiding the checkbox off-canvas (outside of the viewport area) will make it inaccessible to them, because they won’t find it within the viewport bounds as they run their finger over the page. Similarly, shrinking the checkbox to 1px will also make it very difficult to touch.

Here is a video recording in which I explore three checkboxes by touch on an Android touch device. The first checkbox is hidden inclusively using the hiding technique you will learn about in a couple of minutes. The second checkbox is hidden using the `visually-hidden` utility class (which we learned about in the [previous chapter](https://practical-accessibility.today/chapters/hiding-content/). And the third checkbox is hidden off-canvas using absolute positioning.

[using touch movement](/markdown-assets/20.1.using-touch-movement.mp4)

Notice how, as I move my finger across the screen, TalkBack announces the elements that I am dragging my finger on. It “finds” and announces the first checkbox, and announces that it is checked. But the second and third checkboxes are not accessible to me by touch, so their presence is never announced.

_You can test [the debug version of the Codepen](https://codepen.io/pen/debug/VwBmedd?editors=1100) using a touch device, too._

So, **while the `visually-hidden` utility class is great for visually-hiding static content (such as text), it should not be used to hide interactive elements**.

So, how _do_ you hide a checkbox inclusively? The answer is: hide it visually, but **make sure it is remains present in its natural position on the page** so that touch screen reader users can find it using haptic.

Technically speaking this means:

1. remove the checkbox from the page flow using position: absolute so that it doesn’t take up any unwanted space (visually),
2. position it (within the label) on top of the (SVG) image that is visually replacing it,
3. (optionally) enlarge the checkbox using relative width and height,
4. make it invisible by setting its opacity to zero.

Here is a clip demonstrating what that looks like step-by-step:

[styling the input for touch support](/markdown-assets/20.2.using-touch-movement.mp4)

_Note that I’ve already styled the SVG to convey the checkbox’s state in this demo, which is what I’ll cover in the next section._

The CSS that handles the positioning and hiding of the checkbox looks like this:

```css

.c-custom-checkbox {
..
/_ create a positioning context for the checkbox within the label _/
position: relative;
}

.c-custom-checkbox input[type="checkbox"] {
/_ remove the checkbox from flow _/
position: absolute;

    /* Optionally, enlarge the checkbox */
    width: 1em;
    height: 1em;

    /* make it invisible */
    opacity: 0;


    /* sometimes you may need to add z-index */
    z-index: ...;

}
```

So,

1. the checkbox is still where it is naturally expected to be on the page,
2. it is still interactive,
3. it is fully accessible to screen reader users,
4. but it is visually-hidden so it can be replaced with a more styliable alternative: the `<svg>`.

## Styling the SVG accessibly

Since the `<svg>` is going to visually replace the checkbox, it **needs to visually convey the checkbox’s various states**: checked, unchecked, disabled, focus, hover. (And if the checkbox has an indeterminate state, you will need to implement that too.)

The `<svg>` is placed right after the checkbox in the DOM, so we can select it using the [CSS adjacent sibling selector.](https://developer.mozilla.org/en-US/docs/Web/CSS/Adjacent_sibling_combinator)

We need to convey the same states of the native checkbox on the `<svg>`.

When the checkbox receives keyboard focus, we display the focus outline on the `<svg>`:

```css
/* show focus outline when the checkbox receives keyboard focus */
.c-custom-checkbox
  input[type="checkbox"]:focus-visible
  + svg {
  outline: 2px solid deepPink;
  outline-offset: 4px;
}
```

_We will learn all about providing accessible focus indicators for keyboard users in [another chapter.](https://practical-accessibility.today/chapters/focus-indicators/)_

Similarly, you can add disabled state styles using the `:disabled` selector if the checkbox is disabled.

```css
.c-custom-checkbox
  input[type="checkbox"]:disabled
  + svg {
  /*disabled styles */
}
```

And `animate/check/uncheck` the `<svg>` when the checkbox is checked using the :checked selector:

```css
/* style the checkmark & background of the SVG when the checkbox is checked */
.c-custom-checkbox
  input[type="checkbox"]:checked
  + svg {
  .checkbox__background {
  }

  .checkbox__checkmark {
  }
}
```

Using the SVG line drawing technique, your code might look similar to this:

```css
.c-custom-checkbox
  input[type="checkbox"]:checked
  + svg {
  .c-custom-checkbox svg path {
    transition: stroke-dashoffset 0.4s linear;
  }

  .c-custom-checkbox
    input[type="checkbox"]:checked
    + svg
    path {
    stroke-dashoffset: 0;
    stroke: currentColor;
  }
}
```

And finally, while you’re at it, you’ll want to optimize your custom ‘checkbox’ for forced colors environments.

```css
.c-custom-checkbox svg {
  @media screen and (forced-colors: active) {
    .checkbox__background {
      ..;
    }
  }
}

@media screen and (forced-colors: active) {
  .c-custom-checkbox
    input[type="checkbox"]:checked
    + svg {
    .checkbox___background {
      ..;
    }

    .checkbox__checkmark {
      ..;
    }
  }
}
```

We will learn all about adapting `<svg>`s and other content to Forced Colors mode in [another chapter](https://practical-accessibility.today/chapters/forced-colors-mode/).

## Outro

As we mentioned in the [previous chapter](https://practical-accessibility.today/chapters/hiding-techniques/), you will sometimes need to use a combination of hiding techniques to get the result that you need. When you hide an element, ask yourself who you are hiding it from, and who, if anyone, it should remain accessible to. And choose a hiding technique that accomplishes what you need without compromising the usability of your content.

When you need to hide a native interactive element because you’re visually replacing it with something else, don’t use the `visually-hidden` utility class. And don’t position the element outside the viewport bounds.
