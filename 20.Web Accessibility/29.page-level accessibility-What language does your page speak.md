Have you ever tried to pronounce a word in a foreign language that you didn’t recognize? I bet you’ve sounded funny and maybe even got a good laugh out of it. If you try to speak a Spanish sentence using English pronunciation, for example, the words won’t come out right, and are likely going to be difficult to understand by someone who only speaks Spanish.

## Why is document language important?

Assistive technologies like screen readers and other Text-To-Speech (TTS) software speak page content out to the user. And they need to speak the content in its natural language so that it can be understood by their users. So they **need to know what language a page is in, in order to speak or display it properly.** They need to know whether they can go ahead and produce output from the text, or whether perhaps they need to switch to a different language mode.

Most screen readers can speak content in foreign languages, **as long as the content language is identified in the HTML.**

If the page’s language is not identified, screen readers will try to _guess_ the language of the page, and they will typically fall back to the user’s default system setting. For example if the user’s default system language is English, then unless the document language has been explicitly identified in the document or overridden in the browser, a screen reader will usually guess that the page content is set in English, which may not be correct. It will then speak the content using English pronunciation, potentially making it difficult to understand.

For example, here I have a page here that contains 4 sentences in 4 different languages: English, German, French, and Spanish. And then I have a list of numbers from 1 to 10. I have no language defined in the markup, so both NVDA on Windows and VoiceOver on macOS will default to English — which is my operating system’s default language, and will read all four sentences using English pronunciation. The numbers will also be read in English.

Notice how the non-English sentences sounded? They were mostly incomprehensible. Now imagine an entire website being read out like that. Imagine what a terrible experience that would be!

[The 2023 WebAIM Million Report](https://webaim.org/projects/million/) showed that missing document language was one of the top five most common accessibility failures found on the top 1,000,000 websites. According to the report, **18.6% of home pages had missing document language!**

## Identifying page language is a WCAG requirement

Identifying page language is so important that is is a requirement for a page to be considered accessible under the Web Content Accessibility Guidelines.

[Success Criterion 3.1.1 Language of Page (Level A)](https://www.w3.org/WAI/WCAG21/quickref/#language-of-page) states that:

> **The default human language of each Web page can be programmatically determined.**

The intent of this criterion is to make sure that the language of a document is properly identified in the markup so assistive technologies and browsers can render text more accurately. As a result, users with disabilities will be better able to understand the content.

## Identifying the page language using the `lang` attribute

To specify **the language of the page,** you should use the `lang` attribute on the `<html>` element. This is inherited by all other elements. You should use the html element rather than the body element, since the body element doesn’t cover the text inside the document’s head element.

```html
<!-- this page's natural language is English -->
<html lang="en"></html>
```

For a page set in German, the value of the lang attribute will be de:

```html
<!-- this page's natural language is German -->
<html lang="de"></html>
```

An extended code is composed of one or more subtags separated by hyphens. The first two letters (or the first subtag) in the code is going to be the primary-language subtag (for example en). A region subtag associates the language with a particular region of the world (for example: en-gb, which stands for British English).

According to [advice by the W3C](https://www.w3.org/International/questions/qa-choosing-language-tags#langsubtag), _**the golden rule is to keep your language tag as short as possible.** Only add further subtags to your language tag if they are needed to distinguish the language from something else in the context where your content is used._ In other words, you should only use a region subtag if it contributes information needed in a particular context to distinguish this language tag from another one; otherwise leave it out. Region sub-tags are generally ignored by screen readers.

You can find all the subtags you will need to define a language in [the IANA Language Subtag Registry.](http://www.iana.org/assignments/language-subtag-registry) The registry is a long text file, containing nearly 8,000 entries. To find a primary-language subtag, search the page for the name of that language. For example, if you want to label something as French, searching for ‘French’ in the registry will bring you to a record that looks like this:

```code
%%
Type: language
Subtag: fr
Description: French
Added: 2005-10-16
Suppress-Script: Latn
%%
```

Your search will have matched against the `Description` field. Check that the type of this record is language. What you are looking for is the value in the Subtag field, ie. `fr`.

Since identifying the page’s language is a WCAG requirement, most automated accessibility checkers will tell you when the page is missing a lang attribute or when the attribute is present but has no value. But an automated checker will not be able to tell you if the value of the attribute correctly identifies the primary language of the page. You should manually check that the value of the lang attribute matches the natural language of the page’s content.

## Testing screen reader announcement for different languages

To read the content in the defined language, the screen reader must support that language. All modern screen readers have support for multiple languages. Sometimes you will need to manually install or configure language voices or “language packs”.

If you’re using VoiceOver on macOS, you may need to manually add the supported languages for VoiceOver to pronounce each language correctly.

To do that:

1. Go to **System Preferences > Accessibility**;
2. Select **VoiceOver**, and click **Open VoiceOver Utility.**

In VoiceOver Utility, Select Speech on the left. You’ll see a list of all languages on the right. You can add more languages by Clicking the **+** button at the bottom of the list.

[voice over in different languages](/markdown-assets/29.2.voice-over-language.mp4)
_In this video, I go through the steps outlined earlier to manually add language packs to VoiceOver on macOS._

By default, when the required language pack is available and installed, most screen readers are capable of reading foreign languages as long as they are marked up correctly within the document. But sometimes, settings may have been adjusted or may need to be adjusted, or a different speech synthesizer (or TTS Engine) needs to be used.

Here’s the same page I just showed you. In this example, I set the document language on the `<html>` element to German. I commented out all the sentences for now except for the German sentence. I also kept the list of numbers to demonstrate how they will be announced with the appropriate document language defined.

If I enable NVDA now, it should read the page using a German language, and it should also read the numbers in German instead of English. Only it doesn’t…

If you’re testing a multi-lingual site with a screen reader and the screen reader doesn’t automatically switch to the language defined in the document, you may need to switch to a different Text-To-Speech engine.

To do that in NVDA:

1. Open the NVDA menu (Press **insert + N**)
2. Select **Preferences > Settings**
3. In the Settings dialog, Select **Speech** on the left.

Make sure that **Automatic Language Switching** and **Automatic Dialect switching (when supported)** are checked.

In the **Synthesizer** dialog at the top of the panel, click **Change** to change the TTS engine. And choose one of the Engines available in the list. I chose **eSpeak NG.** You can further customize the voice of the screen reader to your liking.

Click **Apply** and select the **OK** button to close the dialog.

Now if we go back to our demo page, NVDA will read the sentence in German, and it will also read the numbers in German — which is the language that we defined on the `<html>` element.

## Using the `lang` attribute to identify language of parts

The `lang` attribute is also important for identifying languages on pages that contain multi-lingual content.

[WCAG Success Criterion 3.1.2 Language of Parts (Level AA)](https://www.w3.org/WAI/WCAG21/quickref/#language-of-parts) states that:

> **The human language of each passage or phrase in the content can be programmatically determined except for proper names, technical terms, words of indeterminate language, and words or phrases that have become part of the vernacular of the immediately surrounding text.**

The intent of this Success Criterion is to ensure that browsers and assistive technologies can correctly present content written in multiple languages.

By default, the language that you define on the `<html>` element is inherited by all elements on the page, unless you override that value and declare a different language on an element.

When you have more than one language on a page, you must define the language of each part of the page separately for screen readers to properly announce its content; the exception to this, as mentioned in the success criterion, are common foreign words (such as croissant; et tu Brutus; cappuccino). These words are exempt and you are not required to set their language.

You can use the `lang` attribute on parts of the page or even parts of a sentence that are set in a different language. For example, if you have a French statement in the context of an English paragraph, you can wrap the French sentence in a `<span>` and define the language of the sentence using the `lang` attribute on the `<span>`:

```html
<html lang="en">
  <!-- .. -->
  <body>
    <p>
      When Sally arrived in New York and got in
      the Taxi, she asked the driver:
      <span lang="fr"
        >“Parlez-vous Français?”</span
      >
    </p>
  </body>
</html>
```

## More benefits to identifying the page’s language

Knowing a Web page’s language is not only useful for accessibility.

- Some search engines let users restrict search results to those of a specific language. So your page can be listed among those search results when the language of the page is identified.

- Spelling and grammar checkers also need to know what language content is in; as do translation services.

- The `lang` attribute also prompts auto-translation services built into the browser (such as Google Translate built into Chrome).

- Browsers depend on the document language to render hyphenation properly when the CSS hyphens property is used. According to the specification, the browser must _"only automatically hyphenate text for which the content language is known and for which it has an appropriate hyphenation resource."_

- The `lang` attribute also allows the browser to display the language’s proper punctuation. For example, English, German and French languages use different quotation marks.

Here is what happens when I change the language on a page that contains a quote. When you use the HTML `<q>` element to create a quote, and the browser can identify the language that the page or the quote is in, it can display the proper punctuation marks:

## Styling content based on its language

And last but not least, when the language of a page, a part of a page, or an element in the page is defined using the lang attribute, you can use :lang() CSS pseudo-selector to apply language-specific styles to your content. For example, you may change line-breaking, justification, the line height, or the font face used on the page when the language is Arabic:

```html
html:lang('ar') { font-family: "Traditional
Arabic", "Al Bayan", serif; }
```

## Outro

Using the lang attribute is necessary to ensure your content is properly displayed and spoken by assistive technologies, so that it can be understood by your users. Leaving the attribute out creates a barrier to access for many users of assistive technologies.

Specifying the natural language of a page (or parts of it) is a requirement without which your content is considered inaccessible by the Web Content Accessibility Guidelines. Using the lang attribute appropriately where it is needed can get you to pass two WCAG success criteria, not just one. So, make sure you do so to ensure that your content is more accessible.
