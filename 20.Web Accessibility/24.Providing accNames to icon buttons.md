In this chapter, we’re going to look into various ways that you can provide an accessible name to an icon button. An icon button is a button that has an icon as a label and no visible accompanying text. These buttons can be found in the majority of apps and user interfaces today.

We will discuss five methods total. We will discuss the pros and cons of each method, which ones are the most widely supported and robust, as well as some considerations to keep in mind.

## The base markup

An icon _button_ is, semantically, a button. It is not an icon or an image that performs an action, because images are not interactive elements. So to create an icon button, we’re going to need to start with a simple `<button>` element so that assistive technology users understand the type of control that they are interacting with.

```html
<button></button>
```

For the icon inside the button, we’re going to use SVG. SVG is the most semantic, flexible, and resilient way to implement icons on the Web. Representing graphics like icons is literally what SVG is made for.

```html
<button>
  <svg width="24" height="28" viewBox="0 0 24 28">
    <!-- the icon -->
  </svg>
</button>
```

Another very common approach to creating the icon for the button involves using an icon font to render the icon using CSS:

```html
<button><i class="fa fa-bars"></i></button>
```

But icon fonts are far less flexible than SVG in terms of representing icons on the web as they come with their own limitations. Not to mention that they have a higher risk of failing to display an icon if and when the font does not load or the CSS isn’t used. So when you use an icon font, you run a higher risk of showing buttons without meaningful labels. Furthermore, when you use SVG to semantically represent icons, you can give the icon itself an accName, in which case the browser may use that to compute the accName of the button. We will elaborate more on this later.

Alright, so we have five different buttons that we’re going to apply our naming methods to.

If you pull up the browser DevTools and inspect any of these buttons, you’ll see that the button currently has no accName. If a blind screen reader user navigates to the button, their screen reader will only announce the button’s role, indicating that the user is interacting with a button; but it won’t announce a name, so the user won’t know what the purpose of the button is or what action it initiates. This makes the button unusable, and is also a violation of [SC 4.1.2 Name, Role, Value (Level A)](https://www.w3.org/WAI/WCAG21/quickref/#name-role-value) which mandates that interface components like buttons have an accessible name.

**`SC 4.1.2 Name, Role, Value (Level A): For all user interface components (including but not limited to: form elements, links and components generated by scripts), the name and role can be programmatically determined;…`**

## Giving the icon button an accName

We learned in [the accName computation chapter](https://practical-accessibility.today/chapters/accName-computation) that there are multiple ways you can give an accName to a button. We also know that an accName is a string of text that has been programmatically associated with the button. Currently, we’re not providing a name to any of the buttons using ARIA. And the icon is the only content inside each button, and since the icon has no text alternative, it does not provide an accName to the button.

Considering [the order of priority for providing accNames](https://practical-accessibility.today/chapters/accName-computation/#order-of-priority-for-choosing-an-accessible-name) to elements that we mentioned in the accName computation chapter, the most inclusive and robust way you can give the button a name is using its contents — more specifically, using a text node inside the button. Unless it’s hidden, this text node would provide both a label and a name to the button.

```html
<button>
  <svg width="24" height="28" viewBox="0 0 24 28">
    ...
  </svg>

  Like
</button>
```

When the button has a visible text label, and that label matches its accName, the button can be activated by all assistive technology users, including voice control users. Voice control users will want to speak the accName of an element to activate it. If the name is hidden, activating the button can be more tedious and time-consuming. We will learn more about voice control software and how voice control users navigate the web, as well as how that impacts our design and development decisions in [another chapter](https://practical-accessibility.today/chapters/label-in-name/).

**If you can provide a visible text label to your buttons, do so. And make sure it matches the button’s accName.**

Since the text label of the button identifies the purpose of the button, and since the icon does the same thing but graphically, the icon no longer adds any relevant information that a screen reader user needs to understand the purpose of the button. So, in order to avoid unnecessary announcements, hide the `<svg>` from screen readers using the `aria-hidden` attribute:

```html
<button>
  <svg
    width="24"
    height="28"
    viewBox="0 0 24 28"
    aria-hidden="true">
    ...
  </svg>

  Like
</button>
```

All this being said… this chapter is about providing accNames to _icon buttons_ that have no visible text label…

### Using the visually-hidden utility class

Since the button’s text label is supposed to be hidden, the most straightforward and robust way to give the button an accName is to hide the label visually, while making sure it remains accessible to screen readers. You can do that [using the `visually-hidden` utility class](https://practical-accessibility.today/chapters/hiding-techniques/#using-visually-hidden-text):

```html
<button>
  <svg height="21" viewBox="0 0 21 21" width="21">
    <g
      fill="none"
      fill-rule="evenodd"
      stroke="currentColor"
      stroke-linecap="round"
      stroke-linejoin="round"
      transform="translate(2 3)">
      <path
        d="m11.6427217 13.7567397-3.14377399-1.2567396h-4v-7.00000002h2l2.80105246-5.5c.57989907 0 1.07487363.2050252 1.48492373.61507546.4100508.41005058.6150761.90502516.6150755 1.48492425l-.8999994 2.40000029 4.0310597 1.34368655c.9979872.33266243 1.5591794 1.37584131 1.3086286 2.37964122l-.0684258.21997226-1.5536355 4.14302809c-.3878403 1.0342407-1.5406646 1.5582517-2.5749053 1.1704115z" />
      <path
        d="m1.5 4.5h2c.55228475 0 1 .44771525 1 1v8c0 .5522847-.44771525 1-1 1h-2c-.55228475 0-1-.4477153-1-1v-8c0-.55228475.44771525-1 1-1z" />
    </g>
  </svg>

  <span class="visually-hidden">Like</span>
</button>
```

Note that the `<svg>`, in this case, remains hidden from screen readers using the `aria-hidden` attribute.

If we inspect the button’s accName in the DevTools, sure enough you can see that the browser indicates that its accName is derived from its contents.

![Screenshot of the Chrome DevTools. The accessibility pane indicates that the button's accessible name is derived from its contents.](/markdown-assets/24.2.using-visually-hidden-utility-class.webp)

## Using hidden + aria-labelledby

Another way you can hide the text is by using the hidden attribute. Then, you can tell the browser to use the text as the accName of the button using the `aria-labelledby` attribute:

```html
<button aria-labelledby="edit-btn-label">
  <svg
    height="21"
    viewBox="0 0 21 21"
    width="21"
    aria-hidden="true">
    <g
      fill="none"
      fill-rule="evenodd"
      stroke="currentColor"
      stroke-linecap="round"
      stroke-linejoin="round"
      transform="translate(3 3)">
      <path
        d="m7 1.5h-4.5c-1.1045695 0-2 .8954305-2 2v9.0003682c0 1.1045695.8954305 2 2 2h10c1.1045695 0 2-.8954305 2-2v-4.5003682" />
      <path
        d="m14.5.46667982c.5549155.5734054.5474396 1.48588056-.0167966 2.05011677l-6.9832034 6.98320341-3 1 1-3 6.9874295-7.04563515c.5136195-.5178979 1.3296676-.55351813 1.8848509-.1045243z" />
      <path d="m12.5 2.5.953 1" />
    </g>
  </svg>

  <span hidden id="edit-btn-label">Edit</span>
</button>
```

As we mentioned in [the hiding techniques chapter](https://practical-accessibility.today/chapters/hiding-techniques/), according to [The Accessible Name and Description Computation specification](https://www.w3.org/TR/accname-1.1/#mapping_additional_nd_te), by default, assistive technologies do not relay hidden information, but you can explicitly override that and include hidden text as part of the accessible name by using `aria-labelledby`.

In other words, you may use a piece of content hidden using the `hidden` attribute for the purpose of providing an accessible name for elements that otherwise don’t visually have one. And that’s exactly what the `<span>` is doing in our example here.

If we pull up the Chrome DevTools again, sure enough we will see that the browser has provided an accessible name for the button using a `<span>` that is referenced via an `aria-labelledby` attribute.

![Screenshot of the Chrome DevTools. The accessibility pane indicates that the button's accessible name is derived from a span element that is referenced via the aria-labelledby attribute.](/markdown-assets/24.3.using-aria-labelledby.webp)

We have mentioned the advantages of using the `hidden` attribute over the `visually-hidden` utility class to provide an accName to an element in previous chapters. One advantage is that the text label will remain visually hidden even when your CSS is not used (such as in reader modes, for example).

This is my go-to method for providing an accName to icon buttons.

## Using aria-label

If you can’t use a visually-hidden text node to provide an accName to your icon button, you may use the `aria-label` attribute.

```html
<button aria-label="Download">
  <svg
    height="21"
    viewBox="0 0 21 21"
    width="21"
    aria-hidden="true">
    <g
      fill="none"
      fill-rule="evenodd"
      stroke="currentColor"
      stroke-linecap="round"
      stroke-linejoin="round"
      transform="translate(3 3)">
      <path d="m11.5 8.5-3.978 4-4.022-4" />
      <path d="m7.522.521v11.979" />
      <path
        d="m.5 9v4.5c0 1.1045695.8954305 2 2 2h10c1.1045695 0 2-.8954305 2-2v-4.5" />
    </g>
  </svg>
</button>
```

If we pull up the DevTools and inspect the accessible name of our button, you’ll see that Chrome uses the `aria-label` value as the accessible name for the button:

![Screenshot of the Chrome DevTools. The accessibility pane indicates that the button's accessible name is derived from the value of the aria-label attribute.](/markdown-assets/24.4.using-aria-label.webp)
