In this chapter, we’re going to look into various ways that you can provide an accessible name to an icon button. An icon button is a button that has an icon as a label and no visible accompanying text. These buttons can be found in the majority of apps and user interfaces today.

We will discuss five methods total. We will discuss the pros and cons of each method, which ones are the most widely supported and robust, as well as some considerations to keep in mind.

## The base markup

An icon _button_ is, semantically, a button. It is not an icon or an image that performs an action, because images are not interactive elements. So to create an icon button, we’re going to need to start with a simple `<button>` element so that assistive technology users understand the type of control that they are interacting with.

```html
<button></button>
```

For the icon inside the button, we’re going to use SVG. SVG is the most semantic, flexible, and resilient way to implement icons on the Web. Representing graphics like icons is literally what SVG is made for.

```html
<button>
  <svg width="24" height="28" viewBox="0 0 24 28">
    <!-- the icon -->
  </svg>
</button>
```

Another very common approach to creating the icon for the button involves using an icon font to render the icon using CSS:

```html
<button><i class="fa fa-bars"></i></button>
```

But icon fonts are far less flexible than SVG in terms of representing icons on the web as they come with their own limitations. Not to mention that they have a higher risk of failing to display an icon if and when the font does not load or the CSS isn’t used. So when you use an icon font, you run a higher risk of showing buttons without meaningful labels. Furthermore, when you use SVG to semantically represent icons, you can give the icon itself an accName, in which case the browser may use that to compute the accName of the button. We will elaborate more on this later.

Alright, so we have five different buttons that we’re going to apply our naming methods to.

If you pull up the browser DevTools and inspect any of these buttons, you’ll see that the button currently has no accName. If a blind screen reader user navigates to the button, their screen reader will only announce the button’s role, indicating that the user is interacting with a button; but it won’t announce a name, so the user won’t know what the purpose of the button is or what action it initiates. This makes the button unusable, and is also a violation of [SC 4.1.2 Name, Role, Value (Level A)](https://www.w3.org/WAI/WCAG21/quickref/#name-role-value) which mandates that interface components like buttons have an accessible name.

**`SC 4.1.2 Name, Role, Value (Level A): For all user interface components (including but not limited to: form elements, links and components generated by scripts), the name and role can be programmatically determined;…`**

## Giving the icon button an accName

We learned in [the accName computation chapter](https://practical-accessibility.today/chapters/accName-computation) that there are multiple ways you can give an accName to a button. We also know that an accName is a string of text that has been programmatically associated with the button. Currently, we’re not providing a name to any of the buttons using ARIA. And the icon is the only content inside each button, and since the icon has no text alternative, it does not provide an accName to the button.

Considering [the order of priority for providing accNames](https://practical-accessibility.today/chapters/accName-computation/#order-of-priority-for-choosing-an-accessible-name) to elements that we mentioned in the accName computation chapter, the most inclusive and robust way you can give the button a name is using its contents — more specifically, using a text node inside the button. Unless it’s hidden, this text node would provide both a label and a name to the button.

```html
<button>
  <svg width="24" height="28" viewBox="0 0 24 28">
    ...
  </svg>

  Like
</button>
```

When the button has a visible text label, and that label matches its accName, the button can be activated by all assistive technology users, including voice control users. Voice control users will want to speak the accName of an element to activate it. If the name is hidden, activating the button can be more tedious and time-consuming. We will learn more about voice control software and how voice control users navigate the web, as well as how that impacts our design and development decisions in [another chapter](https://practical-accessibility.today/chapters/label-in-name/).

**If you can provide a visible text label to your buttons, do so. And make sure it matches the button’s accName.**

Since the text label of the button identifies the purpose of the button, and since the icon does the same thing but graphically, the icon no longer adds any relevant information that a screen reader user needs to understand the purpose of the button. So, in order to avoid unnecessary announcements, hide the `<svg>` from screen readers using the `aria-hidden` attribute:

```html
<button>
  <svg
    width="24"
    height="28"
    viewBox="0 0 24 28"
    aria-hidden="true">
    ...
  </svg>

  Like
</button>
```

All this being said… this chapter is about providing accNames to _icon buttons_ that have no visible text label…

### Using the visually-hidden utility class

Since the button’s text label is supposed to be hidden, the most straightforward and robust way to give the button an accName is to hide the label visually, while making sure it remains accessible to screen readers. You can do that [using the `visually-hidden` utility class](https://practical-accessibility.today/chapters/hiding-techniques/#using-visually-hidden-text):

```html
<button>
  <svg height="21" viewBox="0 0 21 21" width="21">
    <g
      fill="none"
      fill-rule="evenodd"
      stroke="currentColor"
      stroke-linecap="round"
      stroke-linejoin="round"
      transform="translate(2 3)">
      <path
        d="m11.6427217 13.7567397-3.14377399-1.2567396h-4v-7.00000002h2l2.80105246-5.5c.57989907 0 1.07487363.2050252 1.48492373.61507546.4100508.41005058.6150761.90502516.6150755 1.48492425l-.8999994 2.40000029 4.0310597 1.34368655c.9979872.33266243 1.5591794 1.37584131 1.3086286 2.37964122l-.0684258.21997226-1.5536355 4.14302809c-.3878403 1.0342407-1.5406646 1.5582517-2.5749053 1.1704115z" />
      <path
        d="m1.5 4.5h2c.55228475 0 1 .44771525 1 1v8c0 .5522847-.44771525 1-1 1h-2c-.55228475 0-1-.4477153-1-1v-8c0-.55228475.44771525-1 1-1z" />
    </g>
  </svg>

  <span class="visually-hidden">Like</span>
</button>
```

Note that the `<svg>`, in this case, remains hidden from screen readers using the `aria-hidden` attribute.

If we inspect the button’s accName in the DevTools, sure enough you can see that the browser indicates that its accName is derived from its contents.

![Screenshot of the Chrome DevTools. The accessibility pane indicates that the button's accessible name is derived from its contents.](/markdown-assets/24.2.using-visually-hidden-utility-class.webp)

## Using hidden + aria-labelledby

Another way you can hide the text is by using the hidden attribute. Then, you can tell the browser to use the text as the accName of the button using the `aria-labelledby` attribute:

```html
<button aria-labelledby="edit-btn-label">
  <svg
    height="21"
    viewBox="0 0 21 21"
    width="21"
    aria-hidden="true">
    <g
      fill="none"
      fill-rule="evenodd"
      stroke="currentColor"
      stroke-linecap="round"
      stroke-linejoin="round"
      transform="translate(3 3)">
      <path
        d="m7 1.5h-4.5c-1.1045695 0-2 .8954305-2 2v9.0003682c0 1.1045695.8954305 2 2 2h10c1.1045695 0 2-.8954305 2-2v-4.5003682" />
      <path
        d="m14.5.46667982c.5549155.5734054.5474396 1.48588056-.0167966 2.05011677l-6.9832034 6.98320341-3 1 1-3 6.9874295-7.04563515c.5136195-.5178979 1.3296676-.55351813 1.8848509-.1045243z" />
      <path d="m12.5 2.5.953 1" />
    </g>
  </svg>

  <span hidden id="edit-btn-label">Edit</span>
</button>
```

As we mentioned in [the hiding techniques chapter](https://practical-accessibility.today/chapters/hiding-techniques/), according to [The Accessible Name and Description Computation specification](https://www.w3.org/TR/accname-1.1/#mapping_additional_nd_te), by default, assistive technologies do not relay hidden information, but you can explicitly override that and include hidden text as part of the accessible name by using `aria-labelledby`.

In other words, you may use a piece of content hidden using the `hidden` attribute for the purpose of providing an accessible name for elements that otherwise don’t visually have one. And that’s exactly what the `<span>` is doing in our example here.

If we pull up the Chrome DevTools again, sure enough we will see that the browser has provided an accessible name for the button using a `<span>` that is referenced via an `aria-labelledby` attribute.

![Screenshot of the Chrome DevTools. The accessibility pane indicates that the button's accessible name is derived from a span element that is referenced via the aria-labelledby attribute.](/markdown-assets/24.3.using-aria-labelledby.webp)

We have mentioned the advantages of using the `hidden` attribute over the `visually-hidden` utility class to provide an accName to an element in previous chapters. One advantage is that the text label will remain visually hidden even when your CSS is not used (such as in reader modes, for example).

This is my go-to method for providing an accName to icon buttons.

## Using aria-label

If you can’t use a visually-hidden text node to provide an accName to your icon button, you may use the `aria-label` attribute.

```html
<button aria-label="Download">
  <svg
    height="21"
    viewBox="0 0 21 21"
    width="21"
    aria-hidden="true">
    <g
      fill="none"
      fill-rule="evenodd"
      stroke="currentColor"
      stroke-linecap="round"
      stroke-linejoin="round"
      transform="translate(3 3)">
      <path d="m11.5 8.5-3.978 4-4.022-4" />
      <path d="m7.522.521v11.979" />
      <path
        d="m.5 9v4.5c0 1.1045695.8954305 2 2 2h10c1.1045695 0 2-.8954305 2-2v-4.5" />
    </g>
  </svg>
</button>
```

If we pull up the DevTools and inspect the accessible name of our button, you’ll see that Chrome uses the `aria-label` value as the accessible name for the button:

![Screenshot of the Chrome DevTools. The accessibility pane indicates that the button's accessible name is derived from the value of the aria-label attribute.](/markdown-assets/24.4.using-aria-label.webp)

When you use `aria-label`, its value will override the contents inside the button as the accName of the button. This means that the icon, as well as any other text content that may be inside your `<button>`, will no longer be announced as part of the button’s accessible name.

Furthermore, if the button does have a text label, this label will not be exposed as part of the button’s accessible name. For example, if I add a dummy piece of text inside the button: “the visible label”, in the DevTools, you will see that Chrome overrides the contents of the button with the value of the `aria-label` attribute:

![Screenshot of the Chrome DevTools. The accessibility pane indicates that the button's accessible name is derived from the value of the aria-label attribute, and the contents of the button are stroked to indicate that they have been overridden by the value of the aria-label attribute.](/markdown-assets/24.5.using-visible-label.webp)

This mismatch between the visible text label of the button and its accName creates a usability problem for voice control users; and sighted screen reader users interacting with the button may be confused when they hear a name that is different from the label they see. **The accessible name (that you provide in `aria-label`) must match the visible label of the button**, otherwise it creates a usability problem, and if the value of the label is not contained in the accName (as is the case for our dummy example here), you will be in violation of [**SC 2.5.3 Label in Name (Level A).**](https://www.w3.org/WAI/WCAG21/quickref/#label-in-name)

If the button has a text label, don’t use `aria-label`. If you do, you will need to manually ensure that the value of `aria-label` matches the label that the user sees.

And finally, remember that `aria-label` does not translate well, so when you use it to provide an accName for the button, you run the risk of the user not understanding the purpose of the button or the action it initiates if they don’t speak your content’s language. **Use `aria-label` only if you can’t use either of the previous two methods.**

### Using the SVG icon to provide an accName to the button

You can also use the SVG icon itself to provide an accName to the button.

You see, the SVG _is_ part of the content of the button. So, technically, it _can_ contribute to the accName computation of the button if it has a name of its own. If it does, then unless you give the button an accName using ARIA, the browser will pick up the accName of the `<svg>` and use that as an accessible name for the `<button>`. Since the name of the icon may be used as an accName for the button, **the name you provide to the icon should describe what the _button_ does, not what the icon is.**

With the absence of text identifying the button’s purpose, the `<svg>` itself can be used instead. So, you should no longer hide it using `aria-hidden`. Instead, you want to do two things:

1. Expose the `<svg>` as an image, and
2. give it a name that identifies the purpose of the button it will be providing an accName for.

#### Exposing the SVG as an image

Not all browsers expose `<svg>` as an image (or a graphic) by default. When the `<svg>` represents an icon, you will need to explicitly assign it an `img` role using ARIA so that it is exposed as an image:

```html
<svg
  width="24"
  height="28"
  viewBox="0 0 24 28"
  role="img">
  ...
</svg>
```

Once you’ve assigned it a role, it’s time to give it a name.

#### Giving the SVG an accName

There are two ways you can give an `<svg>` an accName:

##### Using the title element

The `<title>` element provides an alternative text description for the `<svg>` similar to how the alt attribute provides an alternative text description for an `<img>` element. So, you can use a `<title>` inside the `<svg>` to give it an accessible name. You just need to keep in mind that the `<title>` element needs to be the first child of its parent `<svg>`.

```html
<svg
  height="21"
  viewBox="0 0 21 21"
  width="21"
  role="img">
  <title>Send</title>

  <g
    fill="none"
    fill-rule="evenodd"
    stroke="currentColor"
    stroke-linecap="round"
    stroke-linejoin="round"
    transform="translate(3 2)">
    <path d="m15.5.465-8 8.033" />
    <path d="m10.5 16.5-3-8.002-7-2.998 15-5z" />
  </g>
</svg>
```

##### Using aria-label in SVG

Like most other elements that are allowed to have a name, you can also give the `<svg>` a name using the `aria-label` attribute.

```html
<svg
  height="21"
  viewBox="0 0 21 21"
  width="21"
  role="image"
  aria-label="Delete">
  <g
    fill="none"
    fill-rule="evenodd"
    stroke="currentColor"
    stroke-linecap="round"
    stroke-linejoin="round"
    transform="translate(3 2)">
    <path
      d="m2.5 2.5h10v12c0 1.1045695-.8954305 2-2 2h-6c-1.1045695 0-2-.8954305-2-2zm5-2c1.0543618 0 1.91816512.81587779 1.99451426 1.85073766l.00548574.14926234h-4c0-1.1045695.8954305-2 2-2z" />
    <path d="m.5 2.5h14" />
    <path d="m5.5 5.5v8" />
    <path d="m9.5 5.5v8" />
  </g>
</svg>
```

##### Using the SVG to provide an accName to the button

Giving the `<svg>` an announced accName should be enough for the browser to pick its name up and use it as an accName for the button. However, the two methods we just used to provide an accName to the `<svg>` don’t (currently) give the same results across all browsers and screen reader combinations.

At the time of making of this course, using `aria-label` on the `<svg>` is the most robust approach to successfully providing the button with an accName derived from its icon.

```html
<button>
  <svg
    height="21"
    viewBox="0 0 21 21"
    width="21"
    role="image"
    aria-label="Delete">
    <g
      fill="none"
      fill-rule="evenodd"
      stroke="currentColor"
      stroke-linecap="round"
      stroke-linejoin="round"
      transform="translate(3 2)">
      <path
        d="m2.5 2.5h10v12c0 1.1045695-.8954305 2-2 2h-6c-1.1045695 0-2-.8954305-2-2zm5-2c1.0543618 0 1.91816512.81587779 1.99451426 1.85073766l.00548574.14926234h-4c0-1.1045695.8954305-2 2-2z" />
      <path d="m.5 2.5h14" />
      <path d="m5.5 5.5v8" />
      <path d="m9.5 5.5v8" />
    </g>
  </svg>
</button>
```

When `aria-label` is used to give the `<svg>` a name, the name will be exposed and announced as the accName of the button by all relevant browser and screen reader combinations.

![Screenshot of the Chrome DevTools. The accessibility pane indicates that the accessible name of the button is derived from its contents (the svg with an aria-label).](/markdown-assets/24.6.using-svg-accName.webp)

When using `<title>` to provide an accName to the icon, the name of the icon is currently not announced as the accName of the button across all browser and screen reader pairings. More specifically, VoiceOver on macOS paired with Safari or Firefox currently does not announce a name for the button when the name is provided using an `<svg>` with a `<title>`.

To (partially) work around this, you need to re-enforce the relationship between `<title>` and the `<svg>` using ARIA. That is, you need to explicitly associate the `<title>` element with the `<svg>` using aria-labelledby:

```html
<svg
  height="21"
  viewBox="0 0 21 21"
  width="21"
  role="img"
  aria-labelledby="send-icon-label">
  <title id="send-icon-label">Send</title>

  <g
    fill="none"
    fill-rule="evenodd"
    stroke="currentColor"
    stroke-linecap="round"
    stroke-linejoin="round"
    transform="translate(3 2)">
    <path d="m15.5.465-8 8.033" />
    <path d="m10.5 16.5-3-8.002-7-2.998 15-5z" />
  </g>
</svg>
```

This, however, does not fill the gap in Firefox. VoiceOver still won’t announce the name of the icon as a name for the button when it is paired with Firefox.

In his article [Contextually Marking up accessible images and SVGs](https://www.scottohara.me/blog/2019/05/22/contextual-images-svgs-and-a11y.html), accessibility engineer Scott O’hara dives into the technical intricacies of the markup patterns used to implement accessible images and SVGs, and shares his extensive tests and findings on how those patterns work in different browser and screen reader pairings.

Scott’s test results are extremely important, and you will find that treating the icon inside a button as decorative and providing an accName to the button using one of the first three methods we discussed is often better than using the `<svg>` to provide an accessible name to the button.

**`To ensure that links and buttons containing SVGs will be accessible, regardless of the screen reader and browser pairing used, it may be best to provide accessible names via other means, and treat the SVG as decorative.`**

## So, which technique is the best?

So, even though you can use the icon itself to provide an accName for the button, it is currently not the most robust and inclusive way to do it.

Knowing that ARIA should be a last resort, not a default strategy, I personally recommend using a visually-hidden text label inside the button, as this remains the most reliable and robust approach.

While you could use `aria-label` on the icon and/or on the `<button>` itself, it is best not to rely on `aria-label` to provide accessible names for your components — for reasons we have mentioned in [previous chapters](https://practical-accessibility.today/chapters/accName-techniques/).

## Outro

If there needs to be one important takeaway from this chapter, let it be that **you should always, always perform your own tests to ensure that a pattern works or does not work as expected.** As Scott notes in his article, the test results and patterns that you may identify as providing the most robust support are often going to be "_representative of a snapshot in time_". Browser and assistive technology support changes, bugs may appear, gaps may be filled, and things may stop working the same way they have always worked.

The one piece of _"advice that I will give time and time again is to test the markup patterns you’re using and ensure the intended information is being communicated to all users."_
