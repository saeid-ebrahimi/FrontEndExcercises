In this chapter, we’re going to look into various ways that you can provide an accessible name to an icon button. An icon button is a button that has an icon as a label and no visible accompanying text. These buttons can be found in the majority of apps and user interfaces today.

We will discuss five methods total. We will discuss the pros and cons of each method, which ones are the most widely supported and robust, as well as some considerations to keep in mind.

## The base markup

An icon _button_ is, semantically, a button. It is not an icon or an image that performs an action, because images are not interactive elements. So to create an icon button, we’re going to need to start with a simple `<button>` element so that assistive technology users understand the type of control that they are interacting with.

```html
<button></button>
```

For the icon inside the button, we’re going to use SVG. SVG is the most semantic, flexible, and resilient way to implement icons on the Web. Representing graphics like icons is literally what SVG is made for.

```html
<button>
  <svg width="24" height="28" viewBox="0 0 24 28">
    <!-- the icon -->
  </svg>
</button>
```

Another very common approach to creating the icon for the button involves using an icon font to render the icon using CSS:

```html
<button><i class="fa fa-bars"></i></button>
```

But icon fonts are far less flexible than SVG in terms of representing icons on the web as they come with their own limitations. Not to mention that they have a higher risk of failing to display an icon if and when the font does not load or the CSS isn’t used. So when you use an icon font, you run a higher risk of showing buttons without meaningful labels. Furthermore, when you use SVG to semantically represent icons, you can give the icon itself an accName, in which case the browser may use that to compute the accName of the button. We will elaborate more on this later.

Alright, so we have five different buttons that we’re going to apply our naming methods to.

If you pull up the browser DevTools and inspect any of these buttons, you’ll see that the button currently has no accName. If a blind screen reader user navigates to the button, their screen reader will only announce the button’s role, indicating that the user is interacting with a button; but it won’t announce a name, so the user won’t know what the purpose of the button is or what action it initiates. This makes the button unusable, and is also a violation of [SC 4.1.2 Name, Role, Value (Level A)](https://www.w3.org/WAI/WCAG21/quickref/#name-role-value) which mandates that interface components like buttons have an accessible name.

**`SC 4.1.2 Name, Role, Value (Level A): For all user interface components (including but not limited to: form elements, links and components generated by scripts), the name and role can be programmatically determined;…`**
