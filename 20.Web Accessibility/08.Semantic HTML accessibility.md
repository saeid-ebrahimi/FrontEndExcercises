You will often hear that semantic HTML is important, and that if you don’t write semantic HTML, then your content will not be accessible. Conversely, you may also hear that if you write semantic HTML then you will get accessibility for free.

The truth is that _**this is only partly true**_.

Semantic HTML is _critical_ to the accessibility of your content. But you should be aware of what exactly makes semantic HTML accessible — particularly to assistive technologies like screen readers — so that you can write it as it is intended, in order to get the most out of its inherent accessibility. (Hint: it’s not the _semantics_ of semantic HTML that make semantic HTML accessible to screen readers!)

In this chapter, you will learn what semantic HTML is, and you will understand **_why_ it is critical to creating accessible websites and applications.** You will also learn _what_ makes semantic HTML accessible, so you can make more informed decisions about which elements to use for your content, and how the semantics of those elements affect (or don’t affect!) the accessibility of your components. Understanding what makes HTML accessible also enables you to better understand **why certain elements are announced the way they are** announced by different screen readers.

## What is semantic HTML?

Semantics express what something is. They convey purpose. They **describe what the element is, which is also an indication of how that thing is to be used.**

**HTML is semantic; it is descriptive and provides meaning**. Each HTML element describes the type of content that it represents. For example, the `<p>`element describes a paragraph of text; the `<ul>`element describes an unordered list (of items (`<li>`s)); the `<h1>` element describes a level 1 heading; and so on and so forth.

When Web professionals say “use semantic HTML” they usually mean “**use the right element for its correct purpose**” — if you have a heading, use a heading element; if you have a paragraph, use a `<p>` tag. If you want to create a button, use the `<button>` element.

> **When we use semantic HTML elements, we elevate the content’s meaning. It gives the content life.** — Jerry Jones , [The Importance of HTML](https://jerryjones.dev/2020/04/20/the-importance-of-html/)

## Why should you write semantic HTML?

**Semantic HTML is the universal language that all devices accessing the internet understand.** It is the language you use to communicate your content to these various devices, including but not limited to browsers, reading apps, screen readers (text-to-speech software), voice control software (speech-to-text software), smart watches, smart refrigerators, cars, and more.

By using semantic HTML, **you make your content understandable by present and future technology** — you make it more robust, which conforms to [one of the fundamental four principles of WCAG.](https://www.w3.org/WAI/WCAG21/quickref/?showtechniques=411#principle4)

Semantic HTML is important to describe the type of content that we are creating to various assistive technologies, **so that they can properly present it to the user.**

Assistive technologies like screen readers **rely on and ‘hook into the semantics of elements’ to present information and to create an interface for navigation for the user**. Without semantics, content will not be understandable by screen readers, nor by their users.

When you use the proper HTML elements everywhere, it allows different apps and devices to convey your content’s meaning to the user so that they know what to expect of it and how to interact with it.

Like assistive technologies, search engines also benefit from semantic HTML. **Semantics increase search engine accuracy and can increase the SEO rankings of your pages.**

> **In many ways, search engines are deaf, blind, use only a keyboard, and have limited technical abilities. Both rely on content structure, semantics, and functionality to either present content to users or determine the relevance of content.** — [“Web Accessibility and SEO”](https://webaim.org/blog/web-accessibility-and-seo/)**, WebAIM**

## How many semantic elements does HTML contain?

There are currently **114 semantic elements in HTML**. They start with the `<html>` root element, and 113 elements that represent various types of content and interactive controls, from headings and paragraphs, to landmarks, form input fields, buttons, disclosure widgets, dialogs, and many more.

**All 114 HTML elements have semantics.** (Yes, _all_ of them.) And each element serves a purpose. Using semantic HTML means knowing which element to choose for the right purpose.

**Using semantic HTML is critical to the accessibility of your content. But it does not guarantee that your content will be accessible, unless you author it correctly…**

## Semantic HTML is as useful to screen readers as its ARIA role mappings

Most semantic HTML elements and attributes have implicit role, state and property mappings. They are mapped to ARIA roles that are exposed to screen readers in the accessibility tree. For example:

- The `<nav>` element is mapped to a navigation role. So it is exposed as a navigation region to screen reader users.

- The `<h2>` element is mapped to a heading role, with the aria-level property set to the number in the element’s tag name, so the screen reader knows this is a level 2 heading.

- The `<img>` element is mapped to an img role, so users know that this is an image.

- The `<button>` is mapped to a button role, so users know it is a button. Since native HTML controls also come with functionality baked in, the button also has attributes indicating that it is focusable, for example.

An element’s role is the the first part of the accessibility information exposed in the accessibility tree. This means that semantics in HTML provide the first (and arguably most important) piece of accessibility information about an element. **The meaning (and by extension, the usefulness) of an HTML element to screen readers is determined by the ARIA role it maps to.**

[The HTML Accessibility API Mappings specification](https://www.w3.org/TR/html-aam-1.0/#html-element-role-mappings) documents all the HTML elements and the roles that they map to. We saw a quick overview of this specification in the [accessibility tree chapter](https://practical-accessibility.today/chapters/the-accessibility-tree/).

For your day-to-day work, [the ARIA in HTML specification](https://www.w3.org/TR/html-aria/#docconformance) provides a more developer-friendly list of mappings that you can refer to. These role mappings **give you _very important insights_** that **help you understand how your content is meant to be exposed to and announced by screen readers.**

The role mappings also provide guidance as to **how some semantic elements must be used to convey the meaning that they are meant to convey** to screen readers.

### 1. Not all HTML elements have equivalent ARIA roles

**There is no one-to-one relationship between HTML elements and platform accessibility APIs**. HTML may, at any time, include features that are not yet supported by AAPIs and have therefore no mappings.

For example, the `<picture>` element has no role mapping. It is not exposed as a “picture” to screen readers. In other words, screen readers don’t understand the semantics that the `<picture>` element carries. If you inspect the role of the `<picture>` in the accessibility tree, you’ll see that instead of exposing a role, Chrome notes that it is “not interesting for accessibility”.

```html
<picture>
  <source
    type="image/svg+xml"
    srcset="path/to/image.svg" />
  <img
    src="path/to/fallback.png"
    alt="Image description" />
</picture>
```

Does this mean that you shouldn’t care about using `<picture>` anymore? Of course not, because:

1. HTML accessibility API mappings are not set in stone. They get updated, and support for new HTML features may be added any time.
2. The `<picture>` element’s usefulness extends beyond semantic meaning, to improving page performance and other use cases that are not strictly related to accessibility. Furthermore, since the `<img>` inside of it is exposed (assuming it has proper alt text), it doesn’t matter if the `<picture>` itself is exposed — what matters is the outcome of using it: displaying an accessible image.

### 2. Not all HTML elements have unique implicit roles

Elements may share the same role even if they have different semantics. For example, both an `<ol>` and an `<ul>` (ordered and unordered lists) map to the same role: list. (You can also see that in the accessibility tree using your browser DevTools.)

Does this mean that you should use only one type of lists moving forward? No, because:

1. Ordered and unordered lists provide “visual semantics” (this is a term I just made up). When you use one list type or the other, you get the visual distinction between the lists — one displays bullets as markers, and the other displays numbers that reflect order (unless, of course, you override the default list styles. We’ll talk about this more in another section.)

2. Even though they map to the same role, the inherent semantics may still affect how each list type is announced by screen readers.

### 3. `div` and `span` are semantic

If you’ve been working in the field long enough, or if you’re new to the field, you may hear, have heard, or even have said statements along the lines of:

- All HTML elements are semantic, except for `<div>` and `<span>`. Use semantic HTML elements and use `<div>` and `<span>` only as a last resort.
  There are 114 HTML elements, and only two of these elements are not accessible:`<div>` and `<span>`.
  These statements, however, are not entirely true.

Semantics express what something is, and they convey purpose, right?

`<div>` and `<span>` are semantic. They represent generic containers. And if you check their ARIA role mappings, you’ll find that `<div>` and `<span>` map to the generic role.

The generic role creates a **nameless container element which carries no meaning on its own.** Unlike other meaningful elements, **a generic container does not give meaning or behavior to the content it contains.**

If a `<div>` contains a piece of text, there is no indication as to whether this text is a paragraph, or a heading, or a list of items, or even a link!

If the text is contained in a `<ul>` tag, it indicates that this is a list of things.

If the text is contained in a `<h2>`, it indicates that this is a level 2 heading.

If the text is contained in a `<a href="">`, it indicates that it is a link that goes somewhere.

But if the text is contained in a `<div>`, it loses its meaning and becomes just **a static string of text that could be anything, but is nothing.** It loses its meaning. Even if you style the `<div>` using CSS to look like a heading, or even like a button, **it would still lack the meaningful semantics required for assistive technologies to identify and expose it as one.**

```html
<!-- CSS class names do _not_ add semantics to HTML elements. -->
<div class="h1">
  I look like a heading but I am not.
</div>
<h1>I am a heading</h1>

<div class="button">Fake button</div>
<button type="button">Real button</button>
```

**All of this also means that you can use `<div>`s and `<span>`s in your markup, as long as you use them for their proper purpose. They still have a purpose**. They are useful as, well, generic containers that can be used as styling hooks in your CSS — as long as you make sure that you are not using them to represent content that should otherwise be represented with a meaningful element. You may use a `<div>` to wrap any kind of content, as long as that content is getting meaningful semantics from another element. (So, yes, it is ok to wrap your `<article>` or `<section>` with a `<div>` for layout purposes.)

This is the main difference between `<div>` and `<span>` and other semantic HTML elements.

Actually, even this isn’t entirely accurate. Because, as far as accessibility information goes, `<div>` and `<span>` are not the only generic containers in HTML…

### 4. Not all semantic elements map to roles that are useful to screen readers by default

`<div>` and `<span>` are not the only HTML elements that map to a generic role. There are other elements semantic elements that also map to the generic role and therefore don’t convey semantics that are meaningful to the user. Even some of the **meaningful elements will map to the generic role depending on the context you use them in**. For example, the `<header>` element maps to the banner role, which indicates that it is a landmark region that contains site-oriented content. But `<header>` doesn’t always map to banner, and it is not always exposed as a landmark. A header is only exposed as a banner landmark region if it is scoped to the `<body>` element. That is, it needs to be a direct child of the `<body>` element:

```html
<body>
  <header class="site-header">
    <!-- site header content (logo, nav, etc.) -->
  </header>
  <main id="main"><!-- main content --></main>
  <footer class="site-footer">
    <!-- main site footer -->
  </footer>
</body>
```

If the `<header>` is not a direct child of the `<body>`, it will also map to the generic role, just like a `<div>` does. The same applies to the `<footer>` element as well as some other landmark roles.

Does this mean that you should limit your usage of these elements to only the main page’s header and footer? No, because **even if their semantics aren’t useful in other contexts to screen readers, they are useful for other forms of assistive technologies that rely on semantics (not ARIA role mappings) to present information,** such as reader modes.

So just because an element doesn’t map to a useful role _by default_, doesn’t mean that it’s not useful — some of these elements may be critical for the accessibility of your content depending on the AT your users are using to consume your content. We will see quite a few more examples of this in upcoming chapters. Furthermore, as we mentioned before, accessibility API mappings may change and these elements may be associated with meaningful roles in the future.

And last but not least,…

### 5. Not all roles are exposed in the accessibility tree by default

Most text-level semantics such as `<strong>` and `<em>` are not included in the accessibility tree by default. Does this mean that they are not accessible? No, because:

1. Their content is accessible, and
2. they _may_ be included in the accessibility tree by some browsers; and the accessibility API **can expose them to the user on demand.**

Exposing text-level semantics and announcing them — such as when the text is italic, or bold — increases [the verbosity](https://en.m.wikipedia.org/wiki/Screen_reader#Verbosity) of the announcements that the user hears, which is not always be desirable. Some screen readers, such as VoiceOver on macOS, offer users the ability to [hear text attributes](https://support.apple.com/en-gb/guide/voiceover-guide/vo2720/web) by changing the verbosity level to their preference. If the user desires it, the verbosity settings allow them to construct a mental model of how webpages are displayed.

So whether an element is exposed in the accessibility tree or not depends on browser and accessibility API support. Some roles are exposed by some browsers, but not announced by screen readers unless the user requests them. Other roles aren’t exposed because browsers and/or assistive technologies have decided that they are not useful for the user, regardless of whether they are mapped to a role or not. Some roles aren’t currently exposed because there are gaps in implementation, but they may be filled in the future.

## Native semantic HTML controls come with accessibility features built in

One of the most common things you’ll hear from professionals advocating for semantic HTML is that **HTML elements come with a lot of accessibility features built in**. This is particularly true for native interactive HTML controls.

In addition to semantics identifying purpose, **interactive semantic HTML elements (such as links, buttons, and form controls) come with accessible keyboard functionality built in**. For example:

- when you use the `<button>` element to create a button, the user understands what the control is (via the implicit role mapping), and the browser provides all the required keyboard behavior out of the box. The button will be focusable, and will be operable using both `SPACE` and `ENTER` keys.

- When you use a group of `<input type="radio">`s with a shared name to create a group of options for the user to choose from, the browser adds keyboard interactivity to the radio buttons out of the box — the user can use the Up/Down/Right/Left Arrow keys to navigate between the options.

- When you implement a checkbox using `<input type="checkbox">`, the screen reader understands that this is a checkbox; the checkbox is focusable out of the box, and the user can check/uncheck it using the `Space` key.

All this **keyboard functionality is provided natively by the browser for free when you use semantic HTML elements.**

If you use a `<div>` to create a button, though, you don’t get this accessibility built into it. A `<div>` that is styled to look like a button is still, semantically, not a button. So the browser doesn’t provide the keyboard behavior like it does with a `<button>` element. A `<div>` is not inherently operable by keyboard:

- it is not focusable,
- and it cannot be activated using either the Space or the Enter keys (or even using a mouse).

You can turn a `<div>` into a button (which is something we’ll discuss in[another chapter](https://practical-accessibility.today/chapters/aria-button/)), but you will be required to provide the semantics, as well as the interactive behavior of a button using JavaScript. But why create a brittle implementation of something that HTML provides you with for free?

**Using the right element for the right purpose will give you a lot of accessibility for free.** Doing so is efficient because it will save you time and budget for other aspects of your product or service.

All this being said, **emerging complex native HTML controls should always be tested for accessibility and usability**. Just because a new element is native to the platform does not guarantee that it will be accessible from the first implementation. The `<dialog>` element is an example of a native HTML widget that wasn’t fully accessible for the first few years it was implemented in browsers. Accessibility engineer Scott O’Hara has documented [the past issues](https://www.scottohara.me/blog/2019/03/05/open-dialog.html) as well as the [current state of the `<dialog>` element](https://www.scottohara.me/blog/2023/01/26/use-the-dialog-element.html) in two blog posts that I recommend checking out for more details.

Similarly, new elements are being worked on by the [Open UI](https://open-ui.org/) group. The purpose of Open UI is to allow web developers to style and extend built-in web UI controls. New controls are currently being discussed that may start making their way into browsers any day. All of these controls need to be tested for accessibility before they are widely adopted.

**You can only confidently know that something works as expected by watching people succeed in using it.**

> **It’s not enough to point to best practices, if those best practices currently have gaps in implementation, have only a passable user experience, or result in avoidable assistive technology quirks.** >**Technology and user expectations change rapidly. We should always test to ensure not only emerging patterns work correctly, but tried and true patterns continue to work as we expect.** **— Scott O’Hara, Accessibility engineer**

## Choosing semantic HTML elements is not enough

The statement _Use semantic HTML and get accessibility for free_ **is a blanket statement**. Choosing the right semantic elements to give meaning to your content is critical. But there are also other considerations to keep in mind to ensure that you are using semantic HTML correctly to convey its meaning properly.

Choosing semantic HTML elements is not enough because:

### 1. Semantics provide only one piece of the accessibility information

We know by now that the browser exposes accessibility information to assistive technologies via the accessibility tree. And we know that the information in the accessibility tree includes the role as well as the name and other properties of an element.

This means that **semantics provide only one part of the information that assistive technologies need** to create a usable interface.

When people say “HTML is accessible by default” they typically mean that native HTML elements, when used correctly, come with meaningful semantics (and sometimes behavior) built-in. And that is true. The `<button>` is a usually a common demonstration of that. The HTML `<button>` comes with semantics and keyboard accessibility built in by default. But even a native button can be inaccessible.

If a button doesn’t have a name that identifies what it does, the user won’t know what to do with it. If a `<button>` is empty because it uses an icon from an Icon Font as a label, for example, it won’t have an accessible name that identifies what it does. While the `<button>` element exposes the appropriate semantics in the accessibility tree, the user needs more to operate it.

```html
<!-- this button doesn't have an accessible name because it is empty -->
<button class="icon-button">
  <i></i>
</button>
```

**Semantics express what the button is; but the accessible name makes it usable by identifying what it does.**

When you choose the right semantic element, you provide one (very important) piece of accessibility information. But you’ll want to make sure that you complement that with an accessible name, and possibly states and other attributes that are required for the understanding and operating of an element.

Furthermore,…

### 2. Some elements are only meaningful when they are used in conjunction with other elements

Some semantic elements will only provide the meaning they are intended to provide **when they are used in conjunction with other elements**. The `<label>` element is an example.

On its own, the `<label>` element doesn’t provide any particular accessibility benefits, because it’s not being used the way it is intended to be used. Even though the `<label>` element is semantic, using it alone is not enough. It only becomes useful when it is properly associated with the input it is providing a label for.

```html
<label>Your name</label>
<input type="text" autocomplete="name" />
```

When the `<label>` element is associated with a control using the for and id attributes, it is then exposed as an accessible name for that control in the accessibility tree:

```html
<label for="name">Your name</label>
<input
  type="text"
  autocomplete="name"
  id="name" />
```

A sighted user can associate a label with its control using visual cues like layout and positioning, but an assistive technology user needs this programmatic association to identify a control by its label.

Form controls missing accessible labels is one of the most common [accessibility issues found in the WebAIM 2022 Million survey](https://webaim.org/projects/million/#labels). According to the survey, 39% of the 4.4 million form inputs identified were not properly labeled. We will learn all about labeling form controls in [an upcoming chapter](https://practical-accessibility.today/chapters/forms/).

So, even when you use semantic elements, **you need to be thoughtful about how they are meant to be used**, otherwise you may still create barriers to access for some users.

## HTML semantics are affected by CSS

You should also be aware of how and when the CSS you write affects the semantics and overall accessibility of the elements you use.

Depending on the browser and screen reader combination, CSS can have unexpected and unwanted effects on HTML semantics.

For example, for many years, changing the `<table>` element’s default display using the display property resulted in the semantics of the table getting completely removed in browsers.

```css
/* This declaration used to remove table semantics
in browsers */
table {
  display: flex; /* or
'grid', or 'block', maybe. */
}
```

This means that if you had a table that you were using to display tabluar data, and you made that table responsive using Flexbox or Grid, you were also unintentionally removing all the inherent semantics of the table and its children in the process.

The `<table>` element’s semantics do not only provide meaning to screen reader users, but screen readers also provide [keyboard shortcuts](https://www.nvaccess.org/files/nvda/releases/2021.2/documentation/keyCommands.html) for navigating the table cells more efficiently. When the table semantics were removed, so were the usability features that came with it.

Conversely, setting display: table on an element does not add or re-instate table semantics on it. The only way to re-instate those semantics was to [explicitly add them using ARIA attributes.](https://adrianroselli.com/2018/02/tables-css-display-properties-and-aria.html#TheTable)

Adrian Roselli has an article on his blog that contains up-to-date [results of testing the effects of the different display property values on tables, lists, headings, and buttons](https://adrianroselli.com/2018/02/tables-css-display-properties-and-aria.html) that you may want to check out for more information about the past and present state of using display on these elements, including any bugs or browser regressions.

Fortunately, tables with flex, grid, and block display properties are now functional across all major browsers. But the way the display property has affected tables over the years is a good example of how CSS can sometimes produce unintended results that impact the accessibility of semantic HTML. Since regressions may happen in the future, make sure to perform your own testing when you use tables in your projects today.

CSS may sometimes modify element semantics in some but not all browser and screen reader pairings. For example, some versions of Safari on macOS will remove list semantics if you remove the default list markers in your CSS:

```css
/* This declaration removes list semantics in Webkit */
ul {
  list-style: none;
}
```

This behavior [was reported as a bug](https://bugs.webkit.org/show_bug.cgi?id=170179) before a Webkit engineer explained that this “bug” was in fact a purposeful change to improve the screen reader user experience:

> This was a purposeful change due to rampant “list”-itis by web developers. In the same way WebKit differentiates layout tables from data tables, it now differentiates layout lists from data lists. […] Basically, if you remove all default visible indication of the list, there is no indication to a sighted user or screen reader user that the content is a list. If you want to override this heuristic for accessibility, you can always add an explicit ARIA role=“list”.

The purpose of introducing this heuristic was to spare screen reader users unnecessary announcements associated with lists when lists were over-used by developers.

Newer versions of Safari (including Safari 16+) will remove list semantics unless the list is contained within a navigation landmark (`<nav>`). In other words, if you use a meaningless `<div>` to create your navigation instead of the `<nav>` element, not only will the navigation not be exposed as a navigation landmark anymore, but VoiceOver will also remove list semantics and all the useful information that comes bundled with it.

```css
/* In Safari 16+. this declaration removes list semantics in Webkit 
    UNLESS the list is contained in a <nav> element */
ul {
  list-style: none;
}
```

If your design requires you to override default list styles but the user does indeed benefit from list announcements (such as exposing how many items there are in a list, and the order of items in a list), you can re-instate the list semantics using the role attribute:

```css
<!-- re-instate list semantics using the role attribute -->
<ul role="list">
    <!-- list items here -->
</ul>
```

Then you can go forth and safely style the list any way you want in your CSS knowing that it will retain its semantics.

Alternatively, Manuel Matuzovich has found that you can [remove the default list markers using CSS without affecting its semantics](https://www.matuzo.at/blog/2023/removing-list-styles-without-affecting-semantics) in Webkit if you remove the markers using the `list-style-type` property instead, and settings its value to an empty string:

```css
ul {
  list-style-type: "";
}
```

The key idea I want you to take away from this section is that writing semantic HTML is important, but keep in mind that the CSS you write to style semantic elements may affect the semantics of those elements and the meaning they carry.

As we just saw, browsers sometimes introduce new heuristics that change how elements are exposed to assistive technologies if they find those changes necessary to improve the user experience or “fix” developer mis-use of certain features. And we will see a few more examples of this as we move through the course.

So you always, always want to check that your content works as expected in common browser and screen reader pairings, and be on constant lookout for bugs, “bugs” (browser heuristics), and gaps in implementation, even if you are using age-old practices.

HTML semantics are also affected by ARIA attributes.

## HTML semantics are affected ARIA attributes

ARIA is [a specification](https://www.w3.org/TR/wai-aria-1.1/) that defines a set of attributes that can be used to extend HTML.

Semantic HTML elements implicitly map to ARIA roles. The HTML accessibiliy API mappings define which ARIA role an element maps to.

**Using ARIA attributes, you can add, remove, modify, and completely override implicit HTML semantics.**

We will take a _very_ deep dive into ARIA in following chapters. In this section, I want to show you an example of how **the mere presence** of an ARIA attribute on a native HTML control can change how that control is announced by screen readers.

The case in point is the `<button>` element. By default, the `<button>` element maps to the button role, and is announced as a button by all screen readers by default. But the `<button>` element’s ARIA role mapping will change in most accessibility APIs if the `aria-pressed` or `aria-haspopup` attributes are specified on it:

```html
<!-- a button with an implicit role exposed as a button but all AAPIs -->
<button>Do Something</button>

<!-- a button with an implicit role exposed as a toggle button by some AAPIs -->
<button aria-pressed="true">Dark theme</button>
```

When the aria-pressed attribute is used on a `<button>` to indicate that this button is pressed, some browser+AAPI combinations will expose the `<button>` as a toggle button, indicating that this `<button>` toggles a certain functionality.

ARIA attributes can do more to semantics than change how they are announced. You can use ARIA to override implicit semantics when it is useful to do so, and to create new semantics when HTML semantics fall short. After all, HTML provides a limited set of interactive controls, but there are components like grids and Tabs, for example, that currently have no equivalent HTML semantics. We will learn all about how powerful (and dangerous) ARIA attributes are in another chapter.

## Outro

Everything we just covered in this chapter is why statements like _use semantic HTML and get accessibility for free_ are blanket statements. And now you know better and understand why.

**HTML is the foundation of accessibility on the Web**. And it should be written and maintained just as thoughtfully and purposefully as any other programming language. As Scott O’Hara says: _**Your semantic HTML is only as accessible as you make it, and maintain it.**_

Semantic HTML comes with a lot of accessibility baked in, but **semantics are not enough**. When you create a new element, consider how the element is exposed in the accessibility tree. Make sure all pieces of accessibility information are there. And consider how the element works and is operated.

Remember that **modern browsers and assistive technologies are updated frequently**. This means that support for features may be added, gaps in implementations may be filled, bugs may be fixed, and even HTML AAMs may change. On the other hand, browsers may introduce new heuristics, new bugs may appear with new updates, and new features may lack proper implementations.

**Perform your own testing.** Just like you test your styles and Javascript across browsers, you need to give your markup the same time and attention to ensure that your content is as accessible across browsers and screen readers.

Make some time to learn about each element in more depth. **A strong grasp of HTML will get you far ahead — farther than most developers in the industry.**

Whether you’re a front-end developer, a back-end developer, or both: **if you’re creating user interfaces, you need to know your HTML.** Learn not only what each element is or does, but also how it relates to other elements, what markup is valid and what isn’t, and, most importantly, why.

**Semantics play a vitally important role for someone who uses a screen reader.** As such, every decision you make as a developer of code impacts the accessibility and usability of the content for the user.

There are 114 (!!!) semantic elements in HTML for you to choose from! Don’t limit yourself to `<div>`s and `<span>`s.

Native HTML elements come with semantics that not only provide meaning, but often also aid navigating a webpage.

In the next chapter, we’re going to learn how to structure our pages using semantic HTML, and how this structure benefits screen reader users and helps them discover and navigate page content more efficiently.
